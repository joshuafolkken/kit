# josh CLI — Run Board, Report and Handoff Command Reference

The commands a run calls to report, show its board, hand off and chain its verification. The rest of the run lifecycle: `docs/josh-commands-run.md`. Where each command came from: `docs/maintainers/josh-commands-run-rationale.md` → "Where each command came from".

A `<!-- usage: … -->` span is generated by `pnpm josh command:derive` from the command's registry entry (`scripts/josh/josh-commands-*.ts`) — edit the entry, not the span.

## Reports, board and handoff

### `josh run:report`

<!-- usage: run:report -->

Generate the session-facing report for this invocation from the run’s event stream (merges, parks, cuts) with the release tail — the same text josh notify sends.

```bash
pnpm josh run:report                              # print the report; the same text josh notify sends
pnpm josh run:report --handoff                    # print the backlogrun hand-off report and send it as the confirmation
pnpm josh run:report --end                        # end the run: the report, run:carry --end, run:wake --stop — stops at a failed stage
pnpm josh run:report --end --stopped "<reason>"   # end a run that stopped: run:carry --end --stopped sends the confirmation
```

<!-- /usage -->

It reuses `run:event`'s `format_event` for every line and appends the release tail `release:scope` decides (the request and the command on `required`, `unknown` printed as `unknown`, silent on `skip`).

**It renders one invocation, not the whole stream**: the scope comes from the run record's start time, so earlier events are left out, and because that field survives a `--cut` the events either side of a cut stay in one report.

**A scope it cannot determine — no record, or one it cannot read — prints a notice and no events**, never a fallback to everything. That is why the report is generated before `pnpm josh run:carry --end` removes the record: `.claude/skills/workflow-commands/backlogrun-steps.md` → "End the record when the run ends" is that ordering rule's single source.

`josh notify --body-file` sends exactly this output, so the AI writes only Step 0's three lines.

### `josh run:event`

<!-- usage: run:event -->

Append to, read or watch the run’s append-only event stream (--append <kind> <text> | --from|--follow <n> | --watch [<n>] | --last).

```bash
pnpm josh run:event --append <kind> <text>   # append one event; prints its position
pnpm josh run:event --from <position>        # every event after <position>, in order (JSON)
pnpm josh run:event --follow <position>      # new events, waiting for one; position on stderr
pnpm josh run:event --watch [<position>]     # every new event, rendered, until interrupted
pnpm josh run:event --last                   # the newest event alone
```

<!-- /usage -->

Keyed to the common git directory `run:carry` uses, so parent and lane children append to one stream that survives a session cut. `--watch` is for debugging; the ambient pane is `run:board`.

`--follow` is `--from` that waits, returning at an event or else at the interval. Events go to stdout and the next position to stderr — the same before
and after a cut. `--watch` loops that pass, printing `HH:MM · <label> · <text>` in the session language.

`<kind>` is one the single enumeration names (`plan`, `child-launch`, `merge`, `park`, `outage`, `usage-limit`, `cut`,
`resume`, `stop`, `pr-opened`, `review-round`, `filed`, `note`, `lane-phase`, `step`, `setup`, `pr-checks`); a kind outside it is refused.
`lane-phase` is a child's first implementation edit (PreToolUse hook) or a driver step.
`pr-checks` is `josh followup`'s poll of a PR's checks, written on change.
`setup` is one stage the run works through (`planning`, `dispatching #<N>`, …) — a trace `run:board` times, never a position.
`filed` is an Issue `issue:file` created, and `note` a one-line
observation below the filing bar (`run:board` shows both). `run:merge` appends `merge`, `park`,
`outage` and `usage-limit`; other steps call `--append`. The stream is bounded.

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh run:event` in detail".

### `josh run:progress`

<!-- usage: run:progress -->

Report an unattended run’s progress once it has gone quiet for an interval.

```bash
pnpm josh run:progress --output <path>
pnpm josh run:progress --once                                                 # five labelled lines now, whatever the clock says
pnpm josh run:progress --interval 20 --repo joshuafolkken/app-kit --hours 4
```

**Options:**

- `--mark` — record that a real report happened without printing a line (keeps the last line for `run:wake --list`).
- `--path` — print the ambient heartbeat log's path and exit. Every heartbeat line is mirrored there, so `tail -F "$(pnpm josh run:progress --path)"` follows the run across a `backlogrun` session cut. Reads no run state, so it answers in a lane child too.
- `--interval <min>` — silence interval (default 20; also `JOSH_PROGRESS_INTERVAL_MINUTES`, then `josh.progress_interval_minutes`).
- `--wait` — start once in the background: as it starts it prints `progress-watcher.md` → "Progress while the run is quiet" once per session (a repeat names it in one line — `run:entry` has printed it first outside a lane child); each report then goes to the event stream and ambient log, never stdout; exits only on an arrival, `josh followup` ending the run, or `--hours`.
- `--hours <n>` — how long the watcher lives (default 8 with `--wait`, 1 otherwise).
- `--repo <owner/name>` — scopes the read.

<!-- /usage -->

**Output / exit codes:** stdout carries only the five labelled progress lines; notices go to stderr. `--once` with no run recorded prints nothing and exits 0; an unreadable listing exits 1. It sends no Telegram; `JOSH_PROGRESS=0` reports nothing (`--mark` still records).

### `josh run:board`

<!-- usage: run:board -->

Draw a live board of the running backlogrun, redrawn every second.

```bash
pnpm josh run:board             # redraw until interrupted
pnpm josh run:board --once      # one frame, then exit
pnpm josh run:board --chat      # one frame for a chat, recorded as a progress report
pnpm josh run:board --every 5   # the --chat frame as a 📊 Progress Telegram every 5 minutes, until the run ends
```

**Options:**

- `--chat` — answers a `backlogrun`, `fullrun` or `halfrun` progress question: the frame `--once` draws, with only `🧠` on the machine line and no escapes; it records the report as `run:progress --mark` does.
- `--every <minutes>` — sends the `--chat` frame as a `📊 Progress` Telegram now and every `<minutes>` until the run ends — only when a person asks for it.

<!-- /usage -->

`josh init`/`josh sync` ship it in `.vscode/tasks.json` as the `josh: run board` task, run from "Tasks: Run Task".

The header is three lines — the first two in three columns, the third a spinner and time under the second column, then the kind's icon and words under the third:

```
▶ backlogrun  ⏰ 7°18′07″  ✅  1/2 ■■■■■───── (+1)  🔄 1  ⏳ 0  💤 0  📮 87/6,912
  kit         💓      20″  💪  11% ■─────────  🧠  29% ■■■───────  💾 2.6M/s ■─────────
              ⠦        4″  🔧 #<N> · Bash pnpm josh test:related
```

The first line is how far the run is: its state mark and name, `⏰` elapsed in degree-minute-second form (`1°15′57″`, `26″` — every length on the board; a colon is a time of day), a progress bar, per-state counts, `📮` open/closed issues. `🛫`: start to first lane.

The second line is what the run is on: the repository's name, `💓` age of the newest event (yellow past 15 quiet minutes, red past 30), and machine gauges (`💪` CPU, `🧠` memory, `💾` swap rate). `⏰` and `💓` share a column, digits right-aligned; both lines' first bars start in one.

The third line is what the run is doing now: a spinner, its age, then the kind's icon and words.

- **At a stage** — the stage's words then why: `⠸  2′31″  🤔 waiting on judgment — 4 waiting`.
- **At a stage a session works on** — that session's newest operation: `⠼  3″  📝 planning · Bash pnpm josh backlog:plan`.
- **Children running, no stage** — the newest child operation or event: `⠙  4″  🔧 #<N> · Bash pnpm josh test:related`.
- **No operation readable** — a log that is missing, unreadable or holds no call falls back to the stage with its time and reason, or how many children run (`🔄 2 running`), with no time.
- **Watching** — nothing running and no stage: `24′10″  🔭 watching — pool empty`, counted from the newest thing the run did (a merge, a park, the drain, or the stage it last stood at).
- **Ended** — the newest thing the run did, in that event's words, timed up to the end: `42″  🔚 backlog drained`.

Below the header: the `📈 throughput` section, `24h` in hourly cells and `7d` in 12-hour cells (a sparkline of closes per cell scaled to the row's peak, `┊` a stopped cell; `⚡` closes per active hour over complete cells, `🟢` active hours, `✅` closes, `🏔` the peak cell's rate and start, `🔄` closes this hour; folded with `t`); then the `⛽ usage` section, Claude's and Codex's 5h and 7d gauges (window label, percent, `┊` at even pace, `≈N` tasks left at the spend per task of the last ten done logs (its derivation: the rationale's "`josh run:board` in detail"), the reset time, and `N′` the reading's age once it is over ten minutes old; read off lane logs and Codex rollout files, no API asked; folded with `u`), and GitHub's `rest` and `graphql` allowances in the same columns, the calls left in place of `≈N`, then a row per touched child (phase icon, elapsed time, CPU and memory), then an earlier run's lane holding a place (drawn alike, `🧳` after its title, never counted as the run's) and `❔` a lane with no lane state record (counted in use, its state unknown), the children not yet started under one `⏳ queued` heading, waiting and parked children, and the newest filings, parks and notes, with a legend at the foot.

A section folded with its key stays folded across launches: every fold is saved to `~/.claude/josh/board.json` (under `$CLAUDE_CONFIG_DIR` when it is set), shared by every repository, and the next live board starts from it. Several boards open at once leave the last fold.

A missing or broken file opens every section; an unknown section name is dropped. A board that is not a terminal (`--chat`, `--once` into a pipe) neither reads nor writes it.

`⏳ queued` lists the rows in the order `backlog:plan --waves` plays them, with no wave headings: a batch starts each row once a lane and its declared paths are free, so the icon a row leads with is what it waits on. An epic's children stay gathered under the epic.

A child whose open lane has had no child process for `lane:await`'s 15-second re-confirm window is drawn stopped; an unanswered probe leaves it running. A single frame that finds an idle lane waits out the window and reads again. A lane this run's record ended (`lane:close`) is stopped too.

A stopped row's times freeze at its stop — the record's end, else its first idle read or transcript's last write, if earlier — and its tail reads `stopped by <command>` if recorded. A child labelled stopped whose transcript reads running stays running: `ship stopped by <command>`.

A finished row leads with `✅` merged, `🏁` done, `⏩` closed by `josh issue:already-done` or `🚫` withdrawn.

マージせず終了した行は、記録済みの短い英語の結論を右端に表示し、その文全体から根拠のIssueコメントを開く。結論（ASCII、1行、80文字以内）は `issue:comment`・`issue:already-done`・`issue:measured`・`issue:premise-unmet` の `--outcome <summary>` で記録する。過去の根拠には `issue:comment --evidence-url <comment URL>` を併用する。同じIssue内に実在する信頼済みコメントだけを根拠とする。管理用のwithdrawコメントは結論を上書きしない。根拠なし・取得失敗では短い英語の代替表示になる。狭い端末では文を省略してからリンクを付け、chat/plainでは同じ可視文字をリンク制御なしで表示する。

停止中のparked/decision行も同じ短い英文と根拠リンクを使う。markerのない過去の停止は、本文を確認して `issue:comment --outcome <next action> --evidence-url <stop comment URL>` で補完する。補完は最新停止に紐づくものだけが有効で、再開後の新しい停止には引き継がない。説明不明でも最新停止コメントのリンクを残し、取得失敗ならIssueを開く `Reason unavailable: inspect issue` を表示する。描画時のAI要約は行わない。リンク非対応の端末やchat/plainでは行頭のIssue番号からIssueを開き、最新停止コメントを確認する（CLIでは `pnpm josh issue:read <N>`）。補完記録は承認・解除・再開を代行しない。

A queued or waiting row draws `<icon> <condition> <number> <kind> <title>  <tail>`: the icon says what it waits on, in place of `⏳`, and the condition column — 11 columns in both sections, the width of `MM-DD HH:MM` — holds its figure, so every row's number starts in one column. The legend names each wait icon the frame draws. A row leads with one icon only, the first of these that holds:

- `🚪` / `📥` / `📤` `<time>` — how long its lane has been opening, installing or dispatching.
- `❓` — neither `run:lane` nor `run:solo`, and a blocker stands (the column names the first) or its start is ahead; a person may judge.
- `🔗 <N>` — a standing blocker; with more, `<N>+<rest>`, the rest after the title. A first blocker too wide for the column (`owner/repo#N`) leaves it blank; every blocker follows the title.
- `🙋 <N>` — withheld for a person; the tail is `→ decide #<B>: <title>`, even with no blocker left.
- `📅 <MM-DD HH:MM>` — the body's `- 実施可能日:` names a UTC time not yet reached, so `backlog:next` (in UTC) withholds it; the board shows local time.
- `📅 <n>/<K>` / `📅 <PR>` — the body's `- 実施可能条件: #<PR> のマージ後 <K> マージ` is not yet met: the lane ledger has recorded `n` of the `K` merges it waits on after `<PR>` merged, or `<PR>` has not merged (or its merge is unread).
  The issue form, `#<issue> を閉じる PR のマージ後 <K> マージ`, shows `<issue>` and counts after the merged pull request that closed it.
- `📋 <N>` — a named run's declared issue `<N>` is ahead of it, in flight or not yet started. Never on a `run:add` issue.
- `✋` — neither `run:lane` nor `run:solo`, due, and nothing blocks it; `backlog:next` holds it alone for its judgment and offers the triaged rows.
- `🔒 <N>` — the running issue `<N>` carries `run:solo`, so nothing starts until it merges or is parked; a waiting `run:solo` row leads with it too. `epic_solo`'s reading, as `backlog:next`'s "carries `run:solo` and is running …".
- `🧍 <N>` — a `run:solo` issue, the first among the judged, due and unblocked rows, waits for the running lane `<N>` to finish; with more, `<N>+<rest>`, the rest after the title. `epic_solo`'s reading, as `backlog:next`'s "carries `run:solo` and waits …".
- `🙅 <N>` — ranked behind the waiting `run:solo` issue `<N>`, which nothing is offered past.
- `📂 <N>` — a path it declares — its recorded plan, else its plan comment, else its body — overlaps one the running issue `<N>` declares, the path after the title; `backlog:next` answers "waits: its `<file>` overlaps …".
- `🧵 <used>/<limit>` — the open lanes fill the limit `lane:limit` prints, read at the board's last local read. It counts every lane `lane:limit` does, an earlier run's too; an unread limit leaves it blank.
  An empty seat draws a `💺` line under the lanes rule: the first `blocked: #<N>: <cause>` while the newest launch was refused, the rest `no issue ready to start` when no waiting row is free to start, `held — <sentence>` while the ledger's open hold stops one that is.
  A held seat with no candidate ends `— <sentence>`. The sentence says what holds the seat and who fills it, as `— open issues await your triage` for `hand-back:judge`.
  The ledger keeps the code (`backlog-hold-text.ts` translates it); an unknown code is shown as is. No seat line is drawn while a free row is about to take the seat, before the plan is read, once the run stopped, or for a single run; none counts as a lane row.
- `🧠 <n>%` — a lane is free, but the driver opens none while the kernel reads critical memory pressure, 🧠 is red or 💾 swaps at a red rate, `💾 <n>M/s` after the title; it resumes within one poll once the kernel reads under critical and both are under yellow. The ledger records the hold as `memory` (its own `lane:stats` row); an unread figure is left out.
- `⏳` with a blank column — no wait is read.

A `🙋` or stopped row outside those sections still ends `🔗` and every standing blocker. A blocked `run:stalled` row ends `waiting on #<B>`.
Above the legend, the terminal board thanks the people who helped review kit, read from a published roster.

While the run is at its `planning` stage, the one row it launches next — a named run's next declared issue, else the plan's first waiting row — leads with `📝 <time>` in place of any wait above; no other row draws it.

On a terminal it draws on the alternate screen, so redraws never grow the scrollback; Ctrl+C, SIGTERM or a normal exit restores the screen and cursor. `--once`, or a stdout that is not a terminal, writes one frame with no screen control and exits — no color either when it is not a terminal.

**Output / exit codes:** exits 0; an unknown argument or a bad `--every` exits 1; Ctrl+C exits 130 and SIGTERM 143. With no run, running or ended, and no held single run (below), it prints `no run`; while the reads fail it prints `❗ read HH:MM <reason>` instead.

A running `fullrun #N` or `halfrun #N` this checkout's `run:hold` record holds is drawn as a one-row board under its own name, the row's phase read from #N's events — over a carry record too, outside a lane; a stop-marked hold is not running.

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh run:board` in detail".

### `josh run:pickup`

<!-- usage: run:pickup -->

Pick the lanes up after a manual cut: launch what the epics offer, then each liveness and the watcher line.

```bash
pnpm josh run:pickup        # one line per lane, then the watcher line
pnpm josh run:pickup 5800   # first one line per child the epic offers: launched, refused or its verdict
```

<!-- /usage -->

With epics named, first `epic:next --lanes` and a `lane:launch` per offered child, one line each: launched, not launched and why, or the verdict (`triage`). Per lane, its `run:liveness` verdict or the `lane:output` to run; then the watcher, printed, never started. Exits 1 when the offer could not be read.

### `josh run:handoff-lanes`

<!-- usage: run:handoff-lanes -->

Chain a backlogrun hand-off: cost --cut, the lane reading, run:carry --cut, run:board --chat and run:report --handoff, answering under, cut, blocked or capped.

```bash
pnpm josh run:handoff-lanes   # after each child’s merge; prints the verdict line, then its next action
```

<!-- /usage -->

`blocked` names each in-flight lane with an unreadable seat or no output path; no cut is taken.

**Output / exit codes:** the four verdicts exit 0; a failed step stops the chain with its exit code.

### `josh run:handoff`

<!-- usage: run:handoff -->

Hand a workflow keyword typed in a consultation session to a child on the role profile model.

```bash
pnpm josh run:handoff kickoff new --brief-file .josh/tmp/brief.md   # waits; prints its final message and URLs
pnpm josh run:handoff fullrun <N> --brief-file .josh/tmp/brief.md   # detached; a bare N is #N; check it with run:progress --once
pnpm josh run:handoff backlogrun <E> --only                         # josh backlogrun with this session’s --agent
```

<!-- /usage -->

Consultation main (Fable / Astra): uses its provider's role profile (`kickoff` / `retrospective` scheduler, else worker). Background `kickoff`. Lane children cannot use `run:handoff`: exit 1 before launch; continue in the current session.

`run:handoff retrospective` starts the end-of-run unit on a generated brief and waits; the brief's close names the calling session as `--owner`, since the carry is that session's. It exits 0 only once the carry holds the unit's `run:carry --retrospective` mark, and exits 1 without starting when the mark is already there.

**Output / exit codes:** exits 0 once the child starts (`kickoff`: once it exits 0); `backlogrun` exits with `josh backlogrun`'s code. A bad argument, an unreadable brief, an unresolvable profile, no git repository, a failed start, or a tree hold that blocks the child's `run:entry` claim exits 1.

A hand-off still starting has not claimed yet, so `run:entry` stays the guard.

### `josh run:watcher:guard`

<!-- usage: run:watcher:guard -->

Guard: exits non-zero when lane children are in-flight but the watcher has not pinged recently.

```bash
pnpm josh run:watcher:guard
```

<!-- /usage -->

The watcher is fresh when `run:progress` has pinged its life record within three watcher ticks, roughly 90 s. Wired as a `PreToolUse` hook, so no next Bash call is issued while it is stale.

**Output / exit codes:** exits 0 when no lane children are in-flight or the watcher is fresh. Exits 1 and writes a note to stderr telling the user to restart `run:progress --wait` before proceeding.

### `josh run:chain`

<!-- usage: run:chain -->

Open the review, or --join to join, attest and record it; --ship starts ship --detach --review after a clean record. Stops at the first refusal with its next action.

```bash
pnpm josh run:chain <N>                                # after `run:cut <N>` alone: merge main (not in a lane child), answer the self-check, run the scoped pair, open the review
pnpm josh run:chain <N> --from check:related           # resume at the stage a stop named, once the run settled it
pnpm josh run:chain <N> --unpinned-ok "only logs"      # forwarded to run:review as given
pnpm josh run:chain <N> --join                         # join the gate, attest and record; every finding holds for disposition
pnpm josh run:chain <N> --join --fixing                # the same, when round 1 has fixes to make
pnpm josh run:chain <N> --join --ship "<title> #<N>"   # ship a clean round; title must match the issue. Record interaction review first.
```
