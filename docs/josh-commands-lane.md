# josh CLI — Lane Command Reference

The commands a run calls to open, dispatch, plan and measure its lanes. The run lifecycle: `docs/josh-commands-run.md`. Where each command came from: `docs/maintainers/josh-commands-run-rationale.md` → "Where each command came from".

A `<!-- usage: … -->` span is generated by `pnpm josh command:derive` from the command's registry entry (`scripts/josh/josh-commands-*.ts`) — edit the entry, not the span.

## Lanes

### `josh lane:open` / `josh lane:close` / `josh lane:list` / `josh lane:prune`

<!-- usage: lane:open -->

Open a lane: a linked work tree with its own branch and its own port seed.

```bash
pnpm josh lane:open 1490   # prints the lane directory on stdout
```

<!-- /usage -->

<!-- usage: lane:close -->

Close a lane, leaving no work tree, branch or directory behind.

```bash
pnpm josh lane:close 1490
pnpm josh lane:close --all
```

**Options:**

- `--all` — closes every lane.

<!-- /usage -->

<!-- usage: lane:list -->

List the open lanes: which issue, which ports, and where each one is.

```bash
pnpm josh lane:list
```

<!-- /usage -->

<!-- usage: lane:prune -->

Close every lane an interruption left without its work tree and every spent lane, then sweep unregistered leftovers under the lanes root.

```bash
pnpm josh lane:prune
```

<!-- /usage -->

`lane:open` branches from default, installs dependencies, copies main's gate caches/hooks, then runs the project's `josh.lane.setup`.

Project setup, `josh.lane.setup` in the lane's `package.json`:

- One shell command, run through `pnpm exec --shell-mode` in the new lane after the install and cache seeding.
- `JOSH_MAIN_CHECKOUT` holds the main checkout's path, for example to copy or link a build directory such as `target/`.
- Unset, nothing runs.
- A non-zero exit fails `lane:open` as a failed install does: its output is on stderr, and the work tree stays for a rerun or `lane:close`.

```json
{ "josh": { "lane": { "setup": "cp -R \"$JOSH_MAIN_CHECKOUT/target\" target" } } }
```

Unreadable `.env`: report lane/reason on stderr; check ports before allocating other seats. Failed process/socket probes refuse allocation.

`lane:prune` names each lane it keeps, with why, on stderr.

`backlog:drive` runs `lane:prune` before each open `backlog:offer` read (`backlog-drive-rate.ts`): leftover lanes are cleared, foreign ones are kept and named with why on the driver's stderr. A failed prune never stops the offer.

Codex hooks in a lane: Codex runs the main checkout's `.codex/hooks.json` in every lane.

- Its trust is the main path and definition hash in `~/.codex/config.toml` `[hooks.state]`.
- Each command finds the lane's scripts through `git rev-parse --show-toplevel`.
- No per-lane trust; `--dangerously-bypass-hook-trust` is never passed.
- A lane's own `.codex/hooks.json` edit takes effect only after it reaches the main checkout.
- A changed hook definition reads `modified` and Codex skips it in every checkout until a person re-approves it in Codex's hook review.

**Settings:**

- `JOSH_LANE_ROOT` — where lanes go; unset means `.<repository-name>-lanes`, a hidden sibling of the repository root.
- `JOSH_LANE_LIMIT` — how many lanes one repository may run at once (default 4); applied by `josh epic:next`. A live `lane:limit` override takes precedence; memory admission may hold starts below the limit.

**Output / exit codes:** `lane:open` prints its directory on stdout, reasons on stderr; refusal exits non-zero with empty stdout. Seats `1..9` (main: 0) are claimed atomically. Install or `josh.lane.setup` failure fails; warming is best-effort. `lane:list`: one row per lane — issue, seat, ports, branch, state, directory, output path, profile.

**`in-progress` / lane:** `lane:list` reports label/lane mismatches on stderr without changing labels.

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh lane:open` / `josh lane:close` / `josh lane:list` / `josh lane:prune` in detail".

#### `josh lane:output`

<!-- usage: lane:output -->

Record, or read back, where the unit running a lane’s child writes.

```bash
pnpm josh lane:output 1713 /abs/path/to/agent-7.jsonl   # record it; prints the path back
pnpm josh lane:output 1713                              # read it; prints the path, or `none`
```

<!-- /usage -->

The record lives in the lane's own `.env`; a lane whose `.env` cannot be read is refused rather than replaced.

**Output / exit codes:** the recorded path prints on stdout. `none` prints and exits non-zero (the lane is open but its child is not handed over yet).

#### `josh lane:dispatch`

<!-- usage: lane:dispatch -->

Start a lane’s child as a detached process that outlives this session.

```bash
pnpm josh lane:dispatch 1749   # prints the child's pid; a refusal is an empty capture and exit 1
```

**Options:**

- `JOSH_{SCHEDULER,WORKER,REVIEWER}_MODEL` — Claude Code role overrides; Anthropic defaults are respectively `claude-opus-5-5`, `claude-opus-5-5`, and `claude-opus-5-5`. Codex keeps its provider-specific model.
- `JOSH_{SCHEDULER,WORKER,REVIEWER}_EFFORT` — role effort overrides for either provider; defaults are `medium`, `medium`, and `medium`.
- `JOSH_REVIEWER_VERIFICATION_{MODEL,EFFORT}` — review round 2 and later (the verification pass); defaults are `claude-sonnet-5-5` / `high` on Anthropic and `high` on OpenAI, falling back to `JOSH_REVIEWER_*`.

<!-- /usage -->

Codex sessions use a detached non-AI supervisor for Codex generations; Claude Code sessions run unchanged `claude -p`.
Worker rollout files persist for active-usage cuts. The printed PID is the supervisor's.

**Before it launches, it applies `in-progress` to `#<N>`**, so the lane counts as busy from the dispatch (`docs/maintainers/josh-commands-run-rationale.md` → "`josh lane:dispatch` applies `in-progress` before it launches"); a label it cannot apply stops the launch.

Blank means unset. The inherited agent session identifier selects the provider, then
`JOSH_AGENT_PROVIDER`; with neither (a plain terminal) it defaults to Anthropic and the launch says so — on the dispatch line, and on stderr for `run:wake --start`,
`review:brief` and `ship --detach`. Conflicting identifiers and a `JOSH_AGENT_PROVIDER` naming no allowed provider refuse launch, as does an invalid model/effort
or an unavailable selected CLI/auth; there is no provider swap, promotion or worker retry. The worker
drops to `low` only in the pre-gate phase, on either provider.

The defaults are pinned model ids rather than an alias such as `opus`, so a run log names the exact
model and a migration can be measured at unchanged effort. Before launch the selected CLI's
version is checked against the model it will run: `claude-opus-5-5` needs Claude Code 2.1.280 or later
(`claude update`), `gpt-6.1-sol` needs Codex CLI 0.159.1 or later, and a lane recorded with
`gpt-6-sol` still needs Codex CLI 0.155.0 or later
(`npm install -g @openai/codex@latest`). A CLI below the floor, or one whose version cannot be read,
refuses launch with that update named — never a quiet switch to an older model. A lane keeps the
profile it recorded at dispatch: a cut, resume or wake of a lane created before a migration stays on
its recorded model (a model the floor table does not name is not version-checked), and only a newly
dispatched lane takes the new default. The one exception is a pre-gate cut of a Claude lane: it moves
to the ship phase's default, `claude-sonnet-5-5`, or to `JOSH_WORKER_SHIP_MODEL` when that is set, lowered to the Issue's
`josh.worker` profile when that is weaker.
`JOSH_{ROLE}_MODEL` overrides reach new Claude Code launches
only; they never rewrite a recorded lane. Legacy
`JOSH_LANE_MODEL/EFFORT` is worker-only; migrate to `JOSH_WORKER_MODEL/EFFORT`.

**Output / exit codes:** prints the child's pid on stdout. Every refusal exits non-zero and sends a `warning` — including one because the `in-progress` label could not be applied (no log path, since nothing started). A child that started but whose log could not be opened warns and exits zero (`dispatched`).

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh lane:dispatch` in detail".

#### `josh lane:await`

<!-- usage: lane:await -->

Block until any of the named in-flight lane children completes; prints which one finished.

```bash
pnpm josh lane:await 1749 1750   # reclaim a resumed conversation’s carry record, then block until either lane completes
```

<!-- /usage -->

Omitted, `--owner` is the `CLAUDE_PID` of the calling Claude session (none elsewhere, e.g. Codex).

`--owner <pid>` names the waiting session's process. When the carry record belongs to the same conversation under an earlier process — a restart resumed it in a new one — the record is moved to this pid before the wait, so a wait longer than the conversation's quiet window cannot read as a crash to `run:wake`. Any other record is left alone.

Polls each child's process every 5 s with a 15 s re-confirm window, so a process that briefly disappears (the pre-gate cut handoff) is not declared done. Exits 0 only once a child confirms completion.

#### `josh lane:launch`

<!-- usage: lane:launch -->

Collapse a backlogrun lane-start event into one call: open the lane, pop and re-install on the first, dispatch the child.

```bash
pnpm josh lane:launch 1749                                                  # every lane after the first
pnpm josh lane:launch 1749 --stash "backlogrun: josh latest before lanes"   # the first lane only
```

<!-- /usage -->

Dependencies are re-installed against the lock the popped stash brought in. A thin layer over `lane:open`, `stash:pop` and `lane:dispatch`, reusing their guards and messages.

Launches reserve 470 MB, one lane's share of the measured claude RSS peak (its subagents run inside it), waiting for free memory without a timeout bypass. The child retains the claim. `run:board` shows the wait; `lane:stats` lists it as `lane:launch` under held-by.

The child's pid is the one thing on stdout; a refusal is an empty capture beside a non-zero exit, as `lane:dispatch`'s is. A lane a park kept (dispatched before) is dispatched into, not reopened; a refused `lane:open`, pop or re-install stops it before dispatch.

#### `josh lane:sample` / `josh lane:stats`

<!-- usage: lane:sample -->

Record the machine load (load average, swap, free memory, working lanes) to the lane ledger — a backlogrun samples itself, this is for a reading outside one.

```bash
pnpm josh lane:sample   # one machine-load reading
```

<!-- /usage -->

<!-- usage: lane:stats -->

Print period lane throughput, stage, stop (by failed CI check, longest first), check and machine-load statistics; --sinks shows stage totals, --over lane chains, --why cause groups above a net-minute threshold, and --pairs scoped pair runs.

```bash
pnpm josh lane:stats --period 7                           # a 7-day period's stage medians and maxima
pnpm josh lane:stats --period 1 --sinks                   # stage totals of the lanes over 30 net min
pnpm josh lane:stats --period 1 --over 40                 # ledger chains of lanes over 40 net min
pnpm josh lane:stats --period 1 --why 40                  # cause groups of lanes over 40 net min
pnpm josh lane:stats --period 7 --pairs                   # a 7-day period's scoped pair runs
pnpm josh lane:stats --since 2026-11-10T01:00Z --why 40   # cause groups since an instant
```

<!-- /usage -->

The followup row is `followup (driver, outside lane net)`; `--why` groups a followup over budget as `driver followup over budget (outside lane net)`, apart from the lane's own causes (`lane-why-period.ts`). Its `open issues` matches each lane's ledger cause key (the last CI check) as well as the stage names, through `lane:why`'s matcher (`lane-why-causes.ts`).

`--sinks [<minutes>]` (default 30) prints one table instead: per `lane:breakdown` stage and lap of the period's merged
lanes over that many net minutes, the total, the lane count and the median per lane, the longest total first
(`lane-sinks.ts`).

The `open issues` column lists each open Issue whose title contains the stage name (case-insensitive): `none` when
none does, `unread` when the listing failed (`lane-sinks-issues.ts`). The `scoped pair` row also matches the file
name of each `over_cap_hub` those lanes' `test-related` runs recorded.

`--over <minutes>`: per merged lane over that many net min, longest first, net/wait minutes, ledger chain,
stages past budget (`implement 58.8/9`), top stage, its `--sinks` open Issues (`lane-over.ts`). A cause table follows
(`lane-over-causes.ts`): per over-cap `hub` and `ci job`, lanes, minutes over, open Issues; `filing candidates:`
lists unnamed.

Groups overlap; each sums net lane time. Implement attribution is unverified; Issues match names.

The chain names `split-notice ×N`, `split-filed <child>`, `round 1 blocking`, `unplanned-notice ×N`, each yield's
holder and redispatch gap (`dispatched before holder end` when the lane came back first, `gap open` while either is
pending) and each `hub over cap <file>` of
`test:related`.

`--pairs` prints one table instead: the period's scoped pair runs by named-file count (`<50`, `50-1000`, `>1000`), by
the reason the import-graph split failed (its detail after `: ` dropped) and by the over-cap hub `test:related` logged,
each with its runs and total minutes (`lane-pairs.ts`), from the `named` and `unsplit` fields of the ship lap and the
hub of the `test:related` record.

A lap overlaps its stage, so those rows do not add up to the lanes' time. The time between ship stages is split by park
only, not by Bash kind, since a transcript call names no lane.

Under the stage table, the implement stage is broken down from the lane transcripts up to each lane's first `josh ship`
(`lane-implement-stats.ts`): `plan` before the first edit, then `read`, `edit`, `check` (a scoped check or gate) and
`review-fix` from `run:review` on, each call's span counted from the previous call's end, less its `lane:pause` time.

The `implement read` table under it splits `read` by lane medians (`lane-implement-read.ts`): the calls' own run time
(`tool`), the turns before them (`thinking`), the distinct files `Read` opened (`files read`), and how many of those an
investigator's report cited by `path:line` (`investigator-cited`).

The `stage turns` table (`lane-turn-stats.ts`) groups period-dispatched lanes' calls by ledger interval:
`implement` until the first ship stage (open until then), the shortest stage holding a call, or `between stages`.
Rows show median calls and measured lanes; lanes without calls appear under `no transcript`, outside the calls median.
`stops per lane (median)` counts in-period stops by `reason` (`conflict` as `sync`) over all dispatched lanes,
including zero-stop and transcript-missing lanes; no dispatched lanes means `not measured`.

Between them, the followup critical path table (`lane-ci-path-stats.ts`) counts, per check that settled last in `followup`'s CI wait,
its runs and the median and maximum seconds into the wait it settled at. A check is timed only once seen pending, and CodeRabbit is
left to the `coderabbit-wait` row (`followup-ci-path.ts`).

Under the stop table, the failed-check table (`lane-stop-check-stats.ts`) counts followup `check` stops per failed CI check
(stops, wait total and maximum, not resumed), and the longest-stop table lists the ten longest stops with issue, `stopped at` and causes.

Under the gate check table, the claim-versus-measured table (`lane-claim-stats.ts`) prints, per check, the median cores it
claimed, the cores it used (`cpu_ms ÷ elapsed_ms`: median, p90, maximum) and the seconds its claims waited — reused runs and
runs with no `cpu_ms` left out. It only reports: a core weight is changed in its own Issue, from this table.

Under the size table, the implement-rate table (`lane-implement-rate.ts`) prints the median `implement` minutes per 100
actual non-test lines over the period's merged lanes, and how many lanes it reads: the `implement` interval joined by
issue to the last `size` measured before the merge, lanes with no size, no interval or zero lines left out.

Procedure and columns for measuring a lane limit: [lane-limit-measurement.md](./maintainers/lane-limit-measurement.md).

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh lane:sample` / `josh lane:stats` in detail".

#### `josh lane:value`

<!-- usage: lane:value -->

Print one lane measurement since an instant as a single number: cell (a lane:stats table cell, --table --row --where --column --item --zero), lint-unmoved (median s of a lint:related that found nothing moved), metrics-stops (pre-detach metrics stops per lane), lint-core-wait (lint:related core-budget wait, min per lane), edit (median s of one Edit).

```bash
pnpm josh lane:value edit --since 2026-10-23T03:29Z                                                                    # the median Edit time since an instant
pnpm josh lane:value cell --table "test:related scope" --row related --column "median (s)" --since 2026-10-23T03:29Z   # one lane:stats table cell since an instant
```

<!-- /usage -->

The value is the output's last line, two decimals, so a measurement Issue declares it (`- 計測宣言:`); a period with no sample prints nothing there and exits non-zero. Per lane divides by the lanes that made a tool call in the period, not their sessions — a lane runs at least a child and a ship-reviewer session.

Two figures outside `lane:value` print the number alone as the last line; `--density` with no lane-child request prints nothing and exits non-zero too:

```bash
pnpm josh cost:audit --density --period 7   # lane-child calls per request over the period
pnpm josh read:set fullrun --bytes          # total bytes the fullrun entry reads
```

`cell` reads the tables `lane:stats` prints over the same window: `--table` is a table's first header cell, `--row` a row's first cell. An address matching no numeric cell, or more than one (the check and claim tables share `check`), exits non-zero.

`--where <header>=<text>` keeps the rows whose `<header>` cell is `<text>`; `--row` may be left out, and `--column` may name the first column.

`--item <label>` reads `<label>`'s exact count from a `label N, label N` list cell (`unpinned (noticed)` is its own label), `0` when the list omits it. `--zero` reads a named table with no matching row as `0`:

```bash
pnpm josh lane:value cell --table "round 2" --row required --where code=live --column decisions --zero --since 2026-11-02T00:00Z   # round 2 required for live
pnpm josh lane:value cell --table stop --row preflight --column causes --item unpinned --since 2026-11-02T00:00Z                   # preflight stops caused by unpinned, not noticed
pnpm josh lane:value cell --table "measured lanes" --column "measured lanes" --since 2026-11-02T00:00Z                            # merged lanes measured
```

#### `josh lane:net`

<!-- usage: lane:net -->

Print a lane's net minutes: its issue's first dispatch to its merge, less the waits its parks, outages, usage-limit stops and yields stood, the host's sleeps and the ship's followup.

```bash
pnpm josh lane:net 4695   # the net minutes a causing-lane line declares
```

<!-- /usage -->

The whole minutes are what an Issue's `- 原因のレーン:` line declares; a lane the ledger holds no dispatch and merge of exits non-zero.

The followup — each `followup start` ship stage to the lane's next ship stage or its merge — is the driver's CI, CodeRabbit and merge wait with no lane seat held, so it is outside the net time (`lane-net-time.ts`).

Detail: `docs/maintainers/josh-commands-run-rationale.md` → "`josh lane:net` in detail".

#### `josh lane:breakdown`

<!-- usage: lane:breakdown -->

Print a merged lane's net time by stage, longest first, the implementation split by its tool calls.

```bash
pnpm josh lane:breakdown 4970              # the breakdown the overrun investigation comments on the lane
pnpm josh lane:breakdown 4970 --timeline   # when each stage ran and where the lane waited
```

**Options:**

- `--timeline` — prints the lane in time order instead, one line a stage, wait or event, the stage lines adding up to the net time.

<!-- /usage -->

The stages — start to plan, implement, each ship stage, between ship stages — add up to `lane:net`'s minutes; the waits it takes out are one line apart. The implementation splits by its tool calls' kind, what no call spent being editing & thinking. A lane the ledger holds no dispatch and merge of exits non-zero (`lane-breakdown.ts`).

`--timeline` prints the lane one line an event, oldest first: start (UTC), minutes since the dispatch, duration, name (`lane-timeline.ts`). Its stage lines are the same spans at their net minutes and add up to the net time.

- `[excluded]` — a wait taken out, named by what opened it (park, outage, usage limit, split, yield, sleep).
- `[driver]` — the followup's CI wait.
- `[event]` — a main merge-in (the ship's `merge` lap), a split or `unplanned` notice, a split, a ship launch, a review round.

A ship stop closes the ship stage open at it. A blocking `lane:plan` wait on a holder is its own `lane:plan wait (#<M>)` row, cut out of the stage it fell in (`lane-plan-wait-event.ts`).

Under the waits taken out, the yield wait splits into `yield wait: holder remaining` and `yield wait: redispatch gap (offer + launch)`; a wait whose note names no holder gets a `no holder named, unsplit` line (`lane-yield-split.ts`).

A subagent call counts under the agent it dispatched (`subagent: reviewer`), a backgrounded one at no time with its count beside it; `lane:stats` adds one such row per type under its implement sub-stages, its untimed calls in the `backgrounded` column. Between the two, its `lane first lint:related` row takes each lane's first timed `lint:related`, over the lanes that ran one.

Under `implement` and `start to plan`, each line is one call group, at most three per row, longest first: `<row> › <label> ×<count> <minutes>` (`test › test:related ×3 8.7 min`), the row left out under `start to plan`.

The `start to plan` line ends with `(outside calls <minutes>)`: the time no timed call or wait covered, a backgrounded call's wait among it and counted beside it; left out when no calls were read.

The label is the josh commands a Bash call chains, a `reserved-run` as what it wrapped (`reserved-run (eslint)`, `reserved-run (test:related)`), else its first 60 characters past a leading `cd`; a reviewer's pass (`round 1`, `interaction`, `round 2`), and its level when the prompt opens with one; any other subagent's type; any other tool's name.

`editing & thinking` has no calls, so no lines; the overrun prompt's one-line form leaves them out (`lane-breakdown-calls.ts`).

The changed files the lane's `josh test:related` runs narrowed past the reach cap get a line before the waits taken out, `test:related <N> over cap, in <capped> of <runs> runs, hub <file>` — `<N>` the widest run's count, the hub the most capped runs recorded, left off where none did — and none when no run capped a file (`lane-breakdown-related.ts`).

The followup is no stage: a `driver followup <minutes> (outside lane net)` line after the waits taken out holds it, with its laps and its own budget. It names the check its CI wait waited on last, and when it settled (`(last check: e2e 150.0s)`), read off the lane's latest `ci-wait` row; a row that names none adds nothing (`lane-ci-path-stats.ts`).

Each ship stage lists its inner steps under it, longest first: the `ship-lap` rows `josh ship` writes and the lane's core-budget waits (`lane-breakdown-laps.ts`).
`lane:stats` prints each step's median and maximum under the stage table (`lane-ship-lap-stats.ts`).

`between ship stages` lists the child's calls there by kind — Bash, `read`, `edit`, `subagent: <type>`, a `ship:wait` begun before — and what no call covered as editing & thinking.

A stretch between ship stages that a park fell in is named after the park instead: `pause for #<M>` or `park (<reason>)`, net of its wait, and what the lane redid up to its next park — `(re-plan, ship ×2 re-run)`, a ship counted again where a stage starts twice (`lane-breakdown-pause.ts`).

#### `josh lane:why`

<!-- usage: lane:why -->

Print a merged lane's stages over budget, one row each, beside the records that say why.

```bash
pnpm josh lane:why 6050   # the cause table an overrun investigation joins by hand
```

<!-- /usage -->

One table row per `lane:breakdown` stage over its budget (`lane-stage-budget.ts`: a lane's 25 minutes as plan 3, implement 9, ship 8 and followup 5, the followup outside the net time), longest first, no model run.

The implement row carries the filing's projected implement minutes (`size-estimate.ts`), the followup row the check its CI wait waited on last and the lane branch's longest CI job and that job's longest step (`ci:timing`, the branch's latest commit), a ship row the lane's stop reasons and its `test:related` cap overrun.

A ship or followup row's `causes` lists its cause keys (`lane-why-causes.ts`): the failed checks, `main changed` verdict and byte budget the last ship log names, and the ledger's last CI check.

There `open issues` lists the open Issues whose title names a key, `unfiled` the keys none names; on any other row, the open Issues naming the stage (`lane:stats --sinks`).

A ship total table follows, printed even when no stage ran over: the ship stages and the time between them, the scoped pair's runs and minutes, the core-budget waits and the `test:related` cap overrun with its hub, all summed over the whole ship (`lane-why-ship.ts`). Stages each within their budget that add up past the lane's target show there.

A missing record leaves its cell blank; an Issue listing that cannot be read prints `unread` in `open issues` and `unfiled`, no open Issue naming the row `none`. A lane with no stage over budget prints one line before the ship total; one the ledger holds no dispatch and merge of exits non-zero (`lane-why.ts`).

### `josh lane:plan`

<!-- usage: lane:plan -->

Record a lane child's planned files; yield its lane, naming file and holder, when an earlier-planned running lane declares or plans one; `--size-approval` bounds lines/files.

```bash
pnpm josh lane:plan 4864 scripts/lane/lane-plan.ts scripts/backlog/backlog-next.ts
```

<!-- /usage -->

A lane child runs it once its work summary settles, before the first edit, naming every file the summary changes. It checks once; until it prints `clear`, `scripts/hooks/lane-plan-guard.ts` refuses its runtime-file edits.

A lane whose plan was cleared, or else recorded first, holds the files, so two lanes never yield to each other; `backlog:next` reads the same record, so a candidate waits on a running lane's plan, read in place of its body. A file under `docs/` never clashes: the lane's sync with main resolves a shared document.

A lane child's `issue:plan` runs it on the recorded plan's backticked paths (`docs/josh-commands-backlog.md` → "`josh issue:plan`").

On a clash the child gives its lane back instead of polling with its seat taken:

- It notes its yield on the event stream, releases its `run:hold`, and the session ends with no edit.
- `run:merge` books it `yielded` — not a merge, a failure or an outage — and closes the lane with a withdrawal naming `its own lane:plan`.
- Its plan stays recorded, uncleared and marked yielded: `backlog:next` holds the issue back on it and offers it again once the holder's lane ends. Unlike `lane:withdraw`, a yield keeps the issue in the run.
- The note ends `· at: summary`, or `· at: entry` for the entry probe below.

A lane dispatched before its holder, with commits, waits instead, keeping its seat (`scripts/lane/lane-plan-wait.ts`):

- It waits when the holder's estimated time left (3-day median lane less its elapsed time) is at most its own worked time, capped at 30 minutes.
- The first such ask records that deadline on the plan; `lane:plan` then blocks, re-reading holders each minute, up to 9 minutes per ask.
- It answers `clear` once the holder's lane ends, `yield` past the deadline, or `wait` when the 9 minutes run out first: ask again.

`--probe` answers the same check and writes nothing. A lane child's `run:entry` runs it once, before the issue report, on the paths dispatch gated on; on a clash it gives the lane back as above and exits 2.

A `run:planned` candidate's plan comment (the latest trusted one carrying `### 影響を受ける既存の利用者`) declares its paths in place of its body: one naming a running lane's file is held back before dispatch; a path its body only cites holds nothing.

A first plan over twice the files its `- 規模見積もり:` declares (tests excluded) answers `split`, exit 3, unrecorded, naming the files to file with `--route split`; an undeclared issue never does. A generated artifact planned beside its source (`.codex/hooks.json` beside `.claude/settings.json`, from `codex_hooks.GENERATED_SOURCES`) is not counted; planned without its source, it counts.

Hunks over twice declared files or declared lines × recent ratio over 200 also split. Splits log their reason; hunks exclude planned files.

A planned `test:related` hub (reach over the test-file cap, `scripts/test/test-related-cap.ts`) also splits, as `split (hub)` naming it; with no dependency graph none reads as a hub. Related: [#6180](https://github.com/joshuafolkken/kit/issues/6180) splits the hubs themselves.

A `--single` plan, or a re-plan after the lane started (`sized`), past any axis is recorded with a `size warning` and logged, never refused; the clash and unread checks still apply.

A dispatched lane's plan (its child mark names the issue) never answers `split`: its first plan past any axis prints one `size warning`, notes nothing on the ledger, and its re-plans print none.

A first plan re-runs each `- 前提:` line of its issue's trusted body (`scripts/lane/lane-plan-premise.ts`), printing `premise: <declaration> measured <value>` on stderr. One that does not hold, or an untrusted body, answers `premise`, exit 4, unrecorded: park the lane. No premise line runs nothing; a re-plan never re-runs them.

`--size-approval <json-file>` (optional; a re-plan never needs one): `issue`, `paths`, `source` (trusted same-issue comment), `rationale`; `declared_lines`/`max_lines` and/or `declared_files`/`max_files`. Records author/body, checks scope; other gates remain. Steps: [Approve a lane plan past its size guide](./how-to/lane-size-approval.md).

`--imports <path>...`, last, probes imported modules: a main guard or top-level `main()` prints `import blocked: <path> — <reason>` and a `run:split <N> --prerequisite <P>` hint.

**Output / exit codes:** `clear` on stdout, exit 0, once nothing holds the planned files. `yield`, exit 2, with the clash (issue, planned file, overlapped path, holder) on stderr: end the session. `wait`, exit 1, on an unreadable listing or a bounded wait on a holder — run it again. No path: the usage, exit 1.
