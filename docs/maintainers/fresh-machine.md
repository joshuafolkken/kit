# Running an install on a fresh machine

`pnpm josh fresh:run` runs one install scenario from start to finish on a machine that has nothing
installed, and keeps what happened as a log. The dogfood runs before it were made on a development
machine that already had pnpm, Node.js and gh, so only the state of the project varied; a `pnpm` that
is missing from `PATH` was a state none of them could reach. The command reference is
[josh-commands-automation.md](../josh-commands-automation.md#josh-freshrun); this page is how to use
it and what it does.

```bash
pnpm josh fresh:run --list                # the patterns
pnpm josh fresh:run kit-test-html-init    # one pattern, start to finish
pnpm josh fr kit-test-html-init           # the same, by its alias
```

## The machine

A Debian image with curl and without Node.js, pnpm, git or gh (`buildpack-deps:bookworm-curl`), on
which a normal user (`dev`) runs the Linux route of
[setup/prerequisites.md](../setup/prerequisites.md) and nothing else:

```bash
curl -fsSL https://get.pnpm.io/install.sh | sh -
# a new terminal
pnpm runtime set node 22 -g
node --version
```

- **One line is not in the guide**: `ENV SHELL=/bin/bash`. The pnpm installer reads `SHELL` to pick
  the profile it edits, and a container build does not set it.
- **"A new terminal" is `bash -i`**. Debian's `.bashrc` returns at its first lines in a
  non-interactive shell, before the lines the installer appended, so every command of a scenario runs
  in an interactive shell — the one a person has after opening a terminal.
- **git and gh are on a second image**, `josh-fresh-machine:github`, built only for a scenario with
  `requires_github: true`. git comes from `apt-get`, gh from the Debian steps of the installation page
  the guide links to, run as root in place of `sudo`. `josh-fresh-machine:base` has neither, so an
  `init` scenario proves the install needs no Git.
- The Dockerfile is generated by `scripts/fresh-machine/fresh-machine-image.ts` and sent to
  `docker build` on stdin, so the build has no context and copies no host file.
  `fresh-machine-image.test.ts` holds its commands to the lines of the guide. `--rebuild` drops the
  layer cache — use it after pnpm or the guide changed.

## kit's six patterns

Three projects by two commands, each from the state its row names:

| Pattern                 | Project before the install                | Git and GitHub before the install      | kit installed from    |
| ----------------------- | ----------------------------------------- | -------------------------------------- | --------------------- |
| `kit-test-lua-init`     | `main.lua`                                | no Git on the machine                  | the packed checkout   |
| `kit-test-html-init`    | `index.html`                              | no Git on the machine                  | the packed checkout   |
| `kit-test-svelte-init`  | `sv create --template minimal --types ts` | no Git on the machine                  | the packed checkout   |
| `kit-test-lua-start`    | `main.lua`                                | no repository                          | the published version |
| `kit-test-html-start`   | `index.html`                              | a first commit on `main`, no GitHub    | the published version |
| `kit-test-svelte-start` | `sv create --template minimal --types ts` | a GitHub repository with `main` pushed | the published version |

- **The patterns run from a kit checkout only.** They install `@joshuafolkken/kit` by name, while the
  tarball and the published version are those of the checkout the command is run from; anywhere else
  a named pattern is refused and points at `--spec`.
- **`init` installs the packed checkout.** The command runs `pnpm pack` — and so the checkout's own
  `prepack` — into a temporary directory mounted read-only at `/pack`, so a fix is retested without a
  release.
- **`start` installs a published version.** Its setup pull request carries `package.json`, and CI
  cannot resolve a tarball path that exists only in the container. The version is always written out
  (`--package-version`, or the registry's latest), and kit alone is excluded from pnpm's release-age
  wait through `minimumReleaseAgeExclude`, so a version published minutes ago installs while every
  other dependency keeps the wait.
- **`start` runs the scoped checks before the gate.** `josh start` leaves the project on its setup
  branch, where `pnpm josh gate` refuses until `pnpm josh lint:related && pnpm josh test:related` has
  passed; the pattern runs the line that refusal hands back.
- **Every pattern ends with two probes**, recorded whatever they exit with: `pnpm josh gate` from
  `bash --noprofile --norc` with an environment of `HOME` and the system `PATH` only, and `josh gate`
  from a `PATH` that has `node` on it and no `pnpm`.

## What the first runs found

Run on 2026-10-13 against kit 1.1387.0 — the packed checkout for `init`, the published version for
`start` — on Debian bookworm:

| Pattern                 | Commands                                             | Bare-shell probe | Node-only probe |
| ----------------------- | ---------------------------------------------------- | ---------------- | --------------- |
| `kit-test-lua-init`     | passed                                               | exit 127         | exit 1          |
| `kit-test-html-init`    | passed                                               | exit 127         | exit 1          |
| `kit-test-svelte-init`  | passed                                               | exit 127         | exit 1          |
| `kit-test-lua-start`    | stopped in `josh start`, step 3 (the initial commit) | not reached      | not reached     |
| `kit-test-html-start`   | passed                                               | exit 127         | exit 1          |
| `kit-test-svelte-start` | stopped in `josh start`, at the push of its branch   | not reached      | not reached     |

- **`kit-test-lua-start` stops until
  [joshuafolkken/kit#3754](https://github.com/joshuafolkken/kit/issues/3754) is fixed.** A machine
  that has never committed has no Git author identity, and `josh start` creates the repository and
  then fails its own first commit. The other two `start` patterns make a first commit before the
  install, as their starting state asks, and set an identity for it; the Lua pattern starts without
  Git and is left to fail, because setting an identity there would hide what a person meets.
- **`kit-test-svelte-start` stops until
  [joshuafolkken/kit#3755](https://github.com/joshuafolkken/kit/issues/3755) is fixed.** A web
  project's pre-push hook runs `pnpm josh audit`, which needs `osv-scanner`; nothing in the guide
  installs it and `josh start` does not provision it, so the hook refuses the push of the setup
  branch. The pattern does not run `pnpm josh audit:provision` first, for the same reason.
- **The bare-shell probe exits 127**: `pnpm: command not found`. The installer puts pnpm on `PATH`
  through `.bashrc` alone, so a shell that reads no profile does not have it.
- **The node-only probe exits 1**, every check failing at once. From the packed checkout each failed
  check prints why — pnpm was not found on the `PATH` this process sees
  ([joshuafolkken/kit#3712](https://github.com/joshuafolkken/kit/issues/3712)); the published
  1.1387.0 predates that fix and prints `✗` with no reason, which is the report #3712 was filed from.
- **Repositories these runs left**, each private: `kit-test-html-start-1` and
  `kit-test-html-start-2` with the setup Issue and pull request `josh start` opened, and
  `kit-test-svelte-start-1` with the setup Issue alone. `kit-test-lua-start-1` stopped before a
  repository was created.

## A scenario from another toolkit

A toolkit that wraps kit runs its own entry point on the same machine with `--spec`. The command, the
image and the log are kit's; the toolkit keeps only the JSON file. Run from the toolkit's checkout,
`package_source: tarball` packs that toolkit and `published` asks the registry for that toolkit's
version — nothing is read from a kit checkout.

```json
{
	"name": "app-kit-test-html-init",
	"files": {
		"index.html": "<!doctype html><html><body><h1>Hello</h1></body></html>\n",
		"josh-app.config.json": "{ \"verify\": { \"dast\": false } }\n"
	},
	"commands": [
		"printf '{ \"private\": true }\\n' > package.json",
		"pnpm add -D --allow-build=esbuild --allow-build=unrs-resolver \"$PACKAGE_TARBALL\"",
		"pnpm exec josh-app init"
	],
	"probes": ["pnpm josh gate"]
}
```

```bash
pnpm josh fresh:run --spec fresh/html-init.json
```

| Field             | Default   | Meaning                                                                                                             |
| ----------------- | --------- | ------------------------------------------------------------------------------------------------------------------- |
| `name`            | required  | Lowercase letters, digits and hyphens. The log, the project directory and the repository are named after it         |
| `commands`        | required  | What a person would type, in order, in the project directory. The first one that fails ends the run with its status |
| `probes`          | `[]`      | Run after the commands passed. Each exit status is recorded and none fails the run                                  |
| `files`           | `{}`      | Path → content, relative to the project directory, written before the first command                                 |
| `package_source`  | `tarball` | `tarball` packs the checkout the command is run from; `published` resolves a version from the registry              |
| `requires_github` | `false`   | Use the image with git and gh, and pass the host's GitHub token                                                     |

An unknown field, an absolute path or one that leaves the project directory is refused with the field
named, before Docker is started.

A command reads three variables inside the container:

| Variable          | Value                                                                           |
| ----------------- | ------------------------------------------------------------------------------- |
| `RUN_NAME`        | The numbered name of this run, also the name of the project directory           |
| `PACKAGE_TARBALL` | The packed checkout's path under `/pack`; empty for `package_source: published` |
| `PACKAGE_VERSION` | The published version; empty for `package_source: tarball`                      |

## The log

`<log-dir>/<scenario>-<n>.log`, by default under `.claude/tmp/fresh-machine`, which kit's distributed
`.gitignore` already ignores. One file holds the image build, the pack and the container's session.
Every command is printed as `$ <command>` before it runs and `[exit <status>]` after, and the probes
follow the line `# probes — recorded, never failing the run`.

`<n>` is one more than the highest number among the logs of the same scenario in that directory, and
`<scenario>-<n>` is also the project directory and, for a GitHub scenario, the repository. A GitHub
scenario therefore also counts the repositories the token's account already owns — another checkout,
or a lane worktree since removed, has logs this directory does not — so a rerun never meets the
repository of an earlier run, wherever that run was started.

## GitHub

- **The token** is what `gh auth token` prints on the host. It is put in the environment of the
  `docker run` client and named — not valued — in its arguments (`--env GH_TOKEN`), so it is in no
  argument list, no image layer and no printed command. Every line is passed through a replacement of
  the token's value before it reaches the console or the log.
- **Signing in** is `gh auth setup-git`: `gh auth login` cannot run without a person, and pointing git
  at gh for credentials is the part of it a run needs.
- **A GitHub scenario creates a real private repository** under the account the token belongs to, and
  no run deletes one. Remove the repositories of finished runs by hand:

  ```bash
  gh repo list --json name --jq '.[].name | select(startswith("kit-test-"))'
  gh repo delete <owner>/<name>
  ```

- **Deleting the logs restarts the numbering**, and the next run of a GitHub scenario then asks for a
  repository name that is already taken. Delete the repositories together with the logs.
