# josh command reference — rationale and history

How the dispatcher behind [josh-commands.md](../josh-commands.md) runs a command — kit's own
checkout and writing a new script — kept here so the reference states only each command's contract.

## How a command runs

Most commands are a TypeScript file under `scripts/`; the rest are a shell line the dispatcher spawns. In kit's own checkout the dispatcher evaluates a script command in its own process rather than starting a second TypeScript runtime for it. Three conditions decide whether a command takes that route:

- **The dispatcher must run from TypeScript source** — kit's own `pnpm josh`. A consumer's `josh` bin is the bundled `dist/josh.js` under plain node, so a consumer keeps the spawning path for every command except one marked `is_bundled`, which it imports pre-built from `dist/commands/` ([runtime-bundling.md](./runtime-bundling.md)).
- **The command must not need node flags of its own.** `doctor`, `latest:scope`, `followup` and `notify` pass `--env-file`, so they keep a process of their own.
- **A shell command has no script to import** and is spawned as before.

A new josh script keeps the canonical main guard `process.argv[1] === fileURLToPath(import.meta.url)`, or none at all. `scripts/josh/josh-in-process.test.ts` asserts the shape for every command that takes this route.

## `josh gate`'s core budget

Each check claims a place in a machine-wide weighted core budget before it starts (joshuafolkken/kit#2351). The weights are the same measured table the plan already uses — the static checks' reserved cores and the unit suite's worker cap — so a lone gate's four claims sum to exactly the core count and, on a machine with room, every one is admitted at once: a solo run's concurrency and worker count are unchanged. Under concurrency the machine-wide sum is what bounds admission, so overlapping gates can no longer each reserve the whole machine, and the "whoever started first took everything" asymmetry is gone — a later gate waits rather than shrinking everyone.

**The budget is what the machine has free, in cores and in memory** (joshuafolkken/kit#3371). The core count is the ceiling, and every claim — a solo one included ([#4238](https://github.com/joshuafolkken/kit/issues/4238)) — reads the machine (`scripts/gate/machine-capacity.ts`): busy cores from the CPU-time difference over a 250 ms window, and available memory from `kern.memorystatus_level` on macOS or `MemAvailable` on Linux — read as none only while the kernel reports critical memory pressure (its warning lingers on macOS long after the pressure passed, joshuafolkken/kit#4199). Swap traffic across the window (more than 16 MB) or compressor traffic (more than 64 MB, `vm.compressor_input_bytes`) names a memory wait as pressure but no longer zeroes the free figure ([#4313](https://github.com/joshuafolkken/kit/issues/4313)): a machine that swaps all day held a third of every wait with memory to spare (joshuafolkken/kit#3943 introduced the zeroing). Only load from outside the ledger shrinks the core budget — every busy core counts, with no baseline exempt, and a waiting claim judges on the mean of that outside load over its last 3 s of readings, each taken against the ledger of its moment, so a momentary dip does not admit it onto a saturated CPU and a claim released inside the window is not counted as outside load — and each heavy tool declares its measured peak memory (`core_budget.MEMORY_MB`) so a claim also waits while that memory is not free. A marker is rewritten with its admission time once it runs; after a 30 s ramp-up window its declared load counts as the ledger's, which is how the reading's load is split into the ledger's and the rest — a tool admitted moments ago has not allocated yet, so its memory is not added back onto what is free. A claim the wait cap admits names both its cores and its memory against the budget. Outside load holds every claim but the first waiter ([#4313](https://github.com/joshuafolkken/kit/issues/4313), reversing [#4238](https://github.com/joshuafolkken/kit/issues/4238)'s hold on the head): that one is admitted against the cores the ledger holds, and a unit claim among them narrows its workers to the room the outside load leaves, so the load bounds its width rather than its start — until the one-minute load average beyond the ledger passes twice the core count, where the first waiter waits like any claim, re-read on every poll ([#4361](https://github.com/joshuafolkken/kit/issues/4361); the busy cores stop at the core count, so only the run queue sees that far past it). A claim that fits beside the running claims passes a waiter claimed less than 30 s before it, so a `lint:related` does not queue behind a heavy unit claim, and a claim made later queues, so the waiter is never starved. A reading that fails (CI, a CPU quota narrower than the host) falls back to the core count with no memory limit.

A leaked place is swept on read by the same pid-and-start-time liveness the unit-run marker uses, and a reservation that never fits is admitted after a wait cap — a unit suite's claim narrowed to the cores the admitted claims leave free (never below one worker), and its workers never exceed the weight it was admitted at ([#4235](https://github.com/joshuafolkken/kit/issues/4235)) — and the gate's summary then prints a `⚠ <check> — started past the core budget …` line above the verdict, so an over-subscribed run does not look like one that fitted. A gate nested inside another gate's unit suite (this repository's own gate tests) takes no place, so it never waits on cores the outer gate is holding. The pre-push `pnpm install` and `pnpm josh audit` join the same budget through [`josh reserved-run`](../josh-commands-automation.md#josh-reserved-run), and the pre-push unit suite reserves the gate's unit-suite weight and memory whenever it runs rather than reusing a passed gate's result ([#3874](https://github.com/joshuafolkken/kit/issues/3874)).

A waiting claim is visible ([#3943](https://github.com/joshuafolkken/kit/issues/3943)): its marker records the command, the checkout and the reason — cores, memory or memory pressure — the command prints one `⏳ <command> waits for the core budget — <reason>` line when its wait starts.

`josh run:board` draws a lane's waiting claim on that lane's row — `🚧` leading it, the reason's header icon, the wait and the check in place of its newest activity — and any other waiting claim as one `🚧` line right before the legend, so nothing is added under the header ([#4052](https://github.com/joshuafolkken/kit/issues/4052)).

## `josh metrics`' totals

The totals are held to the same totals measured on the merge-base, not to a recorded file (joshuafolkken/kit#3644).

- **A tracked baseline conflicted on nearly every pull request.** `.josh/metrics-baseline.json` was raised by each pull request that added code and lowered by each that removed it, so two pull requests touching unrelated sources both rewrote it. A merge driver that resolved the file and a gate exemption for the gate's own lowering write were built to live with that; measuring the merge-base removes the shared file, and both went with it.
- **The merge-base is measured by this checkout's command in a throwaway tree** (`scripts/git/base-tree.ts`, the detached worktree `josh test:red` uses). The same ruler on both trees means a change to how a total is counted moves both sides and never reads as growth. A checkout that sits on the base commit with nothing changed is its own base, so the default branch builds no second tree.
- One base under one ruler is measured once (`tools/metrics/metrics-base-cache.ts`, joshuafolkken/kit#4382). Its key is the base commit and the ruler (the sources `metrics-command.ts` loads, the eslint configuration the code lines are counted under, and the lockfile): a commit-only key would let a branch that changed the ruler pass on the old ruler's reading.
- **An approval records the growth, not the total it reached.** `--accept` writes `{ reason, date, growth }` to `.josh/metrics-accepted/<issue>.json`. Merging the default branch in moves both sides by what landed there, so a recorded delta stays this branch's own where an absolute total would be overtaken by somebody else's change.
- **Only an approval this branch wrote counts.** A file whose text the merge-base already holds approved an earlier branch's growth. The files stay on the default branch as the readable history of every accepted growth; a re-opened issue rewrites its own.
- **`JOSH_METRICS_BASE` names the commit where no merge-base can be asked for.** CI checks a pull request out as a shallow merge commit with no default-branch ref; the workflow fetches two commits and names `HEAD^1`. A name that does not resolve is an error — reading it as "nothing to compare" would turn the ratchet off where nobody watches.
- **Rejected: one writer updating the tracked file after each merge.** It needs a bot commit to the default branch and leaves a window in which the file is stale.
- Prose density is two more totals on this ratchet, not a per-document ceiling table like `document-byte-budget.ts` (joshuafolkken/kit#3866). A shortened document lowers the limit by merging, with no record to edit.
- A paragraph is measured rather than a line, so a column-wrapped document reads the same as an unwrapped one. Bold counts past one per section, so more emphasis in an already-bold section still grows the total.

## `josh metrics`' durations

Performance is a goal no change may worsen (`prompts/collaboration-workflow/principles.md` → "quality-priority"), so `josh metrics` holds four durations to a baseline and fails one that slowed past a tolerance (joshuafolkken/kit#3409).

**Only like is compared with like.** A duration taken under load measures the load: beside the whole unit suite, `josh --help` starts 40–77% slower than on a quiet machine, and its CPU time rises as much, so no tolerance both passes the gate reliably and still catches a real slowdown. The comparison is held to one condition instead of being widened.

- **`gate` and `unit` are read, not timed, and only from solo gates.** `josh gate` already appends its duration and its unit suite's to the lane ledger ([lane-limit-measurement.md](./lane-limit-measurement.md)), so `josh metrics` reads them back. A gate counts only when no other gate of the repository — passed or failed — ran at any point between its start (`at` minus `elapsed_ms`) and its end; the overlap of the gates' own spans decides, not the number of open lanes, and the ledger measured none in 17 gates while three lanes ran. **No other gate is not a quiet machine, so a solo gate must also have run beside no other work** (joshuafolkken/kit#3501): another lane's lint, related tests or `ship` doubled solo gates within minutes (62 s to 127 s on 2026-10-09), and every lane's gate failed on that noise until it was accepted into the baseline. The gate records `external_cores` — the whole cores busy beyond the baseline, by the core budget's own reading (`machine-capacity.ts`) — before its first check and after its last, and between them, every few seconds, the cores other processes' admitted claims hold in the core budget's ledger (joshuafolkken/kit#3556) — the highest of all those readings; only a gate that recorded `0` counts. The machine is read only at the ends, where none of the gate's own checks runs, because the load average cannot separate them: a gate started at a load of 4 on the 11-core machine ended at 21, its own load. Between the ends the ledger separates them instead, since two end readings missed every lane whose lint, tests or `ship` ran only while the gate did — seven lanes moved the solo median from 50.5 s to 60.9 s with no commit between. A gate whose load was never read — a line written before the field, a machine whose reading fails — is not known quiet and does not count. The value is the median of the last five solo gates that ran the unit suite, so one gate slowed by other work (a review, a related test run — 138 s against the usual 47–68 s) does not fail the next. A failed gate counts as well: every check runs to completion whether it passes, so it timed the same work, and a gate this step failed on a slowdown has to count — reading passed gates alone would hold the slow median, and every later gate red, after the slowdown was fixed. The median still trails a fix: it stays slow until the fixed gates are the majority of the five, so up to three gates after a fix still fail — the failure message says so, and a slow reading is rerun before it is accepted, since an accepted baseline never moves back down on its own. They are the _previous_ gates' — the step runs inside a gate whose own duration is not known yet — and fewer than five solo gates (a ledger cleared by a reboot, a new clone) read as not measured (`—`), so a first baseline is never the median of one quick gate.
- **`josh_startup` and `guard_startup` are timed only when `josh metrics` runs on its own** — the gate passes `--no-startup` and neither times nor prints them. Each is the fastest of five runs of `josh --help` and of the `pretool-guard` hook every tool call starts. A startup regression therefore fails a hand-run `pnpm josh metrics`, never a gate.
- **A tolerance of +10%**, where the static totals have none: a count read off a tree is the same on every run, a duration is not.
- **The baseline never moves down on its own.** One quiet run would set a bar the next ordinary run misses; a speedup is recorded with `--accept`, as a raise is.
- **The baseline is per machine and never committed.** It is `josh/metrics-durations.json` in the repository's common git directory — one file per clone, shared by every lane of it. The same durations on two machines do not compare, CI starts each job on a fresh runner, and a committed table keyed by host would publish host names and conflict on every merge. A machine's first measurement of a duration becomes its baseline; deleting the file starts that machine over.

## `josh gate` in detail

- **The last line is the verdict, and it counts what ran apart from what was skipped.** `✔ verification gate passed (6 checks) in 41.2s.` when every check ran, `✔ verification gate passed (2 ran, 4 skipped) in 3.1s.` when some printed only a skip notice, and `⚠ verification gate not verified (0 ran, 6 skipped) in 0.2s.` when none ran — a `basic` project with nothing to check. That last gate still exits `0`, but it is not a passed gate and writes no green record. A check that ran with nothing of the project's to look at — `exports` in a consumer, `behavior` with no transcript — is counted as skipped only beside a real skip, so a gate that skipped nothing keeps the first line.
- Each check claims a place in a machine-wide weighted core budget before it starts, and waits while the budget is full (`scripts/gate/core-budget.ts`). The budget is the cores and memory the machine has free, not the bare core count, and a check the wait cap admitted past it is named in the summary. A lone gate is admitted at once with its concurrency unchanged; overlapping gates share the machine instead of each reserving all of it. How the budget is weighted and swept: "`josh gate`'s core budget" above.

## `josh bytes` in detail

- The recorded ceiling is block-quantized — the next 4 KB multiple at or above the document's size (`document-byte-budget.ts`), so a document growing within its block needs no ceiling edit and parallel command-adding lanes stop conflicting on this record. An over-budget row names the value to record: the next block multiple, not the raw current size. Never fails — the ceiling is the gate's and `josh lint:related`'s to enforce; a non-zero exit means the argument list was unusable.

## `josh metrics` in detail

- **A ratchet, and a step of [`josh gate`](../josh-commands.md#josh-gate).** Exit `1` when the code lines, the comment ratio, the rule lines, the guards, either AI cost or either prose total grew past the merge-base's, naming each with both values. A total that shrank needs no record: once merged it is what the next branch is measured from. The only way up is `--accept --reason "<why>"`, which writes the growth, the reason and the date to `.josh/metrics-accepted/<issue>.json` — one file per issue, so parallel branches never conflict on it. `JOSH_METRICS_BASE=<commit>` names the commit to measure from where no merge-base can be asked for (CI) — "`josh metrics`' totals" above.

## `josh behavior` in detail

- An assertion covers a rule a guard already refuses. The gate reads the whole session, so a violation of a rule that is only measured would leave every later gate in that run red.
- The piped-verification rule is measured, not refused, for `| head`, so it is not an assertion yet. Whether a turn was a consultation, and whether the work summary was given, cannot be decided from a transcript (joshuafolkken/kit#4086).
- **The scope is the current run, not the whole corpus.** The store holds thousands of transcripts and over a gigabyte; walking all of it every gate would cost minutes. Each gate checks its own run — the newest session transcript, resolved exactly as `josh cost` resolves "the run that just finished" — so across runs the whole corpus is covered a run at a time. The engine stays general, so a broad scan of past runs (how a new assertion is verified green before it is added) is the same walk over a different set of files.

## `josh test:unit` in detail

- **The suite runs as two Vitest projects** (`vitest.config.ts`): the classifier's isolation-free files (`tools/test/pure-files.ts`) run `pure` with `isolate:false` — each shared module evaluated once per worker, not once per file, a measured 57% cut on that set — and the rest run `isolated` with the default. They partition the suite exactly, so the same files run and the green condition is unchanged; only the pure ones run faster. The state guard is scoped to `pure`.

## `josh test:declared` in detail

Report whether the working-tree change needs a test — `required`, `exempt`, or `satisfied` — from changed paths alone; the same verdict refuses `pnpm josh git -y` on `required` (`prompts/collaboration-workflow/rule-delivery.md`). On `required` the detail names each untested file's type — `E2E` under `src/routes/`, `Unit` elsewhere (`prompts/testing-guide.md` §1) — and then the one command to run next: declare a test for each and verify with `pnpm josh test:declared --match < summary.md`.

`--match` checks each `Test: <type> — <path>` declaration on stdin against the change set, printing `match` / `type-mismatch` / `path-missing` / `test-not-created` per line and exiting non-zero on any mismatch. A path wrapped in a code span, as the template writes it, is read as the path inside it. A `path-missing` line is followed by the changed paths with the same file name, when there are any, and the `report-format.md` section that defines the declaration line's shape.

## `josh test:red` in detail

Run the changed `*.test.ts` files on a temporary merge-base worktree (the pre-fix tree; the working tree and index are untouched) and print `red`, `green`, `no-test` or `test-only`. A change whose every path is a test file prints `test-only` without running anything — the merge-base runs the same code as HEAD, so its result would say nothing about the fix. A change to a doc or `prompts/` file is not test-only, because a document-rule test reads those files. On an Issue declaring `- 種別: 不具合`, `pnpm josh git -y` refuses `green`.

## `josh test:pinned` in detail

Answer before the review what a reviewer otherwise finds by hand: "reverting this change leaves every test green" (joshuafolkken/kit#4516). The command reads `git diff -U0` from the merge-base for the changed non-test code files (`--diff-filter=M`: an added file's one hunk is the whole module, and removing it fails every importer). An added script file is probed per function instead (joshuafolkken/kit#4647): each top-level `function`, `const` bound to a function, and function member of a top-level object literal has its body replaced by a throw, one at a time. A changed script hunk whose revert emits the same JavaScript — a comment, a type, a blank line — is dropped before the cap: no test can pin it, so listing it would stop every `josh run:review` that edited one. In a detached worktree at HEAD with the working-tree changes copied in — the caller's checkout and index are untouched — it applies each hunk or probe, runs `vitest related <file> --run`, and restores the file before the next one. The checks spread over up to four such worktrees, one per vitest worker the run is admitted on, each vitest capped to its share; a worktree checks its own hunks one at a time, so no two reverts share a tree (joshuafolkken/kit#4706). Each verdict is cached in the checkout's git directory under the hunk's file, function, old and current lines (not its position). A rerun reuses a `red` verdict only while the whole change — the merge-base commit and the content of every path changed since it — is the same: a hunk goes red on the tree with only it reverted, so a fixture, a config or a fix in another file can decide it, and a stale `red` would pass an unpinned hunk. A `green` or `no-test` one is reused while no test file's content changed, since a stale one stops a lane rather than passing it. The whole cache drops once a test file is added or removed. `josh run:review` calls the same run, so it shares the cache. A place on which nothing went red (green, or no related test) prints `unpinned <file>:<line>`, with the function's name for a probe; a function only a whole-module `vi.mock` reaches is listed this way. Each one is one vitest run, so the hunks and probes past `--max` (default 20, shared) print `unchecked <file>:<line>` instead of running. Without `typescript` installed, an added file prints `unchecked <file>`; without Vitest installed, nothing runs and every hunk and probe prints `unchecked`. `josh run:review` runs it before the gate and stops on any `unpinned` line unless `--unpinned-ok "<reason>"` is given, which prints the list and the reason after the brief; a `test:pinned` that cannot run at all prints a note and does not stop it; `josh ship --review --unpinned-ok "<reason>"` forwards it to round 1's `run:review`.

## `josh start` in detail

**Prerequisites:** the [gh CLI](https://cli.github.com/), installed and signed in (`gh auth login`). Without it `josh start` stops before changing anything. A run that creates a commit (the first commit, or the setup pull request) also needs a Git author identity — [Tell Git who you are](../setup/prerequisites.md#4-tell-git-who-you-are); without one it stops before changing anything and prints the two `git config` commands that set it.

Options: `--profile basic|full` sets the profile instead of asking (the detected one is the default). `--yes` accepts the defaults, but is not consent to write to GitHub: when step 4 or 6 is planned, an unattended run without `--github` stops before changing anything. `--public` creates a public repository. Without a terminal, `--yes` is required. `--init-command "<command>"` runs that command as step 2 instead of kit's setup — for a toolkit layered over kit, e.g. `"josh-app init"`. It runs without a shell, with `--profile <confirmed profile>` appended; its non-zero exit stops before the commit, and step 6 also commits every file changed since it ran. `--push-preflight-command "<command>"` runs that command before step 1, after every refusal, and only when step 4 or 6 is planned — for a check the toolkit's own pre-push hook depends on, e.g. `"josh-app start:preflight"`. It runs without a shell; its non-zero exit stops the run with nothing changed. A run that pushes nothing never runs it. `--dry-run` prints what each planned step would create or write ([init.md → Preview with `--dry-run`](../init.md#preview-with---dry-run)) and stops before step 1; it needs no terminal, `--yes` or `--github`, and an `--init-command` is named, not simulated.

Existing state: with a GitHub origin, nothing replaces it and `main` is never pushed to. After a failed commit hook, a re-run on the setup branch resumes step 6. A non-GitHub origin, or commits on a branch other than `main`, is refused before any change. In a repository with at least one commit, the working tree must be clean: uncommitted changes — modified, staged or untracked files that are not ignored — are listed and refused before any change, so the setup commit holds only what kit wrote; commit or stash them (`git stash push -u -- .`) first. The setup branch a failed commit left is exempt, since its uncommitted files are that run's own output.

## `josh adopt` in detail

Upgrade every `@joshuafolkken/*` toolkit installed in **this** repository to latest, sync each toolkit's managed files, update the other dependencies with [`josh latest`](../josh-commands.md#josh-latest), verify, and open the issue and pull request. The consumer-side counterpart of [`josh propagate`](../josh-commands-automation.md#josh-propagate), sharing its step order with `josh latest` added — propagation carries one exact release and leaves the other dependencies alone.

Steps, in this repository's directory: working-tree check, `pnpm add -D <toolkit>@latest` (once per installed toolkit, base tier first), `pnpm josh sync` per toolkit's own CLI, `pnpm install` then `pnpm josh latest` (the other dependencies, the audit and the pnpm pin — after the sync and behind an install, so the lockfile covers what the sync added to `package.json` even when `josh latest` rolls its update back), verification gate ([`josh gate`](../josh-commands.md#josh-gate)), open issue, `pnpm josh git`, return to default branch.

Output / exit codes: exits `0` on a skip (no toolkit declared, or all current with no file changed). A failing step exits non-zero; one that fails before `pnpm josh git` — `josh latest` included — opens no pull request, and a failed return to the default branch leaves the pull request open. Refused inside kit's own repository, when a runnable toolkit is missing or declared under `dependencies`, or when `@joshuafolkken/kit` is not a direct dependency. Stops at the open pull request — merging is [`josh followup`](../josh-commands-automation.md#josh-followup)'s job.

## `josh main:sync` in detail

**Behavior:** refuses inside a linked work tree (a lane) and exits non-zero — run it in the primary checkout instead; a lane's terminal step is `pnpm josh lane:close <issue-number>`. A default branch that has diverged fails loudly under `--ff-only` rather than growing a merge commit — the deliberate opposite of [`josh main:merge`](../josh-commands.md#josh-mainmerge). The same `--ff-only` pull is used by [`josh git`](../josh-commands.md#josh-git) and `josh pr` when they start from the default branch. After the pull it runs `git fetch --prune` and deletes, with `git branch -d`, every local branch whose remote-tracking upstream is `[gone]`, that is merged into the default branch, and that no work tree has checked out — a lane's branch, an unmerged branch, a branch with no upstream and a branch with a deleted local upstream are kept. It prints how many it pruned and names any `git branch -d` refused.

## `josh main:merge` in detail

**Behavior:** the merge strategy is named by the command rather than read from git config, so a diverged branch — the state the command exists for — merges cleanly instead of aborting with `fatal: Need to specify how to reconcile divergent branches`. Merging (not rebasing) avoids the force push the distributed `.claude/settings.json` denies. A conflict or uncommitted work on an incoming path fails; commit via `pnpm josh git -y`.

## `josh version` in detail

Show the global-install version, the current project version, and the latest published version — plus the **running binary** (the install that actually executed, resolved from `import.meta.url`), the single source of truth for which `josh` produced the report. A not-installed target reports `not installed`; a stale one gets a `Run:` hint with the upgrade command. A release inside the `pnpm-workspace.yaml` `minimumReleaseAge` window prints a `Held:` line. When the `josh` first on `PATH` is not the pnpm-global install, a PATH-shadowing warning names both paths and points to [`josh doctor --fix`](../josh-commands.md#josh-doctor).

## `josh ranges` in detail

Check that every dependency range this package **publishes** still resolves for a consumer. For each `dependencies` entry it runs `pnpm view <name>@<range> version` under safe-chain's shims, so the age-filtered view a consumer installs under is observed rather than modelled. `devDependencies`, peer ranges, and non-registry protocols (`workspace:*`, `catalog:`, `file:`, `link:`, git URLs) are set aside and printed, not probed.

In a package built on a `@joshuafolkken/*` toolkit it also compares each published `peerDependencies` range with that of every installed toolkit `package.json` declares, and fails when a floor sits below the toolkit's — `josh latest` never rewrites a peer range, so the declaration would otherwise keep promising versions nobody verified. Matching or narrower ranges, peers no toolkit shares, and kit's own repository report nothing.

Output / exit codes: fails closed — a range resolves only when the output contains a `semver`-parsable version; a probe that cannot answer (network, auth) is reported unresolvable. Probing `@joshuafolkken/*` dependencies needs `NODE_AUTH_TOKEN` — run `export NODE_AUTH_TOKEN=$(gh auth token)` first for a bare invocation. To fix a violation, lower the floor to a release already outside the age window (e.g. `^4.23.4` instead of `^4.23.5`). A peer-floor violation names the dependency, its range, and the toolkit (name and installed version) with the range it requires; raise the `peerDependencies` floor to that range.

## `josh doctor` in detail

`doctor` reports the running binary, the `josh` first on `PATH` (`which josh`), and the pnpm-global install (`pnpm bin -g`), warning when the two differ and printing the recovery command. In a kit consumer it also prints a **Consumer setup** section — one-line `✓` / `⚠` verdicts for the kit plugin, git `core.hooksPath`, `CLAUDE.md`, and secretlint — plus the repository's Dependabot security updates and Allow auto-merge settings (`enabled` / `disabled` / `could not be read`; auto-merge also `paused`) and, where a distributed workflow is present, the Required status checks report of [`josh ruleset:check`](../josh-commands-automation.md#josh-rulesetcheck). None of these ever fail the command, and `doctor` never changes a repository setting.

## The discovered repository map in detail

Discovery is automatic: `doctor` scans the parent directory one level deep, reads each work tree's `origin` remote, and keys the map by that remote's normalized `owner/repo` (SSH, host-alias SSH, credentialed HTTPS, and plain HTTPS all normalize the same). **The directory name is never used as the repository name** — a checkout in `kit-experiment` whose `origin` points at `game-kit` maps as `game-kit`.

## `josh latest` in detail

`josh latest` never lowers a version: a supply-chain age gate can make the registry report an older release as newest, so `latest:update` rolls the whole tree back rather than writing a silent downgrade. It reports the overrides verdict itself and separately fails the run if `pnpm-lock.yaml` no longer honours an unconditional override. Whether a run has to update at all is [`josh latest:scope`](../josh-commands-automation.md#josh-latestscope).

## `josh latest:corepack` in detail

Updates pnpm and pins `packageManager` to the newest release on the project's **current major** (from `packageManager`, or from `devEngines.packageManager.version` when that is the only pin). The command name is retained for compatibility. With an existing `packageManager` pin, it obtains the release integrity value, runs `pnpm self-update`, then restores the integrity suffix and aligns `devEngines.packageManager.version` byte-for-byte with `packageManager`. Without that pin, it adds a verified pin and checks that the selected pnpm version starts. A registry answer that is not newer than the pin, or no release on the major aged past the quarantine window yet, is a skip and exits `0`. Any failure — a registry that does not answer, no integrity value, `pnpm self-update` exiting non-zero, an unexpected pin after it, or a selected version that cannot start — restores `package.json`, prints the cause and exits `1`. When pnpm runs through the Corepack shim, which pnpm 11 and later refuse to self-update under (`ERR_PNPM_CANT_SELF_UPDATE_IN_COREPACK`), the message also names the remedy: `corepack disable pnpm`, a standalone pnpm, and `josh sync` so `devEngines.packageManager.onFail` is `"download"` — the standalone pnpm then fetches the pinned version rather than refusing to run. Either way, existing `devEngines` drift is still aligned to `packageManager`.

## `josh latest:update` in detail

Runs `pnpm update --latest`, skipping **held-back** and overridden packages (effective overrides read from `pnpm-workspace.yaml`) — `typescript` is currently held at `6.x`. Skipped packages print as `⏭ Skipping held-back / overridden packages: …`. If any direct dependency would move down, it restores `package.json` and `pnpm-lock.yaml` to what it found and exits `0`. Otherwise it also moves the `SAFE_CHAIN_INSTALLER_VERSION` / `SAFE_CHAIN_INSTALLER_SHA256` env to the newest `@aikidosec/safe-chain` release — a registry answer that is not an exact semver version is refused and nothing moves — in every workflow under `.github/workflows` and `templates/workflows` and every local composite action under `.github/actions` that carries the pin — in kit itself, the `.github/actions/setup-pnpm` action every workflow installs through, the distributed `ci.yml` included — the hash is computed from that release's `install-safe-chain.sh` once `gh release verify-asset` has checked it against the release attestation GitHub signed at publication, and a failed download or a failed verification leaves the workflows' pins untouched with a warning (the next `josh latest` retries).

When the update moved the installed `@playwright/test`, it runs `pnpm exec playwright install chromium`: a Playwright release cannot launch the browsers an earlier one downloaded. Set `JOSH_PLAYWRIGHT_BROWSERS` in `.env` to a space-separated list (`chromium firefox webkit`) for more — CI reads the same name from a repository variable ([troubleshooting.md](../troubleshooting.md#widening-the-fallback-browser-list)). An unmoved version installs only missing browsers. A failed or rolled-back update that moved it still installs. A failed install prints `✖ Playwright browser install failed` and exits non-zero, stopping `josh latest`.

## `josh backlogrun` in detail

- `--agent`'s start command is built by `scripts/agent/agent-argv.ts`, the same builder that starts lane children, and the choice is handed to the run as `JOSH_AGENT_PROVIDER`.
- `--stop` stops the run in this repository in one command, so the next `pnpm josh backlogrun` starts a new one. It stops the [`run:wake`](../josh-commands-run.md#josh-runwake) supervisor, then the parent session `josh backlogrun` started, then a headless session the run launched (the one the supervisor woke) where that session holds the run's record — the record itself marks it, so this holds after the supervisor's record is gone, then ends the run's record as a stopped run (the board keeps it as one). It takes no other argument: beside an Issue or another flag it prints the usage and stops nothing.
- `--restart` stops the same three processes in the same order and leaves the record, then starts a supervisor on the stopped one's profile — read before the stop removes its wake record, so the shell the restart is typed in does not pick the provider; the supervisor adopts the record whose owner it just lost and wakes a session where a decision is needed, as it does after any crash. It takes over the run rather than rebuilding it: rebuilding is `--stop` and the invocation typed again, so `--restart` does not repeat it. It starts no parent session, because the driver (`backlog:drive`) does the routine work and the plan was made when the run began. It stands alone as `--stop` does. An owner session it may not signal is found before anything is stopped, so a refused restart leaves the run's supervisor and parent running.

**Output / exit codes:** prints one line naming the started pid, session and log path, then the board's exit code. Bad arguments print the usage and exit 1; an agent that cannot start (a missing or outdated CLI) exits 1 without a board. `--stop` prints one line per thing it stopped, or `backlogrun: nothing is running`, and exits 0; it exits 1 only when the record is left with an owner it did not start. `--restart` prints one line per thing it stopped and `backlogrun: kept the run's record`, then the board's exit code; it exits 1 without a board when there is no record, the run has ended, the record cannot be read, the owner is a session it did not start, or the supervisor does not start.

## `josh rule:value` in detail

Print each delivered rule's **unaided compliance** — how far the carried text alone kept the rule in the window before its trigger fired (`scripts/rules/rule-value.ts`). One row per rule: the runs that reached the situation it governs, the rate kept before the trigger (or `unmeasured` where the rule declares no `keeps` predicate, `unreached` where no run reached it), and the refusals the hook actually delivered — followed by `rewritten N` on a rule whose hook rewrote the call instead of refusing it.

- Read once per iteration at the `backlogrun` loop head (`josh backlog:offer`), so a rule that never fires appears as a printed row rather than as something a person has to think to measure. The loop head never measures: it prints the last reading from `node_modules/.cache/josh/rule-value.txt` to stderr and, at most once every 15 minutes, starts a detached `josh rule:value --refresh` that rewrites it, so the offer never waits on the measurement and a failed one never changes its answer. Single sources: `scripts/rules/rule-value-cli.ts` and `scripts/rules/rule-value-cache.ts`.
