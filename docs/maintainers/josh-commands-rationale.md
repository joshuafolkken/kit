# josh command reference — rationale and history

How the dispatcher behind [josh-commands.md](../josh-commands.md) runs a command — kit's own
checkout and writing a new script — kept here so the reference states only each command's contract.

## How a command runs

Most commands are a TypeScript file under `scripts/`; the rest are a shell line the dispatcher spawns. In kit's own checkout the dispatcher evaluates a script command in its own process rather than starting a second TypeScript runtime for it. Three conditions decide whether a command takes that route:

- **The dispatcher must run from TypeScript source** — kit's own `pnpm josh`. A consumer's `josh` bin is the bundled `dist/josh.js` under plain node, so a consumer keeps the spawning path for every command except one marked `is_bundled`, which it imports pre-built from `dist/commands/` ([runtime-bundling.md](./runtime-bundling.md)).
- **The command must not need node flags of its own.** `doctor`, `latest:scope`, `followup` and `notify` pass `--env-file`, so they keep a process of their own.
- **A shell command has no script to import** and is spawned as before.

A new josh script keeps the canonical main guard `process.argv[1] === fileURLToPath(import.meta.url)`, or none at all. `scripts/josh/josh-in-process.test.ts` asserts the shape for every command that takes this route.

## `josh gate`'s core budget

Each check claims a place in a machine-wide weighted core budget before it starts (joshuafolkken/kit#2351). The weights are the same measured table the plan already uses — the static checks' reserved cores and the unit suite's worker cap — so a lone gate's four claims sum to exactly the core count and every one is admitted at once: a solo run's concurrency and worker count are unchanged. Under concurrency the machine-wide sum is what bounds admission, so overlapping gates can no longer each reserve the whole machine, and the "whoever started first took everything" asymmetry is gone — a later gate waits rather than shrinking everyone.

**The budget is what the machine has free, in cores and in memory** (joshuafolkken/kit#3371). The core count is the ceiling, but once the ledger holds more than one place, admission reads the machine (`scripts/gate/machine-capacity.ts`): busy cores from the CPU-time difference over a 250 ms window, and available memory from `kern.memorystatus_level` on macOS or `MemAvailable` on Linux. Only load from outside the ledger — beyond a two-core baseline the weights were measured beside — shrinks the core budget, and each heavy tool declares its measured peak memory (`core_budget.MEMORY_MB`) so a claim also waits while that memory is not free. A marker is rewritten with its admission time once it runs; after a 30 s ramp-up window its declared load counts as the ledger's, which is how the reading's load is split into the ledger's and the rest — a tool admitted moments ago has not allocated yet, so its memory is not added back onto what is free. A claim the wait cap admits names both its cores and its memory against the budget. A solo claim reads nothing and starts as before; a reading that fails (CI, a CPU quota narrower than the host) falls back to the core count with no memory limit.

A leaked place is swept on read by the same pid-and-start-time liveness the unit-run marker uses, and a reservation that never fits is admitted at minimum width after a wait cap — and the gate's summary then prints a `⚠ <check> — started past the core budget …` line above the verdict, so an over-subscribed run does not look like one that fitted. A gate nested inside another gate's unit suite (this repository's own gate tests) takes no place, so it never waits on cores the outer gate is holding. The pre-push `pnpm install` and `pnpm josh audit` join the same budget through [`josh reserved-run`](../josh-commands-automation.md#josh-reserved-run).

## `josh metrics`' durations

Performance work waits for a measured problem, so `josh metrics` holds four durations to a baseline and fails one that slowed past a tolerance (joshuafolkken/kit#3409).

**Only like is compared with like.** A duration taken under load measures the load: beside the whole unit suite, `josh --help` starts 40–77% slower than on a quiet machine, and its CPU time rises as much, so no tolerance both passes the gate reliably and still catches a real slowdown. The comparison is held to one condition instead of being widened.

- **`gate` and `unit` are read, not timed, and only from solo gates.** `josh gate` already appends its duration and its unit suite's to the lane ledger ([lane-limit-measurement.md](./lane-limit-measurement.md)), so `josh metrics` reads them back. A gate counts only when no other gate of the repository — passed or failed — ran at any point between its start (`at` minus `elapsed_ms`) and its end; the overlap of the gates' own spans decides, not the number of open lanes, and the ledger measured none in 17 gates while three lanes ran. The value is the median of the last five solo gates that ran the unit suite, so one gate slowed by other work (a review, a related test run — 138 s against the usual 47–68 s) does not fail the next. A failed gate counts as well: every check runs to completion whether it passes, so it timed the same work, and a gate this step failed on a slowdown has to count — reading passed gates alone would hold the slow median, and every later gate red, after the slowdown was fixed. The median still trails a fix: it stays slow until the fixed gates are the majority of the five, so up to three gates after a fix still fail — the failure message says so, and a slow reading is rerun before it is accepted, since an accepted baseline never moves back down on its own. They are the _previous_ gates' — the step runs inside a gate whose own duration is not known yet — and fewer than five solo gates (a ledger cleared by a reboot, a new clone) read as not measured (`—`), so a first baseline is never the median of one quick gate.
- **`josh_startup` and `guard_startup` are timed only when `josh metrics` runs on its own** — the gate passes `--no-startup` and neither times nor prints them. Each is the fastest of five runs of `josh --help` and of the `pretool-guard` hook every tool call starts. A startup regression therefore fails a hand-run `pnpm josh metrics`, never a gate.
- **A tolerance of +10%**, where the static totals have none: a count read off a tree is the same on every run, a duration is not.
- **The baseline never moves down on its own.** One quiet run would set a bar the next ordinary run misses; a speedup is recorded with `--accept`, as a raise is.
- **The baseline is per machine and never committed.** It is `josh-metrics-durations.json` in the repository's common git directory — one file per clone, shared by every lane of it. The same durations on two machines do not compare, CI starts each job on a fresh runner, and a committed table keyed by host would publish host names and conflict on every merge. A machine's first measurement of a duration becomes its baseline; deleting the file starts that machine over.
