## 分類と根拠の残し方

各 PR の変更ファイルと差分、PR 本文、元 Issue の本文と後続コメントを読む。後続コメントで判断が更新されていれば、その内容を優先する。Issue のラベルだけで結論を決めない。元 Issue がない PR は、そのことを監査表に明記し、PR 本文と差分から判断する。監査表の `reason`、`issue_evidence`、`later_comment` に判断根拠を残す。

取り消された変更や第一親との差分がない統合は `ignore-for-release` とする。掲載する変更では、互換性を壊すものを最優先で `breaking-change` とする。互換性を保つ機能追加・改善は `enhancement`、既存の誤動作の修正は `bugfix`、文書・依存関係・内部保守は `other-change` とする。ラベルの意味と PR 作成時の入力欄は [PR テンプレート](../../.github/pull_request_template.md)、掲載区分は [リリース設定](../../.github/release.yml) に定義している。ここでは履歴監査時の照合順序を定め、同じラベル定義を複製しない。

判断に必要な本文や差分が読めない場合は推測で分類せず、PR 番号と不足情報を保留一覧に記録する。保留を解消してから分類ラベルを付ける。PR は五分類のラベルをちょうど一つ持つように補正し、元 Issue のラベルも本文との矛盾が確認できた場合だけ直す。四区間の監査では各行の根拠とラベルを確認済み。

## 再取得とリリースノートの照合

第一親のマージ履歴を再取得する。件数はこのスナップショットで 1,104 件。対象番号とマージ SHA を昇順に並べて SHA-256 を計算すると `4bfb0abe08e5ff7e6c5a8afeb31f67b529c51b71f740524bb2be52792c525a7c` になる。

```sh
git log --first-parent --merges --format='%H %s' v0.113.0..01eb8610556d27a5a0f60726d133561916dba9b3
pnpm exec vitest run scripts/release/release-classification-audit.test.ts
```

GitHub のリリースノート生成 API に比較開始点を明示してプレビューした。`v1.888.0` はプレビュー用の仮タグ名であり、Release は公開していない。返された本文の PR リンクは 1,093 件で重複なし。第一親履歴との差は、監査表で除外した #349、#352、#364、#379、#385、#531、#675、#756、#758、#763、#2520 の 11 件だけだった。四つの掲載区分の件数も上表と一致した。

```sh
gh api -X POST repos/{owner}/{repo}/releases/generate-notes \
  -f tag_name=v1.888.0 \
  -f target_commitish=01eb8610556d27a5a0f60726d133561916dba9b3 \
  -f previous_tag_name=v0.113.0
```

初回の対象タグが確定したら、そのタグまでの第一親履歴から未監査の PR を抽出して同じ列で根拠を記録し、全件数、重複、欠落、範囲外、保留件数を再計算する。最後に実際のタグを使って同 API を再実行し、除外以外の PR 番号集合と分類別件数を照合する。公開経路と直前 Release の選び方は #2631 が担当する。
