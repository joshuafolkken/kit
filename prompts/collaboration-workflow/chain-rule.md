## `/code-review` → `followup --merge` の連鎖規則

**この規則の単一ソースは [`.claude/skills/workflow-commands/chain-rule.md`](../../.claude/skills/workflow-commands/chain-rule.md) である。** ここに本文を複製しない（「クローン禁止・単一ソース化」の適用。joshuafolkken/kit#1174 のパイロットに続く横展開 joshuafolkken/kit#1186）。

`residency.md` が定めるとおり、この規則は `fullrun` / `queue` が始まった後にだけ効くので、手順本体は skill 側に置く。かつては同じ内容の全文が [`plan-comment.md`](./plan-comment.md) の後半にも重複していた。

**この話題だけは、話題ファイル全体ではなく 1 節の縮小だった。** `plan-comment.md` は Step 3（計画コメントの記録と通知）という別の本文も持ち、[`fullrun.md`](../../.claude/skills/workflow-commands/fullrun.md) からその手順として正当に引用されているので、ファイルごと指し先にはできない。そこで**節をこの 1 本へ切り出してから縮小した**。決め手はファイルの大きさではなく引用である。指し先の検出（冒頭の宣言文）も、指し先を引用してはならないという規則も、ファイル単位で効く — `plan-comment.md` に宣言文を置けば、Step 3 のために張られている正当な引用がそのまま違反として検出される。これを通すには「その引用はどの節に対するものか」を判別する第 2 の機構が要り、節名を書かない引用をどちらの節へ帰属させるかは決められないため、joshuafolkken/kit#1178 が「本文はどのファイルにあるか」の 1 問へ縮めた判定に書き手の裁量が戻る。**1 ファイルに複数の話題があるときは、節を話題ファイルへ切り出してから縮小する** — これが横展開の残りに対する前例である。

参照文書だけにあったのは、自己点検が条件付きである理由（`/code-review <PR>` を単独で打ったときに自動マージへ進ませないための第 1 段である）、自己点検が書かれるきっかけになった違反 2 件（PR #387 / PR #398）、同じ自己点検が `prompts/review.md` の末尾にも写されている理由、そして CLI での機械的強制を調べた結果（`/code-review` は Markdown を返す対話型 skill なので、シェルコマンドが重大度を解釈して判断を代行することはできない）である。いずれも縮小の前に手順書へ畳み込み済みである。

手順書に置かれている内容:

- `/code-review` の出力はターン境界ではなく、中間成果物であること
- `fullrun` / `queue` が停止してよいのは 2 状況だけで、判断を要する blocker は 3 種類に限られること
- `/code-review` の結果を次の行動へ機械的に写す決定表と、末尾の推奨文ではなく指摘の重大度が判断を決めること
- 違反の具体的な文面を並べたアンチパターン集
- 応答を送る直前に走らせるターン終端セルフチェック（モード判定・重大度判定・追記判定の 3 段）
- レビューは合計 2 周までで、2 周目の後に残る High 以外の指摘は 3 分岐へ振り分けること
