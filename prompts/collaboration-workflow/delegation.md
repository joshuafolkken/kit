## 委譲 — 機械的な工程を安価な実行単位へ回す

ランの全工程が同じ深さで走っている。設計・分割判定・レビューのように判断を要する工程と、答えが既に決まっていて手順を実行するだけの工程が、同じ単価で処理されている（joshuafolkken/kit#969）。

### 委譲してよいかはコマンドが答える

```bash
pnpm josh delegate gate-fix     # → delegate
pnpm josh delegate review       # → keep
pnpm josh delegate --list       # 一覧と、却下した工程とその理由
```

標準出力に `delegate` か `keep`、標準エラーに理由が出る。

**判断で決めない。** 「これくらいなら安い方で足りる」は費用の圧力の下で下される判断であり、**誤りが最も起きやすいちょうどそのときに「足りる」側へ倒れる**。`josh review:level` がレビューの深さを変更の中身から決めるのと同じ理由で、ここも列挙とコマンドで決める。

### 既定は `keep`（列挙が規則のすべて）

**列挙に無い工程はすべて `keep` である。** 誰も分類しなかった工程は、「委譲してはいけないと誰も言わなかった」ことを理由に委譲されてはならない。既定を `keep` に置くと、見落としは**費用**として現れる。既定を `delegate` に置くと、見落としは**品質**として現れ、しかも静かに現れる。

### 委譲してよい条件は 3 つで、2 つ目が本体である

1. **やり直さずに検証できる** — 親側で走り、その工程をやり直すより安い検証がある
2. **誤りがその検証で捕まる** — 「起きにくい」ではなく「捕まる」。ここが実質的な条件で、候補の大半はここで落ちる
3. **列挙にある** — 1 と 2 を満たしても、列挙に足されるまでは `keep`

### 委譲してよい工程（列挙）

| 工程         | 内容                                                                                                           | 誤りが捕まる経路                                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `gate-fix`   | ゲートが既に名指しした修正を当てる（lint 規則、型エラー、辞書が拒否した綴り）                                  | `pnpm josh gate` を再実行する。誤った修正は再び落ち、失敗がファイルを名指しする                                                                  |
| `epic-child` | epic の子 1 件を隔離された実行単位で最後まで走らせ（計画・検証ゲート・PR・マージ）、要約だけを親のループへ返す | 親が子の状態を要約ではなく GitHub から読み直す。完了と報告されてマージされていない子は open のままであり、ランが先へ進む代わりに失敗が表面化する |
| `survey`     | 多数のファイルを横断して読み、何がどこに現れるかを報告する（ある記号の全参照、あるマーカーを持つ文書）         | 報告された位置を直接確認する。捏造や見落としは、主張した箇所を 1 回 `grep` すれば残らない                                                        |

### 却下した工程（列挙）

条件 2（誤りが検証で捕まる）を満たさない、あるいは誤りの波及が大きい工程。**記録として残す** — 次に同じ提案をする者が理由を再導出しなくて済むように。`pnpm josh delegate <工程>` はこれらに `kept deliberately` と答え、列挙にすら無い工程の `kept by default` と区別する。

| 工程               | 却下理由                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notify-body`      | 検証経路が無い。誤った本文の通知は送られ、正しいものとして読まれ、後続の誰も否定しない                                                                         |
| `issue-comment`    | 検証経路が無い。決定ログや完了報告は**それ自体が記録**なので、突き合わせる相手がいない                                                                         |
| `status-read`      | 誤読はランを誤った子へ導き、後続のどの工程も否定しない。コマンドを走らせること自体は既に安く、高いのはその結果に基づいて動く部分であり、それはこの工程ではない |
| `diagnosis`        | 誤った根本原因は、ゲートを通過して欠陥を残す修正を生む                                                                                                         |
| `design`           | 誤った設計の費用は、それ以降のすべての工程が払う                                                                                                               |
| `split-assessment` | 分割の見落としは、1 件の Issue を誰も承認していないバッチへ広げる                                                                                              |
| `review`           | レビューは欠陥とマージの間に残る最後の 1 つであり、安いレビューは見つける数が減る                                                                              |

### 機構と単位を分ける

**機構**（どう委譲し、失敗をどう露出させるか）と**単位**（何を委譲するか）は別物である。

- **機構**: 隔離された実行単位へ、明示的な指示とともに渡し、**親が検証できる形の結果**を返させる。失敗は親側の検証で捕まる
- **単位**: 「ランの 1 工程」（`gate-fix` / `survey`）と「epic の子 1 件」（`epic-child`）

**機構を単位に癒着させない。** joshuafolkken/kit#984 が足した `epic-child` は、2 つ目の機構ではなく**同じ列挙の 1 行**である。単位が「工程」から「子 1 件」へ変わっただけで、渡し方・返し方・失敗の露出のしかたは何も変わらない。別々に作れば `CLAUDE.md` の「No clones — single-source」が禁じているクローンになる。

**`epic-child` の検証経路は、子の完了報告ではない。** 親が読むのは GitHub 上の子の状態であり、実行単位が返す要約ではない。要約が「終わった」と言っても PR がマージされていなければ、その子は `CLOSED` になっていない — これが「誤りが捕まる」の中身である。加えて子自身の検証ゲート・`/code-review`・CI は実行単位の中で走り、`pnpm josh followup --merge` はそれらが緑でなければ PR に触れない。

**確認は `epic:next` の次の答えに任せない。** 終わらなかった子は `in-progress` を付けたままであり、`epic:next` はそれをブロッカーより先に「時間で解ける」と分類する（`scripts/epic/epic-classify.ts`）。放っておくと親は 90 分の stale 判定までポーリングするだけで、何も学ばない。**実行単位が返った直後に `pnpm josh issue:state <N>`（別リポジトリの子なら `--repo <owner/repo>` を付ける）を読み、`CLOSED` でなければ失敗として扱う** — ラベルを親が外し、連続失敗のガードに数え、人が要るなら park する。
