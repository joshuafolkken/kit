## `josh epic:audit` — 子 Issue 群を横断して矛盾を検出する

`pnpm josh epic:check` は epic **1 件の形式**を検査するが、**子 Issue 群を横断した整合性**は誰も検査していなかった。joshuafolkken/kit#858 の子を人手で監査したところ、実装を始めれば必ず詰まる矛盾が 2 件見つかり、その間ずっと `epic:check` は 4 要件すべて通過と報告していた。

- **循環依存** — #863 の本文が「#864 の発見結果を使う」と書き、#864 の本文が「公開の判定は #863 と同一実装を共有する」と書いていた。どちらも `blocked-by` は空で、epic 本文は両方を「独立」と宣言していた
- **順序矛盾** — #860 の受け入れ条件が #863 / #864 の成果物を要求していたが、依存グラフ上 #860 はその 2 件より先に走る

人が「バグを探して」と指示して初めて見つかる状態では、無人実行の前提が成り立たない。

### 検査項目

グラフそのものの性質（循環依存、本文の宣言と `blocked-by` の食い違い）は `josh epic:next` が着手可否の計算のために既に検出しており、**その判定を利用する。検出を作り直さない。** 本コマンドが新たに担うのは、子 Issue の**本文の中身**を横断して読む 4 つと、そのうち孤立した子の検索が何を読めなかったかを報告する 2 つである。

| 検査         | 種別   | 内容                                                                                                                                          |
| ------------ | ------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 暗黙の依存   | 警告   | 子 A の本文が同じ epic の子 B を参照しているのに、どちら向きにも依存が宣言されていない                                                        |
| 順序矛盾     | エラー | 子 A の**受け入れ条件**が子 B の成果物を参照しているのに、A が B に依存していない（先に走れる）。ただし A・B がどちらも closed なら警告に降格 |
| 未解決の参照 | 警告   | 本文が参照する Issue が存在しない、または既にクローズ済み                                                                                     |
| 孤立した子   | 警告   | epic を親として参照しているのに epic のタスクリストに載っていない Issue                                                                       |
| 孤児検索     | エラー | 上記を探すための open issue 一覧そのものが読めなかった（レート制限、認証切れ）                                                                |
| 孤児検索     | 警告   | その検索が backlog の末尾に届く前に打ち切られた（500 件のページ上限、または 50 件の一致上限）                                                 |

### 警告とエラーを区別する

**警告は exit code を左右せず、エラーだけが exit 1 になる。** 暗黙の依存の検査は「参照している」ことしか見ないため、後続の子への前方参照（「この部分は #864 が埋める」）にも当たる。これをエラーにすると正当な設計メモが書けなくなるので、**判断は読み手に委ね、機械は見落としを防ぐ側に徹する**。

一方、受け入れ条件が後から作られるものを要求している状態は誰がどう決めても満たせないため、エラーとする。

### 両端が closed の順序矛盾は警告に落とす

順序矛盾がエラーである根拠は「**先に走れてしまう**」という一点にある。子が 2 件とも closed になった時点でどちらにも実行が残っておらず、その根拠は成立しない。にもかかわらずエラーのままにすると、**過去に一度でも順序を宣言し忘れた EPIC は永久に監査を通らなくなる** — `epicrun` は最初の子より前に監査を走らせるため、その EPIC は再開のたびに一歩目で止まる。joshuafolkken/kit#908 で実際に起きており、同じ状態で `epic:next` は次の子を問題無く返していた。すなわち**エラーが止める根拠と、実際に実行を阻むかどうかが食い違っていた**（joshuafolkken/kit#1010）。

**「報告しない」ではなく「警告に降格」を採る。** 受け入れ条件は本文の一部なので、同じ組は暗黙の依存の検査にも当たっており、順序矛盾がその組を報告している間だけ重複が抑止されている。落とせばその組は 1 行下に `implicit dependency` として現れるだけで、**出力は 1 行も短くならず**、「受け入れ条件に書かれている」という唯一読む価値のある情報だけが失われる。短さという利点が実在しない以上、履歴を残す側を採る。closed かどうかは**確認できた場合にのみ**降格する — `epic_issue.normalize_state` は `CLOSED` 以外（`MERGED` を含む）をすべて `OPEN` に写すため、確認できない状態はエラーのまま残る。

### 孤児検索の 2 件は「子の矛盾」ではない

孤立した子の検査は open issue を一覧して本文をクライアント側で照合する。**一覧が読めなかった場合、以前はそれが空の結果として届いていた** — レート制限が「孤児ゼロ」という綺麗な監査結果を生み、何も読んでいないことが出力から分からなかった（joshuafolkken/kit#1033）。

- **`✖ orphan search: Could not list the open issues…`** — 検査そのものが走っていないので、`epic:audit` は exit 1 になり `epicrun` は相 0 で止まる。**対応は監査の再実行だけ**で、直すべき矛盾も決めるべき設計判断も無い — 下記の Tier A にも `needs-decision` park にも当たらない。繰り返し失敗するなら `gh auth status` とレート制限の回復を確認する
- **`⚠ orphan search: The open-issue scan hit its …`** — 検索は走ったが backlog の新しい側だけを見た（500 件のページ上限、または epic に言及する本文 50 件で打ち切り）。監査自体は通るので、行を読んだうえで、より古い位置に孤児が予想される場合だけ人手で確認する

### 実行される場所（人が指示しなくても回る）

- **`josh epic:plan` の相 0** — 一括決定の前に矛盾を洗い出す
- **`epicrun` の開始時** — 矛盾を抱えたまま無人実行を始めない
- **子 Issue を追加した直後、依存を変更した直後**

### 検出した矛盾は Tier A（確認せず直す）

依存の付け直しも本文の記述修正も可逆であり、放置すれば必ず実装時に詰まる。**確認を挟む価値がないので、人に尋ねず修正して根拠を Issue に記録する。** 例外は「どちらの設計を採るべきかが決まらない」種類の矛盾で、これに限り該当の子に `needs-decision` を付けて park する。

### 波及先の点検（計画段階の手順）

機械的検査では捕まらない欠陥として、**新しい概念を導入したのに既存コードの参照箇所が更新されない**というものがある。#858 の監査では 3 件見つかった — `needs-decision` ラベルを導入するのに除外集合への追加担当が無かった、`epicrun` を導入するのに epic 本文が古いコマンドを案内し続ける点の担当が無かった、`in-progress` を付ける処理はあるが外す処理が無かった。

したがって計画段階で次を行う。**新しいラベル・コマンド・状態・成果物を導入する子 Issue がある場合、既存コードでその概念を参照している箇所を列挙し、更新の担当がいずれかの子 Issue に割り当てられていることを確認する。** ラベル名は `scripts/git/issue-labels.ts` に単一ソース化されているので、そこを起点に消費者を辿れる。
