## 後から関連が判明した Issue を epic に束ねる

「2 件以上に分割したら常に epic を作る」は既に効いているが、**発火するのは 1 つの要望をその場で分割したときだけ**である。別々のタイミングで起票された Issue が後から関連していると分かっても、束ねる仕組みが無い。次が漏れる。

- 実装中に Tier A で起票した Issue が、既存の open Issue と順序や依存を持っていた場合
- 何日か空けて起票した 2 件が、実は同じ作業の前後だった場合
- 既存 Issue が実行順を必要としていることに、後から気づいた場合

いずれも束ねられないまま個別に実行され、順序が守られず、分割の根拠がどこにも残らない。

### 発火点

**Issue を新規に起票した直後**に、既存の open Issue を調べる。`kickoff` / `fullrun` / `halfrun` が起票したとき、および実装中に Tier A で起票したとき（`epicrun` 実行中を含む）。

`pnpm josh epic:bundle <N>`（エイリアス `eb`）が候補を探して推奨を表示する。**このコマンドは何も書き込まない** — 候補を出すのが機械、束ねるかを決めるのは AI である。

### 起票の「前」に答えるのは `issue:scout`

`pnpm josh issue:scout "<title>"`（エイリアス `isc`）は、まだ存在しない Issue について同じ配属先の問いに答える（joshuafolkken/kit#1252）。**配属の判定は `epic:bundle` のものをそのまま呼んでおり、実装は 1 つしかない。** 加えて、`epic:bundle` が意図的に採らないシグナル — タイトルの語の重なりによる**重複候補** — を返す。既存 Issue の束ね直しに似た見出しが立つのは強シグナルだけで十分だからだが、「もう起票されていないか」は起票前にしか意味を持たない別の問いであり、しきい値を混ぜていない。

**両方を実行する。順番が違うだけである。**

| いつ                       | コマンド                | 何について答えるか                                 |
| -------------------------- | ----------------------- | -------------------------------------------------- |
| `gh api … issues` の**前** | `issue:scout "<title>"` | まだ番号を持たない下書き。タイトルと要約だけがある |
| 起票の**直後**             | `epic:bundle <N>`       | 実在する Issue。番号と、それに記録された関係がある |

手順上の位置づけと、重複候補が見つかったときに起票せず止まる規則は `.claude/skills/workflow-commands/SKILL.md` → §2e が単一ソースである。

### 後追い Issue は起票した直後に EPIC へ束ね直す

レビュー上限（`prompts/review.md` → "Review round cap"）で切り出す後追い Issue は、**このワークフローで最も件数の多い起票経路**である。それでも手順は長らく「起票して現在の Issue を参照する」までしか定めておらず、束ね直しへの導線が無かった。手順どおりに読むと起票して次へ進んで終わる。

なお 2 巡目を終えた残指摘は、いまは**3 分岐（その場で直す／起票する／PR に 1 行残して落とす）**に振り分ける（`prompts/review.md` → "Review round cap"）。本節が扱うのは**起票する**分岐に入ったものだけであり、その場で直したものと落としたものは Issue にならないので束ね直しの対象にもならない。

手順は 3 段であり、**上の発火点の一適用ではなく、後追い起票の手順そのものに書く**。別の文書を読みに行く前提にしない。

**3 段は CI 待ちの中で実行する。コミットの前ではない。** PR を開くフロー（`fullrun` / `queue` / `epicrun`）では `pnpm josh git -y` の後・`pnpm josh followup --merge` の前に置く。PR を開かないフロー（`halfrun`、ワークフロー外のコミット前セルフレビュー）では、隠れる先の CI が無いので振り分けが決まった時点で実行する。**期限は変わらない** — 現在の Issue が閉じるのはマージ時点であり、マージするのは `followup` なので、どの段も親が open のうちに終わる。第 2 段が要求しているのはそれだけである。変わるのは秒が誰のものかだけで、実測では `epic:bundle` 43 秒・`epic --add` 18 秒（joshuafolkken/kit#1229）に対し、joshuafolkken/kit#1238 の `followup --merge` は 122 秒のうち 78 秒を CI の完了待ちに費やしている（joshuafolkken/kit#1239）。

**これは「レビューを CI と並走させる」ではない。** joshuafolkken/kit#1216 の (b) は不採用と決定済みであり、却下の理由は規則ではなく仕組みである — あちらは**コードを変える作業**を CI と重ねるため、修正を push するたびに CI がやり直しになり、重ねた分をそのまま払い戻す。起票はコードを 1 行も変えないので、走っている CI がそのまま使える。レビュー自体はコミットの前のままで、「コミット前セルフレビュー」は書き換えていない。

1. 残指摘を後追い Issue として起票し、現在の Issue を参照する
2. **現在の Issue が閉じる前に** `pnpm josh epic:bundle <新規>` を実行する。候補探索は open Issue しか読まないため、親が閉じた後では恒久的に `none` になる（joshuafolkken/kit#947）
3. 答えに従う。**`epic:bundle` は推奨するだけで何も書き込まない**ので、「実行する」とは書き込みコマンドを自分で打つことである。**epic 本文の手編集は禁止** — タスクリストと `blocked-by` が食い違い、`epic:next` が `error` を返す

   | 答え                                                                                                                                                                                                                                                                                                                                                                | すること                                                                                                                                                                                                                    | Tier             |
   | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
   | `add_to_epic`                                                                                                                                                                                                                                                                                                                                                       | `pnpm josh epic --add <E> <新規>`（順序があるなら `--before <M>` / `--after <M>`）                                                                                                                                          | **A — 確認不要** |
   | `create_epic`                                                                                                                                                                                                                                                                                                                                                       | `pnpm josh epic "<title>" <新規> <相手> [--ordered]`                                                                                                                                                                        | **A — 確認不要** |
   | `ask`（候補が複数の EPIC に散っている）                                                                                                                                                                                                                                                                                                                             | 停止して尋ねる。epic 同士の統合だけが取り消せないため。**`epicrun` 中はバッチを止めず、その子に `needs-decision` を付けて park する**                                                                                       | **B**            |
   | `none`                                                                                                                                                                                                                                                                                                                                                              | 何もしない                                                                                                                                                                                                                  | —                |
   | **コマンドが答えられなかった** — 非ゼロ終了、または `Nothing to bundle.` の上に出た**あらゆる** ⚠ 警告（一覧の打ち切り、関係を読めなかった Issue）。記録済みの依存は 2 つある強い信号の片方なので、関係の読み取り失敗は本来の `add_to_epic` を `none` に化けさせる。断定的な答え（`Already in an epic` / `Add it to the epic …`）は警告が併記されていても有効である | 何と言ったかを添えて停止・報告する。**警告の後の `none` は「束ねる相手が無い」ではない** — 探索が不完全なのであり、答えとして読むと本規則が塞ごうとしている経路そのもので Issue が EPIC 無しになる（joshuafolkken/kit#950） | —                |

**`none` は正当な答えである。** コミット前セルフレビューをワークフローの外で回した場合、現在の Issue が存在せず参照先が無いため候補は出ない。そのときは束ねずにバックログへ残す — 手順が求めるのは「コマンドを実行して答えに従うこと」であって、必ず EPIC に入れることではない。

**逆に、実行せずに起票だけで終えると、指摘は落ちるのではなく永久に park される。** `epic:next` が返すのは EPIC のタスクリストにある子だけなので、どの EPIC にも属さない Issue は実行中の `epicrun` に一度も渡らない（拾うには番号を知っている人が要る）。バックログから見れば「落ちた」のと区別が付かない。

実測である。joshuafolkken/kit#943 は 2 回目のレビューから切り出され、本文に `親: joshuafolkken/kit#891` と明記していながら、どの EPIC の子にもなっていなかった。親 #891 が閉じたのはその 3 分後である。同じ経路でも手順が実行された joshuafolkken/kit#911 では `epic:bundle` が EPIC を名指しし、そのまま追加されている。**差は、コマンドを打ったかどうかだけだった**（joshuafolkken/kit#946）。

なお **#943 の取りこぼしには 2 層目の原因もある** — 起票が親の close より後になると、`epic:bundle` の候補探索が open Issue しか読まないため恒久的に `Nothing to bundle.` を返す。そちらは joshuafolkken/kit#947 が扱う。本節が直すのは「手順が守られなかった」側だけである。

### 強い信号だけを根拠にする

- 本文の相互参照（新規 Issue が既存を参照している、または既存が新規を参照している）
- 既存の `blocked-by` 関係

**タイトル・本文の内容的な類似は、それだけでは束ねる根拠にしない。** 「関連している」は際限なく広がるため、閾値を持たないと無関係な Issue まで巻き込む。類似は AI の判断を補強する材料に留める。

**候補探索は open backlog に限らない。** 対象 Issue の本文が名指ししている番号は、状態を問わず 1 件ずつ読む。open 限定のままだと、後追い Issue が起票されてから親が close するまでの数分間しか正しく答えられない（joshuafolkken/kit#943 では約 3 分。過ぎると `Nothing to bundle.` を exit 0 で返し、「読めなかった」ではなく「無かった」と断定していた）。

- **closed の参照先は、open な EPIC が既に追跡している場合にのみ候補にする。** 回収したい答えは `add_to_epic` である。閉じた Issue を子に持つ新規 EPIC は実行するものが残っていない
- **open の参照先は無条件に候補にする。** 一覧に出てこなかったのは一覧が打ち切られたからであって、無関係だからではない
- 追加読み取りは参照 1 件につき 1 リクエストで、件数に上限があり、関係の読み取りと同じ形でバッチ化される。**読み取りの失敗も、上限で読まなかった参照も、欠落として報告し「強い信号なし」に畳み込まない** — 黙って打ち切る guard は、「見るのをやめた」を「関係が無かった」と言い換える元の欠陥そのものである
- **番号が pull request だった場合は候補にしない。** REST の issue エンドポイントは PR にも答え、マージ済み PR の state は `CLOSED` ではないため、この判定が無いと「修正は #952 で入った」という散文が PR を新規 EPIC の子に混ぜる
- **実在しない番号は欠落として報告しない。** 打ち間違いや他リポジトリの番号のように GitHub が何にも解決できない参照は、候補にも欠落にも入れず黙って捨てる。これを欠落として報告すると、散文中の `#N` が 1 つ狂っただけで `⚠ Could not read #N.` が verdict の上に出て、上の「打ち切り警告の後の `Nothing to bundle.` は答えではない」規則により**無人実行が停止する** — 存在したことのない参照のために人を呼ぶことになる（joshuafolkken/kit#957）
- **その判別は `gh` のエラー文言ではなく HTTP ステータスコードで行う。** 実在しない番号は REST で **404**、レート制限は **403 / 429** である。GitHub は権限の無い Issue にも存在を漏らさないため 403 ではなく 404 を返すので両者はステータスからは原理的に区別できないが、このコマンドは **直前に open 一覧を取得したのと同じリポジトリ**を叩くため、そこで見えない番号は存在しない番号である。`gh api` の失敗はステータスコードではなく stderr の文言として届くため、**読み取りが失敗したときにだけ** REST を 1 回叩いて分類する。成功経路と、この区別を必要としない呼び出し元には追加リクエストは発生しない — バックログの関係読み取りは最大 200 件あり、レート制限で全滅したときにさらに 200 リクエストを撃つことになるためである。分類する経路は参照の上限（20 件）で抑えられている
- 追うのは対象 Issue 自身の本文だけである。逆方向（閉じた Issue が対象を名指しする）は closed 全件走査になり、かつ不要である — 後追い Issue が親を名指しするのは起票手順そのものだからである

候補探索の解析は `josh epic:audit` の「暗黙の依存」検査と**同一の実装を共有する**。あちらは epic 内に閉じた解析、こちらはバックログ全体への適用というだけで、読む対象は同じ「本文中の Issue 参照」である。同じ解析を 2 回書かない。

### 決定木（「常に新規 epic を作る」ではない）

Issue は 1 つの epic にしか属せない（タスクリストで追跡されるため）。したがって分岐が要る。

| 状況                                                                 | 動作                                                                                   | Tier              |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------- |
| **新規 Issue 自身が既に epic の子**                                  | 何もしない。Issue は 1 つの epic にしか属せず、epic 間の移動はこのルールの担当ではない | —                 |
| 関連候補が**既に epic の子**                                         | **その epic に追加**する（新規 epic を作らない）                                       | A                 |
| 候補が**複数の異なる epic** に散っている                             | 束ねない。epic の統合は影響が大きい                                                    | **B（人に聞く）** |
| どの epic にも属さない候補があり、新規 Issue と合わせて **2 件以上** | **新規 epic を作って束ねる**                                                           | A                 |
| 強い信号を持つ候補が無い                                             | 何もしない                                                                             | —                 |

束ねるのは可逆（epic は編集でき、子は外せる）なので Tier A で確認を挟まない。**epic の統合だけは影響範囲が大きいため Tier B とする。**

### 束ねたら順序も記録する

関連が順序を含む場合、`blocked-by` を付与し、epic 本文の `Dependencies` にも矢印記法で書く。既存 epic への追加時も同じ。**順序を記録しないと、束ねた事実だけが残って束ねた理由が消える。** ただし**誰も宣言していない順序をここで捏造しない** — 既に宣言されている関係だけを引き継ぐ。

### 規模

実測で open Issue は十数件であり、全件を舐めても一瞬なので**索引やキャッシュは用意しない**。件数が問題になってから考える。
