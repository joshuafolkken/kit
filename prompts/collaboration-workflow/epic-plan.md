## `josh epic:plan` — EPIC の判断を計画段階に前倒しする

EPIC を実装している最中に判断が必要になるたび、AI は人に確認して停止する。**停止の中身の多くは、実装を始める前でも同じように答えられる**ものであり、後出しになっているだけで本質的に中断が必要なわけではない。判断の発生タイミングが散らばるために人はランの間じゅう待機を強いられ、同じ論点が子 Issue ごとに複数回聞かれることもあり、決めた内容は会話の中にしか残らない。

`pnpm josh epic:plan <E>`（エイリアス `el`）は EPIC の全子 Issue の番号・タイトル・本文・ラベル・`blockedBy`・状態を 1 つの JSON として出力する。AI はそれを 1 度に読み、判断を仕分ける。

### 相分け

```
[相 0 整合監査]  josh epic:audit で子 Issue 群の矛盾を検出 → Tier A で修正して記録
[相 1 トリアージ] josh epic:plan の出力を読む → auto / ask / defer に分類
[相 2 一括決定]   ask を 1 回にまとめて確認 → ## Decisions と各子 Issue に記録
[相 3 無人実行]   epicrun が最後まで走る
```

### 相 0 の整合監査は省略できない

**矛盾を抱えた計画に対して一括決定を行っても、決定ごと作り直しになる。** `josh epic:audit` を相 1 の前に必ず実行し、循環依存・順序矛盾・暗黙の依存・孤立した子を洗い出す。**検出した矛盾は Tier A として人に確認せず修正し、根拠を Issue に記録する。** 人の判断が要る矛盾だけを相 2 の `ask` に合流させる。

人が「バグを探して」と指示して初めて矛盾が見つかる状態では、無人実行の前提が成り立たない。相 0 はそのための工程であり、省略可能な確認ではない。

### 相 1 のトリアージ

| 分類    | 中身                                         | 扱い                      |
| ------- | -------------------------------------------- | ------------------------- |
| `auto`  | Tier A — 明らかに優れた選択肢がある          | 決めて実装時に記録する    |
| `ask`   | Tier B / Tier C — 拮抗している、または不可逆 | 相 2 に集める             |
| `defer` | この EPIC の範囲外                           | 後続 Issue として起票する |

### 相 2 は EPIC 全体で 1 回

`ask` を **EPIC 全体で 1 回の質問** にまとめて提示する。子 Issue ごとに聞くと同じ論点が複数回飛び、人の関与を減らすという目的に逆行する。

回答は **EPIC 本文の `## Decisions` 節と、該当する各子 Issue のコメントの両方** に記録する。片方だけでは後から辿れない — EPIC だけに書くと子 Issue を読む人が根拠を見つけられず、子 Issue だけに書くと EPIC 全体の判断がどこにも残らない。

#### `## Decisions` の書式

```md
## Decisions

### <決めた論点の要約>

- 対象: #101, #102
- 採用: <選んだ案>
- 却下: <却下した案>
- 理由: <なぜ採用案が優れているか>
- 決定日: <YYYY-MM-DD>
```

### 決定を記録したら park を解除する

`## Decisions` に決定を書いた時点で、対応する子 Issue の `needs-decision` ラベルを外す（Tier A、確認不要）。**これが無いと、判断が返ったのに子が永久に止まる。** ラベルの解除規則そのものは「`epicrun` — EPIC 配下の子 Issue を無人で実行する」が定義する。
