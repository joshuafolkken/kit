## `epicrun` — EPIC 配下の子 Issue を無人で実行する

`epicrun #<E>`（別リポジトリの EPIC を参照する場合は `epicrun owner/repo#<E>`）は、EPIC の子 Issue を人が張り付かずに完走させるためのワークフローキーワードである。実行手順の正典は本節であり、運用手順は `.claude/skills/workflow-commands/epicrun.md` に置く。両者は一致していなければならない。

`queue` との違いはひとつだけである。`queue` は 1 件ごとに人の明示起動を安全弁にしており、実装中に判断が必要になればセッション全体が停止する。停止のタイミングが予測できないため、人はランの間じゅう張り付く必要がある。`epicrun` は**判断が必要になった子 Issue だけを脇に置いて他の子へ進む**。

### EPIC でない Issue も受け取る

`epicrun` は EPIC だけでなく、**タスクリストを持たない普通の Issue も受け取る。** `epicrun #<N>` は `#<N>` を `fullrun` として実行し——計画・検証ゲート・PR・マージまで同じ——それで終わる。

違いは**人がいつ関与するか**である。`epicrun` を先に打つことは、まだ何も分かっていない段階でバッチの承認を 1 回与えることであり、`fullrun` は 1 件の承認なので、分割を検出したら停止してバッチの承認を求め直すしかない。人の操作はどちらも 1 回で、この入口はそれを**最初に**使うだけである。複数件になると見込まれている作業には、こちらの方が短い。

そのため `epicrun #<N>` の実行中に前提 Issue または分割が判明しても、**停止しない**。

1. 新規 Issue を起票する（確認しない。バッチの承認はキーワードの時点で与えられている）
2. **作業中の変更を stash し、`#<N>` から `in-progress` を外す。** 「実行中に前提 Issue が判明した場合」の手順 2 と 4 とまったく同じで、`-u` 付きの `git stash push -u -m "..."`（新規の `*.test.ts` は untracked である）、stash の存在を伝える `gh issue comment <N>`、`gh issue edit <N> --remove-label "in-progress"` の 3 つとも要る。理由も同じで、作業ツリーは既定ブランチで汚れており次の子は `git switch main && git pull` から始まること、`epic:next` が `in-progress` の付いた子を blocker を見る前に「時間で解ける」と分類するため `#<N>` が二度と候補にならず EPIC が詰まること、の 2 点である。**経路が新しいだけで、要る手当ては変わらず、どれも省略できない**
3. **作る前に `pnpm josh epic:bundle <N>` で、既に `#<N>` を追跡している EPIC が無いかを確かめる。** どの EPIC かを名乗る（`#893 already tracks this issue`）。`epicrun` に渡された素の Issue が、既に誰かの EPIC の子であることはありうる——`#893` の子である `#943` に対して `epicrun #943` と打つことを止めるものは無い——そこで 2 つ目の EPIC を作ると、どちらの自動クローズも他方を知らないまま動く。しかも**人が見ていない入口で**起きる。

   | 答え                                                                                                                                                     | すること                                                                                                                                                              |
   | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | EPIC `#<E>` が既に `#<N>` を追跡している                                                                                                                 | 前提なら `pnpm josh epic --add <E> <P> --before <N>`、分割なら `--add <E> <N1> ...`。**2 つ目の EPIC を作らない。** `#<E>` に対してループを続ける                     |
   | どの EPIC も追跡していない                                                                                                                               | 新規作成する（コマンドは下表）                                                                                                                                        |
   | **コマンドが答えられなかった** — 非ゼロ終了、または `Nothing to bundle.` の上に出た一覧打ち切りの ⚠ 警告。断定的な答えは警告が併記されていても有効である | `#<N>` を `needs-decision` で park して報告する。「判定できなかった」は「どの EPIC も追跡していない」ではなく、そう読むとこの手順が防ごうとしている二重追跡が再発する |

   新規作成する場合、`#<N>` は実装中の成果物そのものなので、この経路は常に「昇格せず子として残す」側に落ちる——分割判定の昇格・新規の分岐を、その都度選ぶわけではない。**どのコマンドを使うかは、何が見つかったかで決まる。** `--ordered` は引数の順序をそのまま依存の鎖にするためである。

   | 見つかったもの     | コマンド                                                                                                                                                |
   | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | 前提 Issue `<P>`   | `pnpm josh epic "<title>" <P> <N> --ordered` — 前提を**先**に書く。逆に書くと `blocked-by` が逆向きに記録され、必要としている方を先に実装することになる |
   | 順序を持たない分割 | `pnpm josh epic "<title>" <N> <N1> ...` — **`--ordered` を付けない。** 付けると順序の無い子が直列化され、誰も宣言していない `blocked-by` が記録される   |
   | 順序を持つ分割     | `pnpm josh epic "<title>" ... --ordered`。引数はその順序で書く                                                                                          |

4. **ここで `pnpm josh epic:audit <E>` を走らせる。** 監査は EPIC から始まるランを前提に書かれており、この経路では手順 3 まで EPIC が存在しない。`epic:audit` は `epic:next` と同様にタスクリストの無い Issue を拒否するため、素の `#<N>` に対して走らせるとランは最初の一歩で止まる。この入口の目的と正反対になる
5. **停止せず**、新しい EPIC `#<E>` に対してそのままループへ移行する

**何も出てこなければ EPIC は作らない。** `#<N>` が前提も分割も出さずにマージまで到達したら、そこでランは終わる。EPIC を作るのは、入れる 2 件目が実在するときだけである。子が 1 件だけの EPIC は自動クローズが閉じられない置き土産になる。

**ガードはこの経路でも変わらず適用される** — 子 30 件 / 自動起票 10 件 / 連続失敗 3 回。これらは EPIC の制限ではなくランの制限であり、この入口が確認を 1 つ外せるのは、外した後に残るのがガードだからである。

**`josh epic:next` はこの変更の影響を受けない。** タスクリストを持たない Issue は従来どおり拒否し、`#<N> tracks no children in a task list.` を出力する。単独 Issue を受け入れるのは `epicrun` 側の判断であり、その時点ではまだ EPIC が存在しないので `epic:next` に問い合わせること自体が無い。

### 1 回の起動が承認する範囲

**`epicrun` を 1 回打つことが、その EPIC 配下の N 件のマージ・複数リポジトリへの push・実行中の Issue 自動作成をまとめて承認する。** これがキーワードの存在理由であり、毎ターンの再承認を求める `queue` との差である。

EPIC の外側は承認しない。**例外は `auto-ok` で人がオプトインした Issue だけ**であり、そのラベルを付ける行為はランではなく人のものである点が、これを自己承認ではなく承認の拡張に留めている（→「EPIC の外側 — `auto-ok` でオプトインされた Issue」）。Tier C の行動は従来どおり停止する — ただし停止するのはその子 Issue だけである。

### 子 1 件は隔離された実行単位へ委譲する

`epicrun` の子は、親のループと同じ文脈では実行しない。**子 1 件を隔離された実行単位へ渡し、親のループへは要約だけを返す**（joshuafolkken/kit#984）。

理由は実測である。子 7 件を 1 文脈で回したランでは、文脈の大きさが最初の 20 リクエストで平均 99,789、最後の 20 で 698,928 だった。同じ 490 リクエストを 50 リクエスト（≒ 子 1 件）ごとに区切った場合の課金入力は実測の 33% に収まる。**k 番目の子は、それ以前の k-1 件の残骸を毎ターン読み直している。**

**委譲の機構は新設しない。** joshuafolkken/kit#969 が定めた機構（列挙 ＋ `pnpm josh delegate`）をそのまま使い、単位だけが「ランの 1 工程」から「epic の子 1 件」へ変わる。別に作れば `CLAUDE.md` の「No clones — single-source」が禁じているクローンになる。可否は判断ではなくコマンドが答える:

```bash
pnpm josh delegate epic-child   # → delegate
```

**親が読むのは要約ではなく GitHub の状態である。** これが `epic-child` の検証経路であり、委譲が成立する条件そのものである。実行単位が「終わった」と返しても PR がマージされていなければ、その子は `CLOSED` になっていない。子自身の検証ゲート・`/code-review`・CI は実行単位の中で走り、`pnpm josh followup --merge` はそれらが緑でなければ PR に触れない。**要約を信じて次へ進む形にしてはならない** — それは検証経路を捨てることであり、捨てた時点で `epic-child` は委譲してよい単位ではなくなる。

**確認は `epic:next` の次の答えではなく、子の状態を直接読む。** 終わらなかった子は `in-progress` を付けたままであり、`epic:next` はそれをブロッカーより先に「時間で解ける」と分類するため、番号ではなく `wait` を返す。それを検証だと思い込んだループは、失敗を学ぶ代わりに 90 分の stale 判定までポーリングする。**実行単位が返った直後に `gh issue view <N> --json state,labels` を読む。**

**`CLOSED` 以外を一括りに失敗としない。** 見分けるのはラベルである。

- **open ＋ `needs-decision`** — 実行単位が park した。これは失敗ではない。ラベルはそのまま残し、**連続失敗のガードには数えず**、次の子へ進む。park が 3 回続くのは普通の epic であり、数えれば環境障害として打ち切ってしまう
- **open ＋ `needs-decision` 無し** — 失敗である。`in-progress` を親が外し（Tier A）、連続失敗のガードに数え、**その子を park する**。ガードの表が定める「連続していない失敗はその子を park してランを続ける」は委譲した子にも同じく適用される。park しなければ次の `epic:next` が同じ子を返し、間に成功が挟まるたびにカウンタが戻るため、上限なく再試行され続ける

**`git switch main && git pull` は委譲した場合も親側でもう一度走らせる。** 実行単位の中でマージされた結果は親のチェックアウトには入っていないため、省くと次の子が古い main の上で始まる。

**マージ権限は実行単位まで及ぶ。** 人が `epicrun` を打った時点で与えたバッチの承認は、子を実行する単位にも及ぶものとして扱う（joshuafolkken/kit#986 の `## Decisions`）。委譲しても承認の範囲は変わらない。変わるのは、その承認がどの文脈で使われるかだけである。

**明示起動の要求も同じ経路で及び、それを運ぶのは指示文である。** `CLAUDE.md` の「Explicit invocation required」は、打たれていない `fullrun` 相当のランを始めることを禁じている。指し示す先を持たない実行単位はこれに従って拒否し、子を open のまま返し、失敗として計上される。この規則が禁じているのは**依頼の形からワークフローを推測すること**であって、キーワードの打鍵が実行単位自身の履歴に現れることを要求してはいない。したがって**指示文に、それが由来する起動を明記する** — `epicrun #<E>`、子の番号、そしてその承認の下で `fullrun #<N>` として実行すること。そう書けば推測の余地は無く、規則が求めているのはそこまでである。**書き落とした指示文の側が欠陥**であり、そのとき実行単位は推測しており、拒否こそ正しい答えである。

**委譲できない環境では親の文脈で実行する。** 隔離された実行単位を持たない環境では子を親の文脈で走らせてよく、そのときに効くのが下記の区切り（hand-off）である。**区切りは委譲の代替ではなく、委譲が効かない場合の保険である。**

### 並行度モデル — repo あたり同時 1 件、repo 間は並行

実行状態を GitHub 側にのみ置く設計（`josh epic:next`）の帰結として、**`epicrun` は 1 セッションである必要がない**。リポジトリごとにセッションを立て、各セッションが同じ EPIC に対して `josh epic:next <E> --repo <owner/repo>` を呼び、自分のリポジトリの子だけを取って走る。

**別リポジトリの子は `gh --repo` 経由で読む。** 状態を知るためにクローンは要らず、実装するときだけ要る。`epic:next` は joshuafolkken/kit#869 のマップから各リポジトリのローカルチェックアウトを併記し、ここにチェックアウトが無いリポジトリはその旨を出すだけでクローンはしない。別リポジトリの EPIC を参照する形は `epicrun owner/repo#E` である（joshuafolkken/kit#864）。

**リポジトリをまたぐ依存は、ブロッカーの Issue が閉じただけでは満たされない。** kit の Issue をマージしても kit は publish されないため、その瞬間に「開始してよい」と言われた消費側の子は 1 つ前のリリースを入れるか、そのまま失敗する。この依存が解けるのはブロッカーが閉じ、**かつ**そのリリースがレジストリに現れたときであり、ブロッカーが open のうちはレジストリを見に行かないので、ランが開始直後から publish 待ちで座り込むことはない。

**排他はリポジトリ単位であり、それを適用するのは `epic:next` である。** `josh epic:next --repo <owner/repo>` は、返すべき子がある場合にまずそのリポジトリで何かが走っていないかを尋ね、**park されていない `in-progress` の open Issue が 1 件でもあれば** `wait` を返す — **どの epic に属するかを問わず**、その EPIC が追跡していない Issue であっても同じである（joshuafolkken/kit#925）。2 つの限定は穴ではなく定義の一部である。第一に、尋ねるのは**候補があるときだけ**であり、`stop` と `complete` は何かが走っていてもそのまま返る（どちらもこれから作業を始める答えではない）。第二に、**park された Issue はリポジトリを押さえない** — ここでも分類と同じく `needs-decision` が `in-progress` に優先する。さもなければ `park and continue` が、いま脇に置いたばかりの子にリポジトリを渡してしまう。

**これは advisory であり、アトミックではない。** ラベルを付けるのはこの読み取りの**後**に子の実装へ入る者であるため、完全に同時に起動した 2 セッションは双方が idle を読み、同じ子を渡されうる。このチェックが閉じるのは実際に起きる方の窓である — 子を実行中のセッションはその間ずっとラベルを保持し、そちらは分単位、取り合いは秒単位である。不変条件を機構に変えるガードとして扱うこと。mutex ではない。

**粒度は epic ではなく資源に合わせてある。** 2 つの子が奪い合うのは 1 つの作業ツリー・1 本の `main`・`josh bump` が書き換える 1 つの `package.json` であって、いずれも「どの epic の子か」を区別しない。従来ここに書かれていた論証 — 各セッションは自分のリポジトリの子だけを取り、同一リポジトリ内は 1 件ずつである — は**1 つの epic の中でのみ真**であり、2 つの epic については何も言っていなかった。`epic-classify.ts` はその epic の子だけをラベルで分類するため、同じチェックアウトで 2 つ目の `epicrun` を起動すると双方が「自分の epic に in-progress は無い」と答え、両方が走る。実際に直列化していたのは、人がランを順に打つ習慣であって、モデルの性質ではなかった。

**放置されたラベルは今やリポジトリ全体を押さえるため、stale 規則の対象はその EPIC の子を超える。** 中断したランは `in-progress` を残し、そのラベルは子 1 件ではなくチェックアウト全体を押さえる。したがって後述の「`in-progress` は stale を見つけた者が外す」は、**その EPIC の子に限らず、そのリポジトリの open Issue すべてに適用される**。`epic:next` が押さえている Issue を標準エラーに列挙するのはそのためであり、待ち時間は 90 分の stale 窓が上限を与える。

**読めなかった listing は「動いていない」ではない。** その場合 `epic:next` は子を返さず `wait` を返す。読めなかったものを「何も走っていない」と読むことは、この種のガードが唯一許されない向きの失敗である — その答えは作業を**開始させる**からである。かといってエラーでもない: listing は一過性のレート制限も同じ失敗に畳み込むため、exit すると無人ランが一瞬の不調で終わる。恒久的な失敗はこの読み取りより前に「子が読めない」異常として捕まる。したがってループはポーリングを続け、理由は標準エラーに出る。

**同一リポジトリ内で 2 件を同時に走らせてよくなったわけではない。** このガードはその禁止を慣習から機構に変えただけであり、同一リポジトリ内の並行を安全にするものではない。**それを扱う後続 EPIC は、このガードを止めるのではなく置き換える必要がある** — worktree と、子ごとに単独で書き換えられる manifest で。本節を「並行実行に調整は要らない」と読んではならない。調整は存在し、それがこれである。

同一リポジトリ内の並行を本 EPIC の範囲外とする理由は、`josh bump minor` が同じ `package.json` を書き換えること、1 つのチェックアウトが worktree なしに 2 ブランチを保持できないこと、同じファイルを触る子に衝突予測が要ること、の 3 つである。**いずれもリポジトリを共有していることに固有の理由**であり、リポジトリが別なら manifest が別ファイルで、チェックアウトが既に分かれており、ファイルを共有せず、Actions もマージキューもリポジトリごとに独立しているため、ひとつも当てはまらない。したがって repo 間の並行は本 EPIC の範囲に含める。

並行で速くなるのは依存が無い子だけである。app-kit の子が kit の新機能を必要とするなら `blocked-by` に宣言され、`epic:next` が正しく待たせる。これは並行実行の限界ではなく依存関係そのものである。

### `josh latest` はセッションごとに 1 回だけ — 子ごとには走らせない

`josh latest` は**セッションの手続きであって、子の手続きではない**。`josh epic:next` が最初に子の番号を返した時点で、その子の実装に入る前に 1 回だけ実行し、以後は二度と実行しない。作業ツリーに変更があれば `git stash` で退避してから `git switch main && git pull` に続けて `pnpm josh latest` を実行し、`git stash pop` で戻す（`queue` の手順 1 と同じ、明文化された退避である）。そのあと `dependency-update` skill の手順に従って `pnpm-workspace.yaml` と `package.json` の双方の overrides と `devEngines` を確認する。

**「ラン」ではなく「セッション」である。** EPIC が複数リポジトリにまたがる場合、セッションはリポジトリごとに立ち、それぞれが自分のチェックアウトを更新する。「ラン全体で 1 回」と読んで 2 つ目のセッションが省略すると、そのリポジトリの子は古い依存のままマージされ、`pnpm audit` も走らない。

**子の番号を受け取るまで待つことが、作業ツリーを汚さない条件である。** 最初の `epic:next` より前に実行すると、最初の答えが `wait` / `stop` / `complete` だったラン（再開時には普通に起こる）で、書き換えられた `pnpm-lock.yaml` がコミットされないままデフォルトブランチに残り、次の `git pull` がそこで失敗する。

子の実体は `fullrun #<N>` であり、`fullrun` は実装前に `josh latest` を要求する。したがって手順を字義どおりに辿ると子の件数だけ実行されるが、本節がそれを上書きする。理由は所要時間ではなく**差分の汚染**である。実行のたびに `pnpm-lock.yaml` が書き換わるため、各子の PR にその子と無関係な依存更新が混入する。`/code-review` と CodeRabbit はその差分を読むことになり、依存更新に起因する CI 失敗はその子の失敗として扱われ、**無人実行では持っていない欠陥を理由に子が park される**。加えて `.github/workflows/ci.yml` の eslint キャッシュキーは `hashFiles('pnpm-lock.yaml')` を含むため、毎 PR でキャッシュが失効する。

**書き換えられた lock ファイルは最初の子と一緒に入る。** `josh latest` は `pnpm-lock.yaml` を変更したまま残し、最初の子の `pnpm josh git -y` がそれをコミットする。したがってその 1 件の PR は依存更新を含む — `queue` の最初の Issue とまったく同じである。巻き上げが消すのは残る N-1 件の分であって、最初の子の差分がきれいになるわけではない。最初の子が自分の変更ではなく依存更新で CI に落ちた場合は、それは 1 回だけ現れる依存の問題であり、その子を park する前に fix-forward で解決する。

**`git switch main && git pull` は子ごとに残す。** これは巻き上げの対象ではない。直前の子のマージを作業ツリーに取り込むのはこの 2 つであり、省くと子が古い main の上で実装を始める。ランへ移すのは依存更新だけである。

これは `queue` が既に定めている規則と同一である（`queue` の手順 1 — `josh latest` は最初の Issue の前に 1 回、必須、省略不可）。同じ形の直列バッチに対して 2 つの入口が異なる規則を持っていた食い違いは、これで解消される（joshuafolkken/kit#913）。

**中断から再開した `epicrun` は、新しいセッションとして扱う。** 最初の子に入る前に 1 回実行する。残りの子を決める状態は GitHub 側にあり、再開したセッションが見つける作業ツリーは何日も古いことがあるためである。

### park and continue — 判断が要る子は脇に置いて先へ進む

実行中に、そのランが決めてよい範囲を超える事柄（Tier B の拮抗した選択、Tier C の行動、上流起因の欠陥、人の判断を要する分割）が生じたら、**その子 Issue に `needs-decision` ラベルを付けて中断し、依存していない他の子へ進む**。

**park はセッション停止の置き換えであって、停止を生んだルールの置き換えではない。** 上流の欠陥は従来どおり即座・無条件に起票し（first-party なら Tier A）、回避策を書くことは引き続き禁止である。変わるのは停止の及ぶ範囲だけで、その子は待ち、ランは続く。

**`in-progress` はそのままでよい。** park された子は上のリポジトリ単位の排他において**リポジトリを押さえない** — `epic:next` は分類と同じく `needs-decision` を `in-progress` より優先するため、次の子は通常どおり返る。

**park の解除は Tier A（確認不要）。** 決定が EPIC の `## Decisions` に記録された時点で AI がラベルを外し、`epicrun` を再実行すれば続きから走る。これが human-in-the-loop の後半であり、これが無いと park した子は永久に止まる。

### `in-progress` の解除は、stale を検知したセッションが行う

`in-progress` を外す処理はコードベースに存在しない。正常終了なら Issue が閉じるので無害だったが、中断したランの子には付いたまま残り、その子は以後すべての `epic:next` の候補から永久に外れる。**stale を検知したセッションが自分でラベルを外し（Tier A）、報告してからループを続ける。**

**代償はその子 1 件では済まなくなった。** 上のリポジトリ単位の排他により、`in-progress` を持つ open Issue は `epic:next --repo` に**リポジトリ全体**の `wait` を返させる。したがって放置されたラベル 1 枚が、そのチェックアウトに関わるすべての epic を止める — その EPIC が追跡していない Issue であっても同じである。**この規則はその EPIC の子に限らず、そのリポジトリの open Issue すべてに適用される。** `epic:next` は押さえている Issue を標準エラーに列挙するので、見に行く先はそこから分かる。**判断材料は経過時間だけではない。** 90 分の窓と照らすと同時に、何が押さえているのかを見ること — 90 分を超えて正当に保持される状態が 2 つある。手動確認のために停止した `halfrun` と、子の途中で中断したランである。いずれもチェックアウトに未コミットの作業を残すため、決め手はそのチェックアウトの `git status` である。作業ツリーが汚れていれば保持は正当であり、正しい対応はラベルを外さず報告することであって、その作業の上に 2 件目の子を走らせることではない。

### 待機と終了の判定 — ラベルではなく「人の入力なしに解けるか」

| `josh epic:next` の分類                           | `epicrun` の挙動                                 |
| ------------------------------------------------- | ------------------------------------------------ |
| 着手可能あり                                      | 実行する                                         |
| 着手可能ゼロ・時間で解ける子あり                  | **待機する**                                     |
| 着手可能ゼロ・時間で解ける子なし・open な子が残る | **終了して報告する**（人が要る子の一覧を添える） |
| open な子が無い                                   | `auto-ok` の Issue を拾ってから終了する          |

ラベルで判定してはならない理由は具体的である。kit の子が closed になり app-kit の子が公開待ちで止まっている瞬間は、着手可能ゼロ・`in-progress` ゼロ・`needs-decision` ゼロになる。ラベルを見る判定では終了と誤り、**待つべき場面で終了する**。

### 待機の実体（無限待ちにしない具体値）

| 設定                        | 値     | 理由                                                                  |
| --------------------------- | ------ | --------------------------------------------------------------------- |
| ポーリング間隔              | 60 秒  | 子 1 件の `fullrun` は分単位。これより短くしても API 消費が増えるだけ |
| `in-progress` の stale 判定 | 90 分  | 子 1 件の実測所要を超える。これを過ぎたら相手セッションは落ちている   |
| 公開待ちのタイムアウト      | 10 分  | `josh propagate` と同じ budget。publish が失敗すれば永久に出ない      |
| ラン全体のタイムアウト      | 8 時間 | 一晩で終わらない無人ランは、追加の待機ではなく人を必要としている      |

**いずれも打ち切って報告する** — 無限にリトライするものは一つも無い。stale と判定した子はラベルを外してから次のポーリングへ進む。循環依存による詰みは `epic:next` が検出してエラーにするため、`epicrun` は待機を打ち切って報告する側に徹する。

### 実行中に分割が必要と分かった場合

子 Issue を新規に起票し、`pnpm josh epic --add <E> <N...>` で EPIC のタスクリストに追加して依存を記録する（first-party への起票は Tier A、確認不要）。本文を手で書き換えてはならない——宣言と `blocked-by` が食い違って `epic:next` が `error` を返し、無人実行がかえって止まる。分割の判定基準は `kickoff` の分割判定と同一の定義を使う。分割後の残りに人の判断が要るなら、元の子に `needs-decision` を付けて park し、他の子へ進む。**分割そのものを理由にセッション全体を止めない。**

**前提 Issue の発見はこれとは別の状況である。** 実行中の子はそのまま 1 件の成果物で、その前に別の成果物が要るだけなら分割ではない。「実行中に前提 Issue が判明した場合」の手順に従い、park せずに依存として記録して続ける。

### EPIC の外側 — `auto-ok` でオプトインされた Issue

EPIC のタスクリストはバックログの全体ではない。人の判断を要しない小さな Issue は、誰かが EPIC に入れない限りそこに滞留し続ける。実行力が上がるほど律速になるのは実行そのものではなく**入口**（何が実行対象になりうるか）であり、`auto-ok` はその入口を広げるオプトインである（joshuafolkken/kit#906）。

**`auto-ok` を付けるのは人だけである。AI が自分の判断で付けてはならない。** `epicrun #<E>` が承認するのは `#<E>` の中のマージであってその外側ではなく（→「1 回の起動が承認する範囲」）、このラベルは人がその承認を EPIC の外へ広げる唯一の手段である。AI が自分で付けられるラベルは、無人ランが自分の承認範囲を自分で広げられるということであり、それはガードではない。`fullrun` が分割を検出したときに停止するのは、まさにこの自己拡張を禁じているからである。**人の代わりに打鍵することは「AI が付ける」ことではない** — そのターンで明示的に指示された（「#912 に `auto-ok` を付けて」）なら、決定は人のものであり AI は実行するだけである。それ以外は、どれほど自明に見えても提案であり、Issue コメントとして書いて人に委ねる。

**拾い上げは EPIC の子を消化し終えた後だけに起こる。**

| `epic:next` の答え | 拾い上げ                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| 番号               | その子を実行する。拾い上げは行わない — EPIC の子が先である                                         |
| `wait`             | 待機する。拾い上げは行わない。EPIC はまだ解決中であり、外側の作業は承認済みバッチを追い越す        |
| `stop`             | park した子を報告して終了する。**拾い上げは行わない** — 人を要する状態を無関係な作業で埋没させない |
| `error`            | 報告して終了する。拾い上げは行わない                                                               |
| `complete`         | EPIC の完了サマリを送ってから、下の手順で拾い上げる                                                |

EPIC でない素の Issue から始まったランも、前提や分割が出ないままマージに到達した時点（→「起こらなければ EPIC は作らない」）で同じ地点に立つ。承認された作業が終わっているので、そこでも拾い上げる。**1 つのキーワードが 2 通りの意味を持ってはならない。**

**どの Issue かはコマンドに聞く。`gh` を自分で組み立ててはならない。** ラベル名の単一ソースは `scripts/git/issue-labels.ts` であり、`gh` のクエリに文字列を書き写すことは、何も検査しない場所に 2 つ目の定義を置くことである。

```bash
answer=$(pnpm josh auto-ok:next)                 # 1 件目
answer=$(pnpm josh auto-ok:next --exclude <N>)   # 2 件目以降。直前にマージした番号を渡す
answer=$(pnpm josh auto-ok:next --exclude <N>,<M>) # そのセッションで既に走らせた番号をすべて渡してもよい
```

**2 件目以降で `--exclude` を省略してはならない。** GitHub の `closes #N` は非同期に適用されるため、マージ直後の数秒間、いま終えたばかりの Issue はまだ open として列挙される。渡さなければ同じ番号が返り、既に出荷した作業をもう一度実装しうる。`in-progress` ラベルが偶然それを除外することはあるが、そのラベルは stale を検知した側が外すものなので、頼ってよい保護ではない。

| 答え                            | すること                                                                                                                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 番号                            | `fullrun #<N>` と同じに実行する（委譲単位・検証ゲート・PR・マージ）。終わったらまた聞く                                                                                                        |
| `none`                          | オプトインされた Issue は無い。ランを終了する                                                                                                                                                  |
| **exit 1** — 一覧が読めなかった | 拾い上げを試みられなかったことを報告して終了する。「判別できなかった」は `none` ではない。ここで報告だけで足りるのは、誤りの向きが「作業を始めてしまう」ではなく「作業をしない」側だからである |

**前提が未解決の Issue は渡されない。** 拾い上げは `epic:next` が依存グラフを組み立てるのと同じ GitHub native の `blockedBy` を読み、閉じていない blocker を宣言している候補を除外する。`auto-ok` が言っているのは「この Issue に決定は要らない」であって順序については何も言っていないため、これが無いと無人ランが前提より先に着手しうる（joshuafolkken/kit#996）。

**順序は、直前に人が見せられたものと同じである。** `auto-ok:next` は、各ワークフロー完了時に表示される `🗒 Next issues (newest first)` とまったく同じ関数で並べる — 新しい順、`epic` / `in-progress` / `needs-decision` は除外。別の順序を持てば、その一覧が「次はこれ」と示した Issue とは違うものをランが始めることになる。

**ただし「同じ順序」であって「同じ集合」ではない。** 上の依存チェックは拾い上げ側にしか無いため、`🗒 Next issues` が先頭に出している Issue を `auto-ok:next` が拒むことがある。これは意図した差である — 人はその Issue が blocked だと見たうえで着手を判断できるが、無人ランにその判断は無い。

**子 Issue に適用されるものはすべて、拾い上げた Issue にも適用される** — 分割判定、二層の作業サマリ、`josh latest` のセッション単位へのくくり出し、park and continue、マージ直後の `pnpm josh cost --over 400000` による区切り判定。判断が要るものは子と同じく park し、ランは次を聞く。

**上限は 1 ラン 5 件**で、下のガード表に置く。これらの Issue はバッチとしての分割判定も `epic:audit` も依存グラフも通っていない。ラベルだけが承認のすべてであり、したがって構造的なガードはこの上限しか無いので、EPIC の子の 30 件より意図的に厳しくしてある。到達したら終了して報告する。続きが要るなら人がもう一度 `epicrun` を打つ。

**ラベルは、人が付ける前に存在していなければならない。** 自動で作られるものは無く、存在しないことはエラーでもない — `gh` は空の一覧を返し、`auto-ok:next` は `none` と答え、ランはこの節が無かったときとまったく同じに終わる。**オプトインが無いことが既定である。** 使うリポジトリで一度だけ作る。

```bash
gh label create "auto-ok" --color "0e8a16" --description "Opted in to unattended execution outside an epic"
```

### ガード（暴走の上限）

| ガード                    | 上限 | 到達時                                                              |
| ------------------------- | ---- | ------------------------------------------------------------------- |
| 1 ラン内の子の件数        | 30   | 停止して報告する。これより大きい EPIC は分割すべきである            |
| 1 ラン内の自動起票件数    | 10   | 停止して報告する。これを超えて起票するランは筋を見失っている        |
| 連続失敗                  | 3 回 | 停止して報告する。問題は子ではなく環境の側にある                    |
| 1 ラン内の `auto-ok` 件数 | 5 件 | 終了して報告する。EPIC は終わっており、残りは人が次に打つまで待てる |

連続していない失敗はその子を park してランを続ける。

### 通知と後処理の担当

複数セッションで走る場合、**EPIC の完了サマリを送るセッションと `josh propagate` を走らせるセッションは、EPIC を所有するリポジトリに立っているセッションの 1 つに定める。** `propagate` 自身も供給元リポジトリの外では実行を拒否するため、2 つの規則は一致する。他のセッションは、自分のリポジトリの子が無くなった時点で静かに終了する。

子ごとの completion 通知は従来どおり `pnpm josh followup --merge` が送る。これに加えて、ランの開始時に EPIC の開始通知を、終了時に「何をマージし、何を park し、何を起票したか」を含む完了サマリを送る。

### 停止条件

`epicrun` が止まってよいのは次の 6 つだけである。

1. `epic:next` が `complete` を返し、サマリを送信済みで、`auto-ok` の拾い上げが `none`・上限到達・一覧が読めなかったのいずれかを答えた
2. `epic:next` が `stop` を返した — 残る子はすべて人を要する。一覧を添えて報告する
3. `epic:next` が `error` を返した — 循環依存、または宣言と関係の食い違い
4. 上記ガードのいずれかに到達した
5. 上記タイムアウトのいずれかが経過した

**判断が必要になった子は、この一覧に含まれない。** park してランを続ける。6. **子のマージ直後に `pnpm josh cost --over 400000` が `over` と答えた** — ランは新しいセッションで続けた方が安い。park でも失敗でもなく、起票も stash も行わない。再開コマンドは報告に含める（→「The hand-off」）

### The hand-off — 1 セッションで epic 全体を回さなくてよい

**A session pays for every child it has already run, on every later turn.** What a turn costs is
decided by the accumulated preamble, not by what the turn does: measured across one `epicrun` that
ran six children in one context, the billed input was 222k per request during the first child and
645k during the sixth — the same work at 2.9x the price (joshuafolkken/kit#968). The growth is not
linear in the number of children; the k-th child re-reads the wreckage of the k-1 before it on every
turn.

**So the run hands off when the marginal cost crosses a line, and the line is read, not felt.**

```bash
pnpm josh cost --over 400000
```

It prints `over` or `under` on standard output and the measured figure on standard error. `over`
means the next turn of this session costs more than the threshold in billed input, and the number is
passed explicitly so a run cannot drift it by remembering it wrong.

**閾値 400,000 は計測が出した数字ではない。** joshuafolkken/kit#968 がそう書いたのは誤りで、joshuafolkken/kit#984 で訂正した。計測が支持するのは**ほぼ即座に区切ること**である — 50 リクエスト（≒ 子 1 件）ごとに区切れば課金入力は実測の 33% に収まり、区切り 1 回の費用（新しいセッションで常駐を書き直す約 56,000 ＋ EPIC と子 Issue の読み直し約 15,000 で概ね 70,000 トークン）に対して 1 回あたりの節約は約 14,500,000 トークン、**およそ 200 倍**の開きがある。損益分岐は最初の子の途中で既に超えており、400,000 に達した時点では割高な状態で数百ターン走った後である。

**400,000 が表しているのは、トークンと人の手数の釣り合いである。** 区切るたびに人が `epicrun #<E>` を打ち直すため、計測の答え（子ごとに区切る）をそのまま採ると無人性を失う。トークン対トークンではなく**トークン対人の手数**のトレードオフであり、そう書かれていなかった。

**その釣り合いは、子 1 件を委譲するようになった今の親のループには当てはまらない。** 親の文脈には要約しか積まれないため、この閾値に達すること自体がまれである。現在の 400,000 は、**委譲が使えない環境で親の文脈が膨らんだ場合の保険**として残っている数字であって、計測が導いた最適値ではない。

`over` と `under` のほかに、**終了コード 1 で標準出力が空**という答えがある。トランスクリプトが見つからない場合と、リクエストが 0 件の場合である。**どちらも `under` として扱ってはならない** — 測れなかったことを「まだ安い」と読むのは、`epic:next` の読めない一覧を「指摘なし」と読むのと同じ誤りである。判定できない旨を報告してその子で区切る。

#### いつ聞くか、そして何をするか

**Ask once per child, immediately after its merge and `pnpm josh ms`** — never mid-child. That
moment is the only one where nothing is in flight: the PR is merged, the working tree is on the
default branch and clean, and the epic's state on GitHub is complete. A hand-off taken anywhere else
would have to carry work that is not written down yet.

- **`under`** — go back to step 1 of the loop and run the next child.
- **`over`** — finish the session. Post the epic progress comment naming what merged and what
  remains, send a **`confirmation`** Telegram with the resume command in its body — 区切りは人が次のコマンドを打つのを待つ停止であり、それが `confirmation` の意味である。`completion` は完了していない epic を完了として告げてしまう — and stop with:

  > Please run `epicrun #<E>` to continue this epic in a fresh session.

  **報告は完了報告の書式で書かない。** 区切りは完了でも park でも失敗でもない**第 4 の停止**であり、専用の書式が `prompts/collaboration-workflow/report-format.md` →「区切りの報告（完了報告と区別する・必須）」にある。`原因 / 対応 / 結果` の 3 行は使わない — それは finished なランの形であり、epic はまだ終わっていない。書くのは 4 つ、**終わったこと / 残っていること / 止めた理由 / 次に打つコマンド**である。Telegram 本文も同じ書式で書く。

**This is not a failure and not a park.** No child needs a decision; the run is simply cheaper to
continue elsewhere. `needs-decision` is not applied, nothing is stashed, and no Issue is filed.

#### 何が引き継がれ、それはどこにあるか

**Nothing is carried in the conversation.** Everything the next session needs it reads back:

| What the next session needs                  | Where it reads it                             |
| -------------------------------------------- | --------------------------------------------- |
| Which children remain, and which is runnable | `pnpm josh epic:next <E>`                     |
| The order and the dependencies               | the epic body                                 |
| What each remaining child is                 | the child Issue body                          |
| What already merged                          | the epic's task list, and the closed children |

That is the same state a resumed run has always used (joshuafolkken/kit#861), which is why the
hand-off needs no new mechanism — it makes deliberate what an interrupted run already did by
accident. **A planned hand-off is strictly more certain than an interruption**: an interruption can
land mid-child with a dirty tree and a stale `in-progress` label, and this cannot, because it is
only ever taken when a child has just closed.

**A resumed session is a new session**, so it runs `josh latest` once before its first child, exactly
as the rule above says.
