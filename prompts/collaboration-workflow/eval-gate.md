## `josh eval` をいつ回すか（配布物の変更を測る）

joshuafolkken/kit#855 が `josh eval` を用意し、配布ドキュメント・skill・hook の変更が実際にエージェントの挙動を変えたかを、実セッションの**ツール呼び出し**で測れるようになった。欠けていたのは「いつ払うか」である — `docs/eval.md` に「変更したときに回せ」と書いてあるだけで、どの完了ゲートにも検証ゲートにも現れなかったため、ルールを書き換えた PR が既存ルールを回帰させても検出経路が無かった（joshuafolkken/kit#907）。ここがその定義のカノニカル参照である。

### 発火条件はコマンドが答える（裁量に委ねない）

```bash
pnpm josh eval:scope            # → required | skip ; 理由は stderr
pnpm josh eval:scope --staged   # staged 差分について
```

**入力は変更されたパスの集合だけで、それ以外は無い。** 「今回は文言だけ」は費用の圧力のもとで下される判断であり、その圧力は**回帰が最も出やすいときにちょうど `skip` の側へ倒れる**。`pnpm josh review:level` がレビュー水準を裁量から取り上げたのと同じ理由で、これも段落ではなくコマンドである。

**測定対象のパス集合は `eval_sandbox.DISTRIBUTED_PATHS` から導出され、文書側で列挙し直さない。** シナリオは sandbox が複製したものだけを読むので、その一覧が「スイートが変更を見られる面」そのものである。文書に別の一覧を書けば、どちらかが必ず古くなる。現在の集合は `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `.claude/skills/**` / `prompts/**` / `.claude/settings.json`。

- **1 本でも該当すれば変更全体が `required`。** スイートは変更されたファイルではなく**配布物全体**を測るので、差分の一部だけを測るという状態は存在しない。
- **空の差分も `required`。** 何も変わっていなければ測るものは無いが、`skip` と答えると「差分を読み損ねた呼び出し元」に測ったのと同じ答えを渡すことになる。`josh review:level` も同じ曖昧さを同じ側へ倒しており、姉妹コマンドが別々に答えるほうが罠である。
- **harness とシナリオ自身（`scripts/eval/**` / `evals/scenarios/**`）は発火させない。** 物差しを変えることは測られる対象を変えることではなく、空のシナリオは `scripts/eval/eval-scenario.test.ts` が既に拒否する。
- **1 件だけ、スイートが見られる範囲より粗い項目がある — `.claude/settings.json`。** sandbox はこのファイルを、`pnpm` / `npm` / `yarn` / `npx` / `josh` を起動する hook を落とすフィルタ越しに複製する（`package.json` の無いディレクトリでそれらは失敗するため。`docs/eval.md` →「Where a run happens」）。そうした hook だけを変えた場合も `required` になるが、どのシナリオもそれを観測できない — 報告にそう書き、ランをその hook の測定として読まない。ここで発火条件を絞るには差分の中身を解釈する必要があり、それはこのコマンドが取り除いた裁量そのものである。

### 検証ゲートのどこに入るか

**`/code-review` が収束した後、`pnpm josh bump minor` の前。** `pnpm josh gate` の中には入れない。理由は 2 つあり、どちらも単独で決定的である。

1. `gate` は修正のたびに回り、`epicrun` では子ごとに回る。そこに実 Claude セッション 5 本を置けば、費用がラウンド数に比例して増える。
2. レビューは測られている当の散文を書き換える。収束前に測れば、下書きを測ることになる。

### 失敗時の扱い — `✘` は止め、`?` は止めない

`pnpm josh eval` は最後に 1 行、判定を出す。終了コードでは足りない — 失敗した実行と何も測れなかった実行がどちらも非ゼロで、その 2 つこそ区別しなければならないからである。

| 判定         | 意味                                 | マージ                                                                  |
| ------------ | ------------------------------------ | ----------------------------------------------------------------------- |
| `held`       | 全シナリオが成立                     | 進む                                                                    |
| `blocked`    | シナリオが失敗した（測定された違反） | **止める** — `→` 行が名指すルールの散文を直し、そのシナリオ名だけ再実行 |
| `unmeasured` | 測定が成立しなかった（`?` を含む）   | 進む。報告には必ず書く                                                  |

- **`blocked` は、止める前に「この変更のものか」を切り分ける。** スイートが測るのは差分ではなく配布物**全体**なので、赤いシナリオはこの変更より前から赤かった可能性がある。`docs/eval.md` が比較の単位を**前後 1 組**と書いているのはこのためであり、欠けていたのはその 1 組をブロック判断につなぐところだった。落ちたシナリオ 1 本だけを、変更前の文書に対して回す:

  ```bash
  git stash push -u -m "eval baseline"
  pnpm josh eval <name>          # 変更前の文書
  git stash pop
  ```

  | 変更前   | 変更後     | 何であるか                                                                                                                                                                                                                                                                                    |
  | -------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 成立     | 失敗       | **この変更による回帰。** `→` 行が名指すルールの散文を直して再実行する。**2 巡まで**（`prompts/review.md` の回数上限と同じ理由 — 修正は新しい面を作り、上限の無いループは終わらない）。2 巡目でも赤なら、`epicrun` 配下では `needs-decision` で park、それ以外は `confirmation` を送って止める |
  | 失敗     | 失敗       | **元から立っている失敗であり、この変更のものではない。** 独立した Issue として起票し（Tier A・first-party）、前後 2 つの読みを手元の Issue に記録して先へ進む。ここで止めれば、どの配布ドキュメント変更も自分が入れていない欠陥の後ろで凍る                                                   |
  | 測定不能 | いずれでも | 組にならないので切り分けられない。baseline を 1 度だけ再実行し、それでも測れなければ全体を `unmeasured` として報告する                                                                                                                                                                        |

  **baseline を取らずに「元から赤い」と判断してはならない。** それはこのコマンドが取り除いた裁量が、向きを変えて戻ってきたものである。

- **`unmeasured` はルールについて何も言っていない。** `docs/eval.md` が書くとおり、連続する `?` は共有バジェットについての言明であって規則についてのものではない。ここで止めれば、外部の障害で作業が park される。**ただし黙って通してはならない** — 完了報告に「測定できなかった」と書く。判定行が 1 行も出なかった場合（`claude` CLI が無い、認証が切れている等）も `unmeasured` として扱い、同じく報告する。**「緑だった」と書くことは、どの経路でも許されない。**

### 判定行が答えであり、終了コードは答えではない

`pnpm josh eval` は `unmeasured` でも `blocked` と同じく非ゼロで終了する。したがって `josh eval && ...` のように連結したり `set -e` の下に置いたりしてはならない — 上流のバジェット障害でランが止まることになり、それはこの規則が避けようとしている結果そのものである。**読むのは最後の判定行である。**

**スイートが実行できなかった呼び出しは `unmeasured` ではなく `blocked` になる。** `blocked` の後の復旧手順は `pnpm josh eval <name>` であり、そこでシナリオ名を打ち間違えると判定行が 1 行も出ない。それを `unmeasured` と読めばマージは止まらない — 測定を求めて何も得られていない以上、答えは `blocked` である。

### 消費側リポジトリでは、測られるのはインストール済みの kit である

発火条件は**そのリポジトリ**の変更パスを読み、sandbox は**インストール済みの `@joshuafolkken/kit`** から文書を複製する。kit 自身では両者は同じ木だが、消費側では違う。消費側で `josh sync` の結果をコミットすると `required` になり、測られるのはその sync が入れたばかりの配布物である — 消費側は配布ドキュメントをローカルで編集しない（`CLAUDE.md` →「配布ドキュメント・設定の変更は kit に上流化する」）ので、これは正しい対象である。**消費側で赤が出た場合、それは kit 側の上流 Issue であってローカルの修正ではない。** 消費側のプロジェクト固有 skill はそもそもスイートの視界の外にあり、そこで `required` が出ても得るものは無い — ランの結果をその変更の測定として読まず、報告にそう書く。

### コストの上限 — 「全シナリオ」を「Issue に 1 回」

**回すときは常に全シナリオ**であり、変更に関係するシナリオだけを選ぶことはしない。シナリオが宣言するのは測る**ルール**であって読む**ファイル**ではなく、どの文書を読むかは実行時にエージェントが決める。パスから「関係するシナリオ」を機械的に選ぼうとすれば、シナリオごとにパスの宣言を新設することになり、その宣言自体が推測である。加えて `docs/eval.md` が書くとおり比較の単位は `n/m` であり、部分集合の `n/m` を全体の基準線と比べることはできない。

**上限は「何本回すか」ではなく「何回回すか」に置く — Issue につき 1 回。** 検証ゲートの中で `/code-review` の後ろに 1 度だけ置いているのは、この上限そのものである。

### EPIC 完了時には回さない（joshuafolkken/kit#907 の決定）

joshuafolkken/kit#907 の追記は、EPIC 完了時にもう一度回し、開始時からの低下をランの失敗とするかを問うた。**回さない。** 理由は「費用が高いから」ではない。

**上の「全シナリオ」という決定が、その発火点を先に満たしてしまっている。** 配布物に触れた子はどれも全シナリオを回し、`blocked` でマージを止める。したがって「1 件では見えない緩やかな劣化」は、**変更のたびに配布物全体が測られる**ことで既に捕まっている。EPIC の最後に測るのは、最後に配布物へ触れた子が測ったのと**同じ木**である — 2 度目の測定であって、新しい情報ではない。

「無人ランには成果の質を測る計器が無い」という追記の論点への回答はこうである — **計器は在り、子ごとに、配布物全体に対して、マージを止める強さで作動している。** joshuafolkken/kit#917 が数える介入回数では見えない経路をふさぐのは、この per-child の発火点であって、EPIC 完了時の再測定ではない。

加えて「開始時からの低下」を判定するには、セッションと子をまたいで基準線を保存する必要がある。`epicrun` の実行状態は GitHub にしか無い（joshuafolkken/kit#860）ため、これは新しい保存機構の追加を意味する。`?` が日常的に出るスイートで 2 つの `n/m` を比べれば、バジェット由来の偽の「低下」でランを失敗させることにもなる。**得られるものが 2 度目の同じ測定である以上、その機構は正当化されない。**

配布物に一度も触れない EPIC では、どちらの発火点も作動しない。それは正しい — 配布物が変わっていなければ、エージェントの挙動を変えたものは無い。
