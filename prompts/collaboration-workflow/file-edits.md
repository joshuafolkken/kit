## ファイル編集はコマンド本文に本文を載せない

`CLAUDE.md` →「Never carry a file's new text inside a shell command.」の正典。

### 何を禁じているか

**編集後のテキストを丸ごとコマンド行に載せる形を禁じる。** 典型は、インタプリタを起動して領域を書き戻す次の形である。

```bash
python3 - <<'PY'          # ← 禁止
text = open('CLAUDE.md').read()
open('CLAUDE.md', 'w').write(text.replace(OLD_REGION, NEW_REGION))
PY
```

`NEW_REGION` は変数ではない。実際には**置換後の本文そのもの**がここに直接書かれ、コマンド行に載る。それがコストの正体である。

領域を指定して書き換える編集は **Edit ツール**（old / new の差分）で行う。`node -e`、`cat > file <<'EOF'`、`tee file <<'EOF'`、`perl -0pi -e` に長い置換文字列を渡す形も同じ理由で禁止される。

### 判断基準は「本文を丸ごと運ぶか」であり、ツール名ではない

禁止の対象は**ツールの種類ではない**。判断は 1 問で決まる。

> **そのコマンドは、置換後のテキストを丸ごとコマンド本文に載せているか。**

- yes → 禁止。Edit を使う
- no → 許可

したがって短い置換に `sed -i` を使うのは**許される**。パターンと置換語しか運ばないので、Edit の `old_string` / `new_string` より本文が小さい。逆に「Edit を使ったから安全」も成り立たない — 300 行のファイルを全文 `new_string` に入れれば、禁じている形と同じコストになる。次節はその後半を条件として書き下したものである。

### 編集は指摘された箇所だけを対象にする（全文書き直しの条件）

**既定は部分編集である。** 直す行が決まっているなら、`old_string` / `new_string` はその行の周辺までに狭める。数か所を直せば済むファイルを全文書き直しで出力する形は、`python3` の heredoc と同じコストを、ツールを替えただけで払っている。

**ファイルを全文書いてよいのは、ファイルそのものを置き換える意図があるときだけである。** 該当するのは次の 3 つで、それ以外は部分編集にする。

- **新規ファイルの作成** — 既存本文が無いので、運ぶ重複がそもそも発生しない
- **ファイル全体の作り直し** — 構成の組み替えや生成物の再生成で、変更後の本文が元の本文とほとんど共有しない場合
- **部分編集のほうが大きくなる場合** — 変更箇所がファイル全域に散っていて、`old_string` / `new_string` の合計が全文を超えるとき

**レビュー指摘の修正がこの規則の主戦場である。** 「この行の条件が逆」「この定数を切り出す」といった局所的な指摘ほど、部分編集は小さくなる。一方で全文書き直しのコストはファイルの大きさで決まり、指摘の小ささでは下がらない。**指摘が局所的であるほど、全文書き直しとの差は開く。**

joshuafolkken/kit#1251 のランで実測した値（joshuafolkken/kit#1260）:

| ターン             | 出力トークン | 内容                                                     |
| ------------------ | ------------ | -------------------------------------------------------- |
| レビュー指摘の修正 | 11,104       | 2 ファイルの全文書き直し。そのランの単一ターンとして最大 |
| 同じランの別ターン | 3,282        | 全文書き直し                                             |

実効生成速度は約 87 トークン/秒なので、**この 1 ランで約 2 分 45 秒が、すでに存在する行を打ち直すことに使われている。**

### `sed -i` を使う前に満たす 4 条件

`sed` が安いのは事実だが、Edit と違って**一致した全行**を書き換え、**一致が 0 件でも黙って成功する**。Edit の一意性検査に相当するものが無いので、使う前に次を満たす。

1. **出現回数を先に数える** — `grep -o '<pattern>' <file> | wc -l` が `1` であること。**`grep -c` を使ってはならない** — 数えるのは一致した「行数」であって出現回数ではないので、同じ行に 2 回出る場合も `1` を返す。`s///` は 1 行につき 1 回しか置換しないため、そこを一意と読むと**半分だけ書き換わったファイル**が黙って残る。`0` なら何も起きないまま成功して返る
2. **メタ文字を持ち込まない — パターン側と置換語側の両方** — 区切りの `/`、`&`、`\`、正規表現の `.` `*` `[` `]` `^` `$` のいずれかがどちらかに入るなら Edit を使う。散文が対象のこの repository では `/` とバッククォートが頻出し、**危ないのはむしろパターン側**である（`s/prompts\/…/…/` はエスケープを 1 つ落とすだけで `unterminated 's' command`、`.` は書き手が意図していない箇所に静かに一致する）
3. **`-i` の引数はプラットフォームで違う** — BSD / macOS は `sed -i '' 's/…/…/' file`、GNU / Linux は `sed -i 's/…/…/' file`。片方の形を他方で走らせると、エラーになるか `''` という名前のバックアップファイルが残る。**配布ドキュメントに手順として書くときは必ずこの差を明示する** — kit の成果物は両方のプラットフォームの consumer に届く
4. **編集後に自分で整形する** — `.claude/settings.json` の `PostToolUse` フックは `Bash` にも一致する（joshuafolkken/kit#1337）が、渡されるペイロードにはコマンドしか入らずファイルパスが無いため、Bash 経由の編集では整形は走らない。`sed` で表の行や折り返しのある段落に触れたら、続けて `pnpm josh format` を走らせる。**`format:edited` は手で呼べない** — フックが渡す JSON を stdin から読んで `tool_input.file_path` を取り出す設計で、引数にパスを取らないからである。放置すると `pnpm josh lint`（`prettier --check .`）が後から落ちる

**4 条件のどれかが面倒に見えたら、そこが Edit を使う場所である。** `sed` はコストを下げるための例外であって、既定の編集手段ではない。

| 形                                            | 可否         | 理由                                                      |
| --------------------------------------------- | ------------ | --------------------------------------------------------- |
| Edit（数行の old / new）                      | 可           | 差分だけが本文に載る                                      |
| `sed -i` の短い置換                           | 条件付きで可 | パターンと置換語しか載らない。上の 4 条件を満たすこと     |
| `python3 - <<'PY'` で領域を書き戻す           | 不可         | 置換後の本文が丸ごと載る                                  |
| `cat > file <<'EOF'` で既存ファイルを書き直す | 不可         | 同上                                                      |
| `cat > new-file <<'EOF'` で新規ファイルを作る | 可           | 既存本文を運んでいない。ただし長文なら Write のほうが安い |
| 読み取り・検索（`cat` / `sed -n` / `grep`）   | 可           | 本文を運ばない                                            |

### なぜコストが二重になるか

インタプリタで書き戻す形は、編集後の本文が**コマンド本文とファイルの両方**に載る。さらに悪いのは持続性である。**コマンド本文は、書いた時点以降のすべてのリクエストで読み直される。** ランの序盤に書いた編集スクリプトほど、そのランの残り全リクエストぶん課金され続ける。ファイル側は次に読んだときだけ載るのに対し、コマンド側は消えない。

joshuafolkken/kit#1144 のランのトランスクリプトで実測した内訳（joshuafolkken/kit#1150）:

| 種別                    | 割合      |
| ----------------------- | --------- |
| tool_result             | 37.7%     |
| **Bash のコマンド本文** | **30.2%** |
| thinking                | 24.9%     |
| text                    | 4.7%      |

Bash コマンド本文 97,042 tok・427 呼び出しの内訳:

| 種別                                  | 呼び出し数 | トークン   | 割合      |
| ------------------------------------- | ---------- | ---------- | --------- |
| `python3 - <<'PY'` 形式のファイル編集 | 145        | **79,317** | **81.7%** |
| git / gh / pnpm                       | 140        | 12,716     | 13.1%     |
| 読み取り・検索                        | 110        | 3,215      | 3.3%      |
| その他                                | 32         | 1,794      | 1.8%      |

**編集スクリプトだけでセッション全体のコンテキストの約 2 割を占めていた。** 1 回あたり平均 547 tok、上位は 1,200〜1,800 tok。総量そのものより、二重計上と持続が効いている。

適用後の再計測は joshuafolkken/kit#1159 が担当する。

### なぜ resident に置くか

residency 基準（`residency.md`）は 1 問で決まる。

> **その規則は、skill がロードされていないターンでも効く必要があるか。**

答えは yes である。ファイル編集はワークフローのキーワードが打たれていないターンでも起き、**編集の直前にロードされる skill は存在しない。** skill 側に本体を置いた場合、この規則は一度も発火しない — 規則を書いたのに削除したのと同じ振る舞いになる。

そのうえで、常駐側に置くのは**トリガと導線だけ**である。常駐側に残すのは次の 3 点で、それだけで正しく振る舞える。

1. 領域を指定する編集は Edit で行い、インタプリタや heredoc で領域を書き戻さない
2. **Edit 自体を全文へ広げない**（joshuafolkken/kit#1260）
3. 判断基準は「本文を丸ごと運ぶか」であってツール名ではない（短い `sed -i` は許される）

実測値・可否表・二重計上の説明・全文書き直しが許される 3 条件、そして**インタプリタの具体形**（`python3 - <<'PY'` / `node -e` / `cat > file <<'EOF'`）はこのファイルにあり、常駐側からは落としている。これらは「読まなくても正しく振る舞えるが、読めばより納得できる」種類の記述だからである。**具体形を指し先へ移したのは削除ではなく移動である** — 禁止の区分は常駐側の「インタプリタや heredoc」が担い、個々の形はこのファイルの可否表が担う。

### マーカーテスト

`scripts/inline-edit-rule.test.ts` が次を固定する。

- `CLAUDE.md` に規則のトリガ文と判断基準の一文が resident で存在すること
- `CLAUDE.md` に全文書き直しの禁止（「Edit を全文へ広げない」）が resident で存在すること
- 常駐側がこのファイルを導線として指していること
- このファイルが判断基準・可否表・`sed -i` の 4 条件・全文書き直しの 3 条件を持っていること
- インタプリタの具体形 3 つ（`python3 - <<'PY'` / `node -e` / `cat > file <<'EOF'`）が常駐側にも residency 一覧にも残っておらず、このファイルにあること
- 実測値（79,317 / 81.7% / 30.2% / 11,104 / 3,282）が常駐側にも residency 一覧にも貼り戻されていないこと
- residency の一覧（`.claude/skills/workflow-commands/SKILL.md` とこのディレクトリの `residency.md`）にこの規則が載っていること
