## Step 1: Issue 作成テンプレ

タイトルは簡潔で明瞭な英語にする（「出力の言語（`JOSH_SESSION_LANG`）」の例外）。日本語や改善できるタイトルは実装開始前に `pnpm josh issue:plan <N> --body-file <path> --title "<title>"` で計画と一緒に書き換える。本文は次のテンプレートの節をすべて含める:

````md
## 背景

<不具合なら `- 種別: 不具合`、そうでなければ `- 種別: 非不具合` を宣言する>
<不具合なら `- 原因: #<PR>`、追えなければ `- 原因: 不明（<理由>）` を宣言する>
<人の判断が要らなければ `- 人の判断: 不要`、要るなら `- 人の判断: 要（<方針の判断 / 外部アカウント / 目視確認>）` を宣言する>
<レーンを延ばした原因なら `- 原因のレーン: <分> 分（#<N>）` を宣言する。分は `pnpm josh lane:net <N>`>
<そのうちこの Issue の原因で縮められる分は `- 原因の損失: <分> 分` で宣言する。再発のたびに 1 行足す>
<セキュリティの指摘なら `- セキュリティ: <迂回される gate・ガード・権限>` を宣言する>
<Issue を park させた、またはランを止めた run 機構の不具合なら `- 原因の park: #<N>` を宣言する>
<任意。`- 優先度: 緊急（条件 <1-3>）`、`- 優先度: 高（<根拠>）`、`- 優先度: 通常` のどれか。無ければ下限か通常>
<差分の見積もりを `- 規模見積もり: 約 <N> ファイル / <M> 行（テスト除く）` で宣言する>
<見積もりが分割の目安を超えても 1 件にするなら `- 分割しない理由: <理由>` を宣言する>

<なぜ必要か>

## 現象

<現在の問題>

## 期待結果

<どうなれば完了か>

## 受け入れ条件

- [ ] 条件1
- [ ] 条件2

## 発火点

<AI の振る舞いを変える Issue のみ。その規則が破れる瞬間に最初に呼ばれるツールコール名を 1 つだけ書く（例 `Bash` / `Edit` / `Read` / `Write` / `AskUserQuestion`、回答を判定する規則は `Stop`）>

## ベースライン

<AI の振る舞いを変える Issue のみ。「コマンド + 値」で書く>

- `<測定コマンド>` → <現在の値>

## 再現

<AI の振る舞いを変える Issue、および `- 原因: 不明（<理由>）` の不具合のみ。「コマンド + 実際の出力」で書き、出力はフェンス（``` または ~~~）で囲む>

- `<再現コマンド>`

```
<実際の出力>
```

## 期待効果

<`- 目的: 時間短縮` のみ。出典はコマンドと値>

- 効く率: <値>
- 1 回あたりの得: <値>
- 外れたときの損: <値>
- 出典: <`pnpm josh lane:stats` → 値>

## Origin

<別リポジトリのセッションから起票した場合のみ。起票元 Issue を `owner/repo#N` 形式で書く。自リポジトリ発の Issue では節ごと省略する>
````

### `## 背景` 直下の宣言と分類ラベル

起票は `pnpm josh issue:file "<title>" --body-file <本文ファイル>` で行い、本文の検査（`pnpm josh issue:lint <path>` と同じ）と下表のラベル付与はコマンドが行う。**宣言は起票者が選ぶ。** `- 人の判断:` の行は必須で、`issue:file` が検査し `auto-ok` の判定に使う（`scripts/issue/issue-auto-ok.ts`、`docs/how-to/run-backlog.md`）。`不要` を宣言する起票には `--label run:lane`（kit 自身の検証が `main` で毎回決まって誤った答えを出す不具合なら `run:solo`。時々出る誤判定は `run:lane` と `priority:critical`）も付ける — 無ければ `issue:file` が拒否する。

| 宣言                                                     | 付くラベル                             | 選ぶ基準                                                                                              |
| -------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `- 種別: 不具合`                                         | `bug`                                  | 報告された症状を直す（無ければ `- 種別: 非不具合`）                                                   |
| `- 目的: 機能追加`                                       | `enhancement`                          | 新しい機能。修正・文書・依存更新・保守には書かない                                                    |
| `- 目的: 機能改善`                                       | `enhancement`                          | 既存機能の改善。目的が曖昧なら受け入れ条件を具体化してから                                            |
| `- 目的: 時間短縮`                                       | `enhancement`                          | 所要時間を短くする。`## 期待効果` の 4 行が必須                                                       |
| `- 互換性: 破壊的変更`                                   | `breaking-change`                      | 契約を変える。移行措置があっても書き、廃止対象と影響を書く                                            |
| `- 種別: 振る舞い変更`                                   | なし                                   | AI の振る舞いを変える。下の 3 見出しが必須                                                            |
| `- 人の判断: 不要`                                       | `auto-ok`（除外ラベルが無ければ）      | 方針の判断・外部アカウント・目視確認のどれも要らない                                                  |
| `- 実施可能条件: #<PR> のマージ後 <K> マージ`            | `not-before`（待つ間）                 | 追跡計測。元の PR のマージ後に lane ledger が K 件のマージを記録するまで着手しない                    |
| `- 実施可能日: <UTC>`                                    | `not-before`（待つ間）                 | 外部の期限など暦そのものに意味がある待ち（`YYYY-MM-DDTHH:MMZ`）。追跡計測には使わない                 |
| ``- 計測宣言: `<command>` <= <数値>``                    | なし（閉じたら `measured`）            | 追跡計測の既定。比較は `<=` `<` `>=` `>`                                                              |
| `- 計測宣言なし: <理由>`                                 | なし                                   | 追跡計測の値を 1 コマンドで出せない（Actions の記録・外部サービスなど）                               |
| `- 原因のレーン: <分> 分（#<N>）`                        | なし                                   | レーン #N を延ばした原因。並びの代替キーで、下限は作らない（下の F）                                  |
| `- 原因の損失: <分> 分`                                  | 合計 30 分以上で下限（宣言が無いとき） | 原因ごとの縮められる分。再発ごとの行を合計して並べる（下の F）                                        |
| `- セキュリティ: <迂回される gate・ガード・権限>`        | 下限（宣言が無いとき）                 | 下の H                                                                                                |
| `- 原因の park: #<N>`                                    | 下限（宣言が無いとき）                 | 下の I。#N は park された、またはランが止まった Issue                                                 |
| `- 優先度: 緊急（…）`                                    | `priority:critical`                    | 下の A。条件番号を括弧に書く                                                                          |
| `- 優先度: 高（…）`                                      | `priority:high`                        | 下の D・E・F・H・I のどれか。根拠を括弧に書く                                                         |
| `- 優先度: 通常`                                         | なし                                   | どれにも当たらない                                                                                    |
| `- 実施順: 最後`                                         | なし                                   | 触るファイルが事前に読めない広域 upgrade など、列の末尾でまとめて走らせたい作業。緊急・高と同居しない |
| `- 規模見積もり: 約 <N> ファイル / <M> 行（テスト除く）` | なし                                   | epic 以外は必須。目安の判定は `issue:file`（`scripts/issue/size-estimate.ts`）                        |
| `- 分割しない理由: <理由>`                               | なし                                   | 目安を超える見積もりを 1 件のまま起票する（`split-assessment.md` → "The question"）                   |

集計・計測（`計測` / `before` / `変更前後`）を Issue コメントに記録する受け入れ条件と実装の見積もりを併せ持つ本文 → 集計・計測を `--route split` の先行 Issue に分け、そのコメントを `## 背景` に引く（`issue:lint` が拒否する。`scripts/issue/aggregation-split.ts`）。

優先度の基準（`scripts/issue/issue-priority.ts`）。`kickoff new critical` / `high` と打った優先度があれば本文は判定しない:

- A. 割り込み起票の 3 条件のどれか（`wip-cap.md` →「3 条件 — 該当するかは判断ではない」）
- D. 人が示した期限や方針がある
- E. ほかの open Issue 2 件以上の前提（blocked-by）になっている
- F. `- 原因の損失:` の合計（再発ごとに 1 行足す）が 30 分以上なら高。再発の追記の後は `pnpm josh issue:priority <N>` がラベルを付ける。`- 原因のレーン:` は 1 本のレーンの見積もりなので下限を作らない。同じ優先度の中の並びは `- 原因の損失:` の合計、無ければ `- 原因のレーン:` の分。その次が `## 期待効果` の週あたりの短縮分（`効く率` の週あたりの回数（「2 週間で 10 回」は週 5 回に直す）× `1 回あたりの得`、分）で、どちらかが数値で読めない Issue はその後ろ。% は計算しない。超過調査はそのレーン 1 本の記録から、工程別内訳（`pnpm josh lane:breakdown <N>`）の長い工程の順に、縮められる分の大きい原因を最大 5 件（1 件 1 分以上）起票する（`scripts/lane/lane-overrun-prompt.ts`）
- H. 信用できない入力が検証 gate・ガード・権限を迂回する経路の指摘。レビューの範囲外の残りを含む（高）
- I. 実際の Issue を park（`run:stalled`）させた、またはランを止めた run 機構の不具合（高）
- 下限・拒否・宣言が無いときのラベルは `issue:file` が出す（`scripts/issue/issue-priority.ts`）
- `- 目的: 時間短縮` の Issue は `## 期待効果` の 4 行を書く。短縮の % は求めず、% による拒否も下限も無い
- 根拠の無い `緊急` / `高` も `issue:file` が拒否する

- **持ち主の意図と違う動きは、コード・コメント・テストに書かれた設計どおりでも `- 種別: 不具合` とする。** 例: コメントとテストに固定されたまま意図より広く働く自動付与、文書だけでも意図と違う分類を生む基準
- `- 種別: 不具合` の回帰テストは、利用者が症状を見たのと同じ粒度で書く。修正前のツリーでも緑になるテストは `pnpm josh git -y` が拒否する（joshuafolkken/kit#2448）
- `bugfix`（PR のリリース分類）を Issue の `bug` の代わりにしない。`enhancement` と `breaking-change` の両方を持つ Issue の PR は `breaking-change` にする
- `## 発火点` の名前は `prompts/collaboration-workflow/rule-delivery.md` の配送表と突き合わされる
- `## ベースライン` の測定コマンドは、マージ後に `pnpm josh measure:rerun <N>` が再実行して before / after を印字する（作者が `OWNER` / `MEMBER` / `COLLABORATOR` の Issue に限る）
- `- 計測宣言:` は `backlog:drive` がレーンを起こす前に実行し、基準内なら閉じる（`scripts/backlog/backlog-measure-close.ts`）
- 公開しないと利用側が使えない変更には `--release` を付ける（既存 Issue は `pnpm josh issue:release <N>`、`docs/josh-commands-backlog.md` → `josh issue:release`）

### 起票元へのバックリンク（`## Origin` / `## Upstream issues`）

**別リポジトリのセッションから起票した Issue には、起票元へのリンクを双方向で必ず書く。**

| 方向            | 置き場所               | 固定見出し              | 内容                       |
| --------------- | ---------------------- | ----------------------- | -------------------------- |
| 上流 → 起票元   | 上流 Issue の本文      | `## Origin`             | 起票元 Issue               |
| 起票元 → 上流   | 起票元の本文かコメント | `## Upstream issues`    | 起票した上流 Issue 全件    |
| 起票元 → 未起票 | 起票元の本文かコメント | `## Upstream candidate` | 第三者への報告候補と下書き |

- 見出しは固定する。起票元の本文が確定済みなら、同じ見出しでコメントに書く
- **リンクは必ずリポジトリ修飾する**（`owner/repo#N` または完全 URL）
- チェックボックス行（`- [ ] owner/repo#N`）で書かず、散文か素の箇条書き（`- owner/repo#N`）にする（epic の自動クローズを止めるため）
- third-party への報告はユーザーの明示指示まで起票しない（→「第三者リポジトリへの書き込みは Tier C（明示指示が必要）」）
- 割り込みで起票する手順は `upstream-interrupt.md`

### 複数 Issue に分割するときの epic Issue

**1 つの要望を 2 件以上の Issue に分割したら、件数や順序の有無にかかわらず常に epic を作る。** 作成は `pnpm josh epic`、点検は `pnpm josh epic:check <E>`、子の追加は `pnpm josh epic --add` で行い、本文を手で編集しない。epic 自体を実装ランに渡さない（`backlogrun #<E> --only` が子を回す）。記法は `epic-commands` スキル →「Creating an epic」。

`josh` が使えない環境での手作業手順:

1. 子 Issue をすべて起票し、番号を控える。`epic` ラベルは `josh sync` が用意する。
2. epic を作り、`id` ではなく **number** を控える: `gh api repos/{owner}/{repo}/issues -f title="<epic-title>" -f 'labels[]=epic' -F body=@<body-file> --jq .number`。本文は次の形にする（順序がなければ `Dependencies` に `None — the children are independent; any execution order works.` と書く）:

   ```md
   ## Split rationale

   <why this split>

   ## Dependencies

   #101 -> #102

   ## Execution

   backlogrun #<E> --only

   ## Progress

   - [ ] #101 <title>
   - [ ] #102 <title>
   ```

3. 順序があるときだけ、別ステップで依存を足す（Issue 番号ではなく database id を渡す。失敗しても止めない）: `gh api repos/{owner}/{repo}/issues/<N2>/dependencies/blocked_by -F issue_id="$(gh api repos/{owner}/{repo}/issues/<N1> --jq .id)"`
