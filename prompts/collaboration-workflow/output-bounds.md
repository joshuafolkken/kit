# コマンド出力が文脈へ持ち込む量の上限（joshuafolkken/kit#1173）

**上限は機構で決まり、実行側の判断には委ねられない。** どのコマンドが何行返すかは実行前には分からないので、「たぶん短いだろう」と推測して絞るかどうかを決める形は、費用の圧力が高いときほど「これくらいなら素通しでよい」へ倒れる。joshuafolkken/kit#1094 が「区切りを判断ではなく機構にする」と述べたのと同じ原則を、出力側へ適用したものである。

## 何をしているか

配布される `.claude/settings.json` の `env` ブロックが `BASH_MAX_OUTPUT_LENGTH` を宣言する。Claude Code は Bash ツールの出力がこの文字数を超えると真ん中を省略して渡すので、**1 回のコマンドが文脈へ持ち込む量に harness 側で上限が掛かる**。エージェントは何も判断しない。

```json
"env": {
	"BASH_MAX_OUTPUT_LENGTH": "8000"
}
```

**8,000 文字。** harness の既定は 30,000 文字、受け付ける最大は 150,000 文字である（`claude` バイナリ内の `default:30000, upperLimit:150000`）。

## なぜ既定の 30,000 では足りないか

直近 25 セッション・tool_result 2,333 件を実測した。**Bash の出力は tool_result トークンの 87.5%（1,848 件・1,241,642 トークン）**を占める。その 1,848 件のうち **30,000 文字を超えたものは 0 件**だった — 既定の上限はこのプロジェクトで一度も作動していない。存在するが届かない上限は、上限が無いのと同じである。

Bash 出力の長さの分布（文字数）: p50 = 570 / p75 = 1,920 / p90 = 4,421 / p95 = 8,342 / p99 = 15,989 / 最大 = 28,908。

上限ごとに、真ん中を省略したときに削れる量:

| 上限（文字）   | 該当する呼び出し  | 削れる量（tool_result 全体に対して） |
| -------------- | ----------------- | ------------------------------------ |
| 4,000          | 218 件（11.8%）   | 26.6%                                |
| 6,000          | 124 件（6.7%）    | 18.2%                                |
| **8,000**      | **95 件（5.1%）** | **12.7%**                            |
| 10,000         | 69 件（3.7%）     | 8.7%                                 |
| 15,000         | 22 件（1.2%）     | 2.5%                                 |
| 30,000（既定） | 0 件              | 0%                                   |

**8,000 を採ったのは p95 だからである。** 20 回に 19 回はこれまでと何も変わらず、残る 1 回だけが範囲を指定して読み直す形になる。4,000 は削れる量こそ倍だが 8 回に 1 回が切り詰められ、読み直しの往復が上限で浮かせた分を食い返す。

## 却下した案と、その理由

- **非有界コマンドを PreToolUse guard が拒否する。** 実測が否定した。tool_result の上位には `cd`（5.4%）と `for`（4.4%）が入り、先頭語を見ても正体が分からない — 命令は `cd <dir> && …` や `for n in …; do …; done` の内側にある。さらに 2 位の `sed`（16.6%）は本 Issue が推奨する範囲指定の形そのもので、構文上は有界なのに 1 ブロック 8,000 トークンを運んでいる（`sed -n '30,400p'`）。**形で見分ける案は、実データ上で外れる。** 大きさで切る案にはこの弱点がない。
- **共通ラッパで切り詰める（`josh` のサブコマンド等）。** ラッパを通すかどうかが実行側の判断になり、本 Issue が問題視した構造がそのまま残る。上限を機構にするという要件を満たさない。

## 切り詰められたときにどうするか

**情報を落とすのではなく、必要な範囲に合わせて読み直す。** 同じコマンドを再実行しても上限は同じなので、絞り込んで読む:

- ファイルなら範囲を指定する（`sed -n '120,180p' <file>`）か、`Read` ツールの `offset` / `limit` を使う
- 一覧なら件数を絞る（`--limit`、`| head -30`）
- JSON なら必要な項目だけ取り出す（`gh api … --jq '…'`）
- どうしても全量が要るときは、いったんファイルへ落として（`> <file>`）から範囲を読む

## 切り詰められた出力を、完全な出力として読まない

**検証ゲートと差分は、切り詰められた結果で判断しない。** 上限は harness が掛けるので、`pnpm josh gate` の出力も `git diff main...HEAD` も等しく対象になる。両者の性質は違い、危険なのは後者である。

- **`pnpm josh gate` は判定そのものは失わない。** 真ん中が省略されても先頭と末尾は残り、合否の 1 行（`✔ verification gate passed` / `✗ verification gate failed: …`）は末尾に出るので、赤いゲートが緑に見えることはない。失われうるのは失敗の内訳なので、個別のチェック（`pnpm josh lint` など）を single で回して読み直す。
- **差分には判定行が無い。** `git diff` が切り詰められると、抜けた hunk があること自体は省略マーカーで分かるが、抜けた内容は復元されない。自己レビューの対象が欠けたまま「指摘なし」と結論づけるのは、ゲートを弱めたのと同じである。**差分はファイルへ落としてから範囲で読む。**

```bash
git diff main...HEAD > /tmp/diff.patch && wc -l /tmp/diff.patch
```

**切り詰めは黙って起きない** — 省略された箇所には harness がマーカーを残す。マーカーを見たら、それは「短い出力」ではなく「一部しか読んでいない出力」である。

## この上限が届かないもの

`BASH_MAX_OUTPUT_LENGTH` は **Bash ツールにだけ効く**。実測では `Read` ツールが tool_result の 10.6%（単一最大 18,991 トークン）、`Agent` が 2.3% を占めており、どちらもこの上限の対象外である。別の量として別途扱う。

## 検査

`scripts/bash-output-cap.test.ts` が、配布設定に上限が宣言されていること、値が harness の既定 30,000 より小さい（＝実際に作動する高さである）こと、受け付ける最大 150,000 を超えないこと、そしてこの文書が設定と同じ数値を書いていることを固定する。**「宣言されている」だけでは不十分**で、30,000 以上に戻された上限は宣言があっても作動しない — この文書が書かれた理由がそれである。
