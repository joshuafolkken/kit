# コマンド出力が文脈へ持ち込む量の上限（joshuafolkken/kit#1173）

**上限は機構で決まり、実行側の判断には委ねられない。** どのコマンドが何行返すかは実行前には分からないので、「たぶん短いだろう」と推測して絞るかどうかを決める形は、費用の圧力が高いときほど「これくらいなら素通しでよい」へ倒れる。joshuafolkken/kit#1094 が「区切りを判断ではなく機構にする」と述べたのと同じ原則を、出力側へ適用したものである。

## 何をしているか

配布される `.claude/settings.json` の `env` ブロックが `BASH_MAX_OUTPUT_LENGTH` を宣言する。Claude Code は Bash ツールの出力がこの文字数を超えると真ん中を省略して渡すので、**1 回のコマンドが文脈へ持ち込む量に harness 側で上限が掛かる**。エージェントは何も判断しない。

```json
"env": {
	"BASH_MAX_OUTPUT_LENGTH": "8000"
}
```

**8,000 文字。** harness の既定は 30,000 文字、受け付ける最大は 150,000 文字である（`claude` バイナリ内の `default:30000, upperLimit:150000`）。

## なぜ既定の 30,000 では足りないか

直近 25 セッション・tool_result 2,333 件を実測した。**Bash の出力は tool_result トークンの 87.5%（1,848 件・1,241,642 トークン）**を占める。その 1,848 件のうち **30,000 文字を超えたものは 0 件**だった — 既定の上限はこのプロジェクトで一度も作動していない。存在するが届かない上限は、上限が無いのと同じである。

Bash 出力の長さの分布（文字数）: p50 = 570 / p75 = 1,920 / p90 = 4,421 / p95 = 8,342 / p99 = 15,989 / 最大 = 28,908。

上限ごとに、真ん中を省略したときに削れる量:

| 上限（文字）   | 該当する呼び出し  | 削れる量（tool_result 全体に対して） |
| -------------- | ----------------- | ------------------------------------ |
| 4,000          | 218 件（11.8%）   | 26.6%                                |
| 6,000          | 124 件（6.7%）    | 18.2%                                |
| **8,000**      | **95 件（5.1%）** | **12.7%**                            |
| 10,000         | 69 件（3.7%）     | 8.7%                                 |
| 15,000         | 22 件（1.2%）     | 2.5%                                 |
| 30,000（既定） | 0 件              | 0%                                   |

**8,000 を採ったのは p95 だからである。** 20 回に 19 回はこれまでと何も変わらず、残る 1 回だけが範囲を指定して読み直す形になる。4,000 は削れる量こそ倍だが 8 回に 1 回が切り詰められ、読み直しの往復が上限で浮かせた分を食い返す。

## 却下した案と、その理由

- **非有界コマンドを PreToolUse guard が拒否する。** 実測が否定した。tool_result の上位には `cd`（5.4%）と `for`（4.4%）が入り、先頭語を見ても正体が分からない — 命令は `cd <dir> && …` や `for n in …; do …; done` の内側にある。さらに 2 位の `sed`（16.6%）は本 Issue が推奨する範囲指定の形そのもので、構文上は有界なのに 1 ブロック 8,000 トークンを運んでいる（`sed -n '30,400p'`）。**形で見分ける案は、実データ上で外れる。** 大きさで切る案にはこの弱点がない。
- **共通ラッパで切り詰める（`josh` のサブコマンド等）。** ラッパを通すかどうかが実行側の判断になり、本 Issue が問題視した構造がそのまま残る。上限を機構にするという要件を満たさない。

## 切り詰められたときにどうするか

**情報を落とすのではなく、必要な範囲に合わせて読み直す。** 同じコマンドを再実行しても上限は同じなので、絞り込んで読む:

- ファイルなら範囲を指定する（`sed -n '120,180p' <file>`）か、`Read` ツールの `offset` / `limit` を使う
- 一覧なら件数を絞る（`--limit`、`| head -30`）
- JSON なら必要な項目だけ取り出す（`gh api … --jq '…'`）
- どうしても全量が要るときは、いったんファイルへ落として（`> <file>`）から範囲を読む

## 切り詰められた出力を、完全な出力として読まない

**検証ゲートと差分は、切り詰められた結果で判断しない。** 上限は harness が掛けるので、`pnpm josh gate` の出力も `git diff main...HEAD` も等しく対象になる。両者の性質は違い、危険なのは後者である。

- **`pnpm josh gate` は判定そのものは失わない。** 真ん中が省略されても先頭と末尾は残り、合否の 1 行（`✔ verification gate passed` / `✗ verification gate failed: …`）は末尾に出るので、赤いゲートが緑に見えることはない。失われうるのは失敗の内訳なので、個別のチェック（`pnpm josh lint` など）を single で回して読み直す。記録済みの緑を再利用してスキップしたときはこの 2 行が出ず `✔ this tree is already green …` だけになるが、出力そのものが 2 行なので切り詰めの対象にならず、かつ緑のときにしか出ない（joshuafolkken/kit#1328）。
- **差分には判定行が無い。** `git diff` が切り詰められると、抜けた hunk があること自体は省略マーカーで分かるが、抜けた内容は復元されない。自己レビューの対象が欠けたまま「指摘なし」と結論づけるのは、ゲートを弱めたのと同じである。**差分はファイルへ落としてから範囲で読む。**

```bash
git diff main...HEAD > /tmp/diff.patch && wc -l /tmp/diff.patch
```

**切り詰めは黙って起きない** — 省略された箇所には harness がマーカーを残す。マーカーを見たら、それは「短い出力」ではなく「一部しか読んでいない出力」である。

## 検証コマンドをパイプに繋がない（joshuafolkken/kit#1556）

**パイプラインの終了コードは最後のコマンドのものである。** `pnpm josh gate 2>&1 | tail -40` は `tail` の終了コードで終わるので、**赤いゲートがシェルの上では成功として返る。**

joshuafolkken/kit#1546 の実行中に実際に起きた。2 回目のゲートが `✗ verification gate failed` を印字しながら、パイプラインは 0 を返していた。失敗は本物（Prettier の整形と、マーカーテスト 1 件）で、**実行した子が出力を読んでいたから気づいた**。終了コードだけを見ていれば、赤いツリーがそのままコミットされていた。

**これは `josh gate` の欠陥ではない。** 非ゼロは正しく返っており、パイプラインの終了コードが最後のコマンドのものになるのは POSIX シェルの規定どおりの挙動である。**直すべきはコマンドではなく、呼び出し方である。**

### どう呼ぶか

- **既定はパイプなしで実行する。** josh の各チェックは合否の 1 行を末尾に出すので、この文書の上限で真ん中が省略されても判定は残る（前節）。切り詰める理由がそもそも無い
- **出力をどうしても絞るなら、ファイルへ落として範囲で読む**（`pnpm josh gate > /tmp/gate.log 2>&1; tail -40 /tmp/gate.log`）。リダイレクトは終了コードを奪わない
- **パイプが避けられないなら `set -o pipefail` を前置する。** パイプラインが検証側の終了コードを運ぶ
- **どの形でも、印字された判定行を読む。終了コードだけを答えにしない**

### 対象は「結果が合否を意味するコマンド」だけ

`gate` ／ `check` ／ `lint*` ／ `cspell*` ／ `test*` ／ `eval` — 合否を返すものに限る。

**`git log | head` や `gh issue list | head` は対象外であり、意図的にそうしている。** 一覧を `| head` で絞るのは読み方として正しく、そこで拒否するフックは transcript の最頻形で発火することになる。**規則を広げると無視される方向に働き、無視される規則は無い規則より悪い**（`rule-delivery.md` →「誤ったターンで発火するフックは、フックが無いより悪い」）。

**フックは 2 つの形にも黙る。** `set -o pipefail` を前置したパイプラインは検証側の終了コードを運ぶので握りつぶしていない。引用符の中のコマンド列（`--body "cd x && pnpm josh gate | tail"` のような Issue 本文）はテキストであって呼び出しではない。**どちらも「規則に従った呼び出しを拒否しない」ためである** — 配送はラン 1 回きりなので、従った呼び出しで 1 回を使い切ると、後から本当に握りつぶしている呼び出しが素通りする。

`eval:scope` ／ `latest:scope` ／ `review:level` ／ `review:brief` も対象外である。これらは**判定ではなく答えを印字する**コマンドで、`$(...)` で受けるのが正しい使い方である。コマンド置換そのものの無音の失敗は別の規則が扱う（`docs/josh-commands.md` →「`VAR=$(...) && cmd`」）。

### 引き金つき配送で強制する —— 却下した 2 案

- **手順書の実行例を書き換える。** 却下。**書き換える例が存在しない。** 文書・プロンプト・skill の全体を調べて、パイプ付きの検証例は `docs/josh-commands.md` の 1 件だけで、しかもそれはこの不具合の説明そのものだった。パイプは手本から写されているのではなく、**毎ターン新しく発明されている**
- **呼び出し規約として書く**（「ゲートをパイプに繋ぐな」「`set -o pipefail` を前置しろ」）。却下。**同じ案が既に却下されている** — `scripts/time/time-reported-failure.ts` が「規約は守られるか守られないかのどちらかであり、図が捉えるべきは『そうすべきだったこと』ではなく『実際にしたこと』である」としてこれを退け、代わりに検出器を置いた。散文が数値を動かさなかった計測は joshuafolkken/kit#1344 と joshuafolkken/kit#1460 にもある

採ったのは**引き金つき配送**である（`rule-delivery.md`）。`pnpm josh rule:guard` が、合否を意味する josh のチェックがパイプの手前に立った `Bash` 呼び出しを**その場で拒否する**。**拒否は読み飛ばせない。**

**検出器は残る。** `scripts/time/time-reported-failure.ts` はゲート自身の `✗ verification gate failed:` 行を `is_error` の上に読む。フックが届くのは Claude Code だけで、停止スイッチを立てたセッションにも他の harness にも届かない — 検出器はその外側を覆い、かつ**規則が守られたかどうかを事後に測れる唯一の経路**である。配送と検出は代替ではなく、前者が防ぎ後者が数える。

### 検査

`scripts/piped-verification-rule.test.ts` が、配送文が仕組み・逃げ道・境界の 3 つを運ぶこと、この節が規則と却下した 2 案を単一ソースとして持つこと、そして `rule-delivery.md` の列挙表に行があることを固定する。発火・非発火そのものは `scripts/rules/delivered-rules.test.ts` が両方向から固定する。

## この上限が届かないもの

`BASH_MAX_OUTPUT_LENGTH` は **Bash ツールにだけ効く**。実測では `Read` ツールが tool_result の 10.6%（単一最大 18,991 トークン）、`Agent` が 2.3% を占めており、どちらもこの上限の対象外である。別の量として別途扱う。

## 検査

`scripts/bash-output-cap.test.ts` が、配布設定に上限が宣言されていること、値が harness の既定 30,000 より小さい（＝実際に作動する高さである）こと、受け付ける最大 150,000 を超えないこと、そしてこの文書が設定と同じ数値を書いていることを固定する。**「宣言されている」だけでは不十分**で、30,000 以上に戻された上限は宣言があっても作動しない — この文書が書かれた理由がそれである。
