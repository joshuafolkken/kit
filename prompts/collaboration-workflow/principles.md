# 原則

## no-clones — クローン禁止・単一ソース化

既存の非自明なロジック（別ファイル・別モジュール・上流依存を含む別パッケージにあるもの）を、ソースを変えずに済ませるために**コピー・移植・再実装しない**。複製したくなったら、全消費者が import する共有モジュール／export／パッケージへ単一ソース化する。

- 既存の重複は再重複の理由にならない（例: josh-game が kit をコピー）。3 つ目のコピーを足さず、重複を surface する
- 「上流を参照する」は再利用することで、コードを貼り付けることではない
- 「X を触るな」という制約でクローンを黙って正当化しない。「クリーンな修正は kit の変更が必要、代替はクローン、どちらにする？」と先に提示する
- 複製は、単一ソース化の代替案とコストを提示し、ユーザーの明示承認を得た後にのみ行う

計測は `pnpm josh clone:scan`（`pnpm josh oracle:list` の決定オラクル）。リポジトリ内と `JOSH_REPO_PATHS` の他リポジトリを跨いだ複製の件数と各 `file:line`（`[same-file|cross-file|cross-repo]`、なしは `clean`）を印字する。

## elegant-design — 設計はエレガント・シンプルを第一目標にする

フック・ガード・ルール・抽象化を足す前に、**原因側を直せばその仕組みが要らなくならないか**を問う。要らなくなるなら足さず、原因を直す。検出・通知・叱責を強化する前に、その入力を生んでいる側を断つ。

書かれたコードの可読性は `prompts/coding-standards.md` の担当で、ここはどの仕組みをどこへ足すかの規則である。互いの本文を写さず、指すだけにする。

## automate-first — 判断の要らない手順は AI に渡さず自動化する

AI の判断が要らない手順は、AI に読ませて実行させない。規則を足すときは、次の順で最初に成り立つ形を選ぶ。

1. コマンド — 手順そのものを `pnpm josh <command>` にする
2. フックの自動実行 — フックがその場で実行する、または呼び出しを `updatedInput` で書き換える
3. 差し戻しガード — 正しい形が呼び出しから決まらないときだけ拒否する
4. 文書 — 上の 3 つのどれも成り立たないときだけ書く

下の段を選ぶときは、上の段が成り立たない理由を示す。配置の問いは `residency.md` →「自動化の問い」、ガードの理由は `scripts/rules/guard-remedy.ts` の `why` に書く。

## quality-priority — 品質目標が衝突したときの優先順位

上の段は、下の段のために犠牲にしない。

1. **正しさ** — 仕様どおりに動き、検証ゲートが緑であること
2. **同列で、どれも悪化させない** — 次の 4 つに上下はない
   - **複雑さ**（読みやすさを含む）— 初見の読み手が前提知識なしに意図を追えること。部品や間接層は読む量が減るときだけ足す
   - **冗長さ**（重複を含む）— 同じ知識を 1 か所に置く（no-clones）
   - **パフォーマンス** — gate・CI・josh 起動・テストの所要時間
   - **AI コスト** — エージェントが読み込み・出力するトークン量
3. **コメント最小** — まず命名・分割・型で表現する。残すのは「なぜ」だけ

2 段目の目標同士が衝突したら、次の順で決める。

1. **まず、全部を満たす方法を探す** — 処理を減らす変更は、多くの場合すべてを良くする
2. **1 つを悪くするなら、同じ変更の中で別の場所を削って埋め合わせる** — 合計を悪化させない
3. **それでも両立しないときは、数字を示して利用者に聞く**（Tier B）— 何をどれだけ悪くして、何を得るか

不具合や複雑さへの対策を出すときは、次のようにする。

- 機能や最適化の追加を止める・凍結する・後回しにする案を出さない。順序は優先度ラベルが決める
- 進化を続けたまま不具合を防ぐ仕組み（単一ソース化、層の統合、不変条件のテスト）を提案する

## concise-prose — 文章は条件と動作だけを書く

docs・prompts・skills・拒否文・Issue・PR の文章に適用する。

- 本文には、いつ何をするか（条件と動作）だけを書く
- 理由と経緯は rationale 文書に置き、本文からは指さない — 根拠文書（`docs/maintainers/`）の側から手順を指す
- 太字は 1 節に 1 つまで。箇条書き先頭の見出し語は数えない。`→ "…"` で引かれている太字は消さない
- 同じ内容を言い換えて繰り返さない
- ファイルや節が自分自身を説明する文（「このファイルは〜である」）を書かない

## concise-reply — 対話の回答は結論・要点・次の一手

ユーザーへの回答に適用する。

- 順序: 結論（1〜2 文）→ 表か箇条書き 1 つ → 次の一手
- 散文（コードブロック・表・箇条書きの外）の上限は `scripts/rules/concise-reply.ts` の `PROSE_LIMIT`。超えた回答は Stop フックの `pnpm josh stop:guard` が書き直させる
- 仕組みの説明や同じ内容の言い換えを並べない。詳細はファイルや Issue に書く
- 対象外: 直前の発話に「詳しく」「具体的に」「詳細」がある回答、`pnpm josh run:board --chat` のような固定出力をコードブロックで返す回答、ファイルや Issue に書く成果物

## consult-vs-execute — 相談と実行を区別する

進め方・理由の質問や目標の表明（「〜したい」等）には分析と推奨のみ返し、編集・起票しない。実装可否は launcher の `JOSH_AGENT_ROLE` を読む `agent_session_role.can_implement` に従う。worker のみ実装可、scheduler・reviewer・未設定・不明値は不可。モデル名や会話から補完せず、文書・レビュー結果の記録は別扱いにする。

- **相談の主セッションは相談・起票・運用を担当する。実装は実装レーンが担当し、主セッション自身で実装を開始しない。** 「起票して」は起票を実行し、「対応してください」は合意した起票・Issue 更新・レーン操作として処理する。実装が必要なら Issue に範囲と計画を残し、既存の実装レーンへ引き渡す
- 明示されたワークフローキーワード（`kickoff` / `halfrun` / `prrun` / `fullrun` / `backlogrun`）は `workflow-commands` skill の既存手順へ渡す。主セッションが実装する根拠には読み替えない。`kickoff` は起票・計画で停止し、実装系の実行は実装レーンへ引き渡す
- 判別できないときは相談として扱う。承認済みの起票・Issue 更新・レーン操作と、実装レーン内の Tier A 判断は再確認せず進める。実行が指示された後の判断点は `CLAUDE.md` → "Decision autonomy" の Tier で決まる
- 相談スコープのシェルが通すのは、書き込み先が無いと判定できる読み取りだけ → `scripts/hooks/implementation-shell.ts`。通る: 読み取りプログラム、`-exec` / `-delete` の無い `find`、`pnpm view`、`-X` 無しまたは `-X GET` の `gh api`、`pnpm -s josh <読み取り>`、`cd <dir> &&`、`time`、読み取りプログラムだけにループ変数を渡す `for`。拒否: リダイレクト、`cd` と並ぶ書き込み、書き込み系 josh コマンド、GET 以外の `gh api`、`node` などの任意実行

## latest-first — 最新優先・fix-forward（pin-back は最終手段）

依存・ツールチェーンは**既定で最新版を採用する**。`dependency-update` skill → "4. When the bump breaks something — fix forward" はこの節を指す。

1. 適応の手間を避けるために古いバージョンに留まったり戻したりしない
2. バンプで lint クラッシュ・新規ルール・型エラー等が出たら fix-forward で解消する:
   - 新ルール／エラーが正当なら消費者コードを直す
   - ルール上書きが要るなら kit / app-kit の共有設定でスコープする。消費者リポジトリで一回限りの disable にしない
   - first-party パッケージ（kit / app-kit）起因なら、そこに Issue を立てて直す（→ `upstream-interrupt.md`）
3. **pin-back は最終手段**: fix-forward が不可能／ブロックされている（例: 未リリースの上流修正待ち）ときだけ固定し、理由を記録して最新へ戻すトラッキング Issue を立てる。pin-back を既定の推奨にしない
4. fix-forward は保護された pin を黙って書き換える許可ではない。overrides と `devEngines` の承認ゲートは `CLAUDE.md` → "Decision autonomy" と `dependency-update` skill に従う
5. バンプ起因の破壊は同じセッション内で対処し、pin の裏に先送りしない

## durable-rules — 恒久ルールは MEMORY ではなくプロンプト／ドキュメントに書く

共有価値のある恒久ルールに気付いたら、**kit が配布するプロンプト／ドキュメント**（`CLAUDE.md` / `prompts/*`）の変更として書き、自動 MEMORY（`~/.claude/projects/<repo-slug>/memory/`）で済ませない。MEMORY はマシン固有のパスなど本質的にローカルな文脈だけに使う。

- ターンがドキュメント変更を承認していない（相談中など）なら、MEMORY に黙って保存せず変更を提案する
- 消費者リポジトリで気付いたら、kit 側へ Issue／PR として上流化する
- MEMORY にあるルールが共有すべきものなら、プロンプト／ドキュメントへ移し、MEMORY 側を削除する

## upstream-to-kit — 配布ドキュメント・設定の変更は kit に上流化する

- 消費者リポジトリ（app-kit / game-kit）では、kit が配布する `CLAUDE.md` や他のドキュメント／設定をローカル編集しない（`josh sync` が上書きする）。編集前に配布物か確認し、配布物なら kit 側に Issue／PR で提案する
- kit リポジトリ自身では編集してよい。編集先は `CLAUDE.md` 1 本である（次節）

## エージェント規則の単一ソースは `CLAUDE.md`（`AGENTS.md` / `GEMINI.md` / `.cursorrules` は導線）

**規則の本体は `CLAUDE.md` にしか無い。** `AGENTS.md`・`GEMINI.md`・`.cursorrules` は「規則は `CLAUDE.md` にある。作業前に全文を読むこと」と「規則を書き戻さない」だけを書いた導線である（`.cursorrules` は Svelte MCP の案内だけを足す）。

- 規則の追加・変更・節の追加は `CLAUDE.md` に 1 回だけ書き、導線文書には書き戻さない

### Claude Code 以外のエージェントでの読み替え

Codex・Gemini CLI など別のエージェントは `CLAUDE.md` を次のように読み替える（joshuafolkken/kit#3079）。

- **フック**: フックが走らない・出力が見えないツールでは、[`rule-delivery.md`](./rule-delivery.md) →「配送されている規則」の各項目を自分で守る。加えて、最初の実行時コード編集の前に Step 0 の作業サマリを提示し、編集後に `pnpm josh lint:related` と `pnpm josh cspell:dot` を走らせ、`JOSH_SESSION_LANG` を `.env` から解決する。フックの全体は `.claude/settings.json` の `hooks`
- **Skill・`/verify-ui`・`/code-review`**: その skill の `SKILL.md` を読んで自分のセッションで従う
- **`.claude/settings.json` の deny list** は効かないが、`CLAUDE.md` → "Git Rules" はそのまま拘束する
- **`AskUserQuestion`** は、ユーザーに平文で尋ねることを指す
