## 報告フォーマット（平易な概要 ＋ 技術詳細）

作業前サマリ（Step 7）と完了報告（Step 5）は、**平易な概要を先頭に置き、技術詳細をその下に置く 2 層構造**で書く。

### 機械的な半分は `josh report:lint` が検査する

ラベルの有無、概要行の字数上限、コードフェンス囲み、概要へのファイルパス・CLI フラグの混入、ケース段と「壊れるとしたら」段の形は、サマリを標準入力で `pnpm josh report:lint` に渡して検査する（`ok` か違反行を印字する — joshuafolkken/kit#2123）。

### 骨組みは `josh report:template` が印字する

作業前サマリと完了報告の骨組みは `pnpm josh report:template summary|done [<path>...]` で印字し、写さない。ラベルは `report:lint` と同じ 1 つのラベル表（`scripts/report/report-labels.ts`）から、`JOSH_SESSION_LANG` の言語で出る（`ja` 以外は英語）。渡したパスは「対象」「変更ファイル」と変更ごとの行を埋め、そのパスに `josh cases` が求める異常系を「壊れるとしたら」の先頭に置く。残る `<…>` だけを書く。

- 出力はコードフェンスで囲まない（空白での桁揃えと単独行の `---` も使わない）
- ラベルに注釈を付けない。`■ 概要（平易な説明）` は誤り。注意書きはラベルの下の説明文に置く
- 成果物の散文（Issue 本文、Issue／PR コメント、Telegram 本文）のラベルも、このコマンドが印字するラベルで書く。英語のまま残るのは「出力の言語（`JOSH_SESSION_LANG`）」が挙げた 3 つだけ
- 区切り（hand-off）のラベル: `■ Hand-off` → `■ 区切り`、`Done` / `Remaining` / `Why it stopped` / `Next command` → `終わったこと` / `残っていること` / `止めた理由` / `次に打つコマンド`

### 作業前サマリはいつ・どう出すか

- **いつ**: 実装コードを書く前に、Issue ごとに 1 回出す。`fullrun` / `halfrun` / `prrun` / `backlogrun` で必須、`kickoff` は対象外。確認のための停止ではない — 出したらそのまま実装に進む
- **概要**: `Now` / `Change` / `Check` を各 1 文、セッション言語で、プログラマでない人にも追える文で書く。各行に具体的な主語を書き、主語のない文は不可（下記「具体的な主語を必ず書く」）。ファイルパス・関数名や型名・CLI のオプションフラグは書かない — 禁じるのは内部識別子だけである
- **技術詳細**: すべての変更をそのテストとともに `<変更内容> — Test: <Unit|E2E> — <file path> — <検証する挙動>` の形で並べる
- **完了報告**は `Cause` / `Fix` / `Result` を先頭に置く

### 作業前サマリ（セッション向け・`JOSH_SESSION_LANG` の言語）

`pnpm josh report:template summary <触るファイル...>` が印字する。各欄に書くこと:

- 概要の 3 行: 利用者から見て何が起きているか / 手段ではなく直った後どうなるか / どう確認するか
- 方針はアプローチとその理由、副作用 / スコープ外は意図的に外した点（なければ省略）
- 変更ごとの行は `<変更内容> — Test: <Unit|E2E> — <テストのファイルパス> — <検証する挙動>`

テスト宣言はケース単位の 2 段で書く（joshuafolkken/kit#2246）。

- 第 1 段（ケース）は固定語彙を並べ、**該当しないものは `該当なし` に続けて理由を書いて消す**（例:「重複: 該当なし — 入力は集合なので重複しない」）
- 第 2 段（壊れるとしたら）は、この変更に固有の壊れうる条件を**最低 3 件**書く。書けないときは `どう呼ばれても壊れない` と明示する
- 複数ケースは `it.each` 1 本に畳んでよい
- 差分が HTTP・プロセス起動・ファイル IO・時間の境界を跨ぐときは、`pnpm josh cases <path...>` が印字する異常系を第 2 段に載せる

### 行数予算は編集前に読む

**「対象」に書くファイルは、書き始める前に `pnpm josh lines <path> [<path>...]` に渡し、上限に近いと言われたファイルには分割方針を「対象」に書く**（joshuafolkken/kit#1425）。行数は `wc -l` で数えない。関数単位の上限は `pnpm josh lint` が報告する。

### 変更対象はまとめて読んでから編集する（joshuafolkken/kit#2202）

`pnpm josh read:files` / `edit:files` で畳む — [`turn-batching.md`](turn-batching.md) →「実装中の独立編集に効く合成コマンド」。

### 完了報告（セッション向け）

`pnpm josh report:template done <変更したファイル...>` が印字する。各欄に書くこと:

- 概要の 3 行: なぜそうなっていたか / 何をしたか / 利用者から見て何が変わったか（版を添える）
- 実行証跡: 実行可能な経路を触った変更では、実際に叩いたコマンドとその出力（UI ならスクリーンショット）。無いなら理由
- 捕まえられた検証: 不具合修正のみ。その検証の種類を 1 行（2 回目は台帳で昇格, #2448）
- 残課題: なければ「なし」

**実行証跡は「動くこと」の証拠であり、gate の緑ではない**（joshuafolkken/kit#2246）。同じ証跡を PR 本文の `## 実機証跡` 節（コマンド＋実出力のフェンス）にも置く。無い実行時の変更は `pnpm josh followup` がマージを拒否する（#2446）。

### PR 本文の受け入れ条件の対応表

`## 受け入れ条件の対応` 節の行の形（`pnpm josh pr` が識別子つきの `未記入` 行を付け、`pnpm josh followup` が照合する — `scripts/review/acceptance-map.ts`）:

```md
- `ac-1a2b3c4d` <条件> — 満たした: <テスト名・`file:line`・実行出力のいずれか>
- `ac-5e6f7a8b` <条件> — 見送り: #<切り出した Issue> <理由>
```

**`run:carry` の実行証跡は `JOSH_TEMP_ROOT` を新しい一時ディレクトリに向けて取る（必須）。** 状態レコードは本物の run と共有なので、`JOSH_TEMP_ROOT="$(mktemp -d)" pnpm josh run:carry --begin …` のように各コマンドの頭に付ける（`docs/environment-variables.md` → "Runs"）。`run:merge` は main の同期・lane の close・GitHub への書き込みを行うため、これでは切り離せない。

### 区切りの報告（完了報告と区別する・必須）

`backlogrun` の区切り（hand-off）は完了報告ではない — **`原因` / `対応` / `結果` を使わない**。書式は [`.claude/skills/workflow-commands/backlogrun-handoff-report.md`](../../.claude/skills/workflow-commands/backlogrun-handoff-report.md)。

### 概要 3 行の書き方（ここが本体）

字数と内部識別子の混入は `report:lint` が検査する。平易にするために語彙と抽象度を制約する:

- 専門用語は使わないか、`〜（＝…のこと）` の形でその場で言い換える
- 変更点の羅列ではなく、原因 → 対応 → 効果の因果で書く
- 主語は利用者・システムの振る舞い。「利用者から見て何が違うか」が書けない行は技術詳細に置く

**送信前セルフチェック**: コードを見ていない読み手が、概要 3 行だけでどれの話か特定できるか。できないなら具体的な名詞を 1 つ足す。

### 具体的な主語を必ず書く（禁止と対になる要求）

- **何かが「古い」「壊れている」「変わらない」と書くときは、その対象を名指しする** — 対象パッケージ名・画面名・出力の種類のいずれかを含める
- 主語のない「状況」「案内」「問題」「その処理」だけで済ませない
- 書いてよい具体名: 利用者が画面で目にするもの — パッケージ名、表示されるコマンドの目的、画面名、メッセージの種類
- 書いてはいけない具体名: 内部識別子 — ファイルパス、関数名・型名、CLI のオプションフラグ

悪い例は「古いままだと警告が出るのに、案内されたコマンドを実行しても状況が変わらない」（何の話か特定できない）。良い例:

```md
- **今こうなっている**: バージョン確認が「全体で使う app-kit が古い」と警告するのに、一緒に出る更新コマンドは既に入っている版を指していて、実行しても何も変わらず同じ警告がまた出る。
- **こう直す**: 何も変えられないコマンドを出すのをやめ、なぜ変えられないかを一行で説明し、同じコマンドが並ぶときは 1 つにまとめる。
- **確かめ方**: 自動テストで、効かないコマンドが説明に置き換わり、重複が 1 行になり、通常の表示は変わらないことを確かめる。
```

### 成果物（Issue / PR / Telegram）側

言語は「出力の言語（`JOSH_SESSION_LANG`）」に従い、構造もセッション向けと同じ 2 層にする。`--notify-message` は `Added ... / Changed ...` の羅列ではなく、`Cause / Fix / Result` の 3 行を先頭に置き、変更点を `Details:` 以下にまとめる（実例は [`followup.md`](../../.claude/skills/workflow-commands/followup.md)）。
