## 分割判定は全入口で共通（`kickoff epic` は作らない）

「実は複数 Issue が必要だった」を検出する分割判定は、かつて `kickoff new` だけが持っていた。そのため `fullrun new` は、3 件に分けるべき要望を 1 つの PR に詰め込んだままマージまで走ることができた。判定は**全ての入口が同一の定義で持つ**。正典は本節、運用手順は `.claude/skills/workflow-commands/split-assessment.md` に置く。

### 判定の問い

**その要望には、それぞれ単独でマージできる成果物が 2 つ以上含まれているか。**

基準は「単独でマージできるか」であって、規模でもファイル数でもない。正しく動くために 1 コミットで入らなければならない変更は、どれだけ大きくても 1 件である。それぞれ単独で出荷できる変更は、どれだけ小さくても 2 件である。

### 入口ごとの挙動

| 入口                          | 単一                              | 2 件以上                                              |
| ----------------------------- | --------------------------------- | ----------------------------------------------------- |
| `kickoff new`                 | Issue を 1 件作り計画を載せて停止 | 子を作り、**新規 epic** を作って停止                  |
| `kickoff #N`                  | `#N` に計画を載せて停止           | 子を作り、**`#N` を昇格**するか新規 epic を作って停止 |
| `fullrun new` / `halfrun new` | 通常どおり進む                    | 子と epic を作って**停止**                            |
| `fullrun #N` / `halfrun #N`   | 通常どおり進む                    | 子を作り、昇格または新規 epic を作って**停止**        |

### 2 件以上なら常に epic（入口による違いを作らない）

**2 件以上に分割したら常に epic を作る。件数の閾値も、実行順序の有無による分岐も無い。** これは元々 `kickoff new` の分割パスに書かれていた無条件ルールであり、判定を全入口に広げる以上、このルールも同じ入口すべてに同じ条件で適用される。**入口ごとに条件が違う状態は欠陥である** — どこで分割に気付いたかによって、その後の扱いが変わってはならない。

epic は分割理由の「閉じない置き場」である。最初の子に付けたコメントは、その子がマージされて閉じた瞬間に埋もれる。これは分割のたびに必ず起こる。

**分割で作られた子 Issue は `route:split` を付けて起票する。** `kickoff.md` の multi-issue split path の `gh api … issues` 呼び出しがそれを担い、どの入口でも同じラベルを付けることで、バックログの内訳を本文の grep ではなく機械的に集計できる（joshuafolkken/kit#1083）。

### 昇格か新規 epic かの分岐（Tier A）

`kickoff #N` と `#N` 系のランには、この分岐が 1 つだけある。AI が選び、根拠を Issue に記録する（確認不要）。

- **`#N` が要望・議論・容れ物なら昇格させる** — `pnpm josh epic --promote <N> <N1> <N2> ... [--ordered]`。本文は置換せず追記するので、分割理由そのものである元の議論がその場に残る
- **`#N` 自体が実装対象の 1 件なら、`#N` は子として残し新規 epic を立てる** — バグ報告が 3 つの修正に分かれる場合がこれで、報告を epic に昇格させると報告そのものの行き場が無くなる

### 実行系の入口で分割を検出したら停止する

`fullrun` / `halfrun` は、子と epic を作った時点で**停止する**。実装に進まないし、黙って `epicrun` に格上げもしない。

`fullrun` の起動が承認したのは「1 件の Issue を実装してマージする」ことであり、N 件のバッチではない。黙って格上げすると、**承認範囲の拡大が人の知らないところで起きる**。一括決定という関与点を 1 つ残す設計も、この停止によって守られる。作成したものを報告し、`epicrun #<E>` の実行を促して終わる。

### `kickoff epic` というキーワードは作らない

会話からの分割は `kickoff new` と完全に重複する。同じ仕事に 2 つの入口ができれば「どちらを打つべきか」を人が判断することになり、**人の関与が増える** — これらのコマンドの目的と正反対である。分割は、上の判定によって全ての入口から到達できる。

なお「別々のタイミングで起票された Issue が後から関連していると分かった場合」は分割ではないため本節の範囲外であり、`josh epic --promote` の別の使い方として joshuafolkken/kit#873 が扱う。
